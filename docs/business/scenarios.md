# Сценарии обработки заявки

## 1. Назначение

Документ описывает, как заявка на подключение ШПД проходит через систему: в трёх базовых сценариях, которые требует ТЗ, в подготовительном сценарии регистрации компании и в крайних случаях.

Документ — вход для:
- [бизнес-процесса](business-process.md) — сценарии являются его конкретными прохождениями;
- [статусной модели](../system/status-model.md) и [правил маршрутизации](../system/routing-rules.md) — какие переходы и маршруты должны поддерживаться;
- [SLA](../system/sla.md) и [уведомлений](../system/notifications.md) — где запускаются сроки и какие события возникают;
- QA — каждый сценарий и крайний случай имеет идентификатор (`SC-xx`, `EC-xx`) и может стать автотестом;
- демонстрации на защите.

Роли и их коды — по [roles.md](roles.md). Обоснование признаков маршрута — [research-b2b.md](research-b2b.md), раздел 9.

## 2. Общие условия

### 2.1. Допущения

- Услуга — ШПД для юрлица или ИП.
- **Одна заявка = одна компания-клиент + один адрес подключения.**
- Компания-клиент зарегистрирована на платформе и подтверждена (SC-00). Заявку создаёт и отправляет **представитель клиента**.
- Со стороны оператора заявку ведёт **менеджер по продажам**: закреплённый за клиентом в CRM или взятый из очереди. Он фиксирует коммерческие условия и отправляет заявку в работу.
- Данные о клиенте (сегмент, закреплённый менеджер, признак госзаказчика, задолженность) система получает из mock CRM, mock биллинга и mock справочника клиентов.
- Профильные согласования (юридическое, финансовое, закупочное) идут **параллельно**; управленческое — **после** них.
- Названия статусов ниже — **рабочие**. Финальные коды и переходы задаёт [статусная модель](../system/status-model.md).

### 2.2. Рабочие статусы заявки

| Статус | Смысл |
|---|---|
| Черновик | Представитель клиента заполняет заявку |
| Проверка данных | Система проверяет клиента во внешних системах и назначает менеджера |
| У менеджера | Менеджер проверяет заявку и фиксирует коммерческие условия |
| Проверка ТВ | Технический специалист проверяет возможность подключения |
| На согласовании | Идут одно или несколько согласований |
| На доработке | Заявка возвращена менеджеру для исправления |
| В исполнении | Стройка, монтаж, настройка |
| Услуга активирована | Канал работает, ждём подписания акта |
| Закрыта | Услуга сдана клиенту — успешный финал |
| Отклонена | Отказ: нет ТВ или согласование отклонено |
| Отменена | Отменена клиентом, менеджером или координатором |

### 2.3. Параметры заявки

| Параметр | Кто заполняет | Значения |
|---|---|---|
| Компания-клиент | Система | Из профиля представителя |
| Адрес подключения | Клиент | Текст / адрес из справочника |
| Скорость | Клиент | Мбит/с |
| Желаемая дата подключения | Клиент | Дата |
| Контактное лицо | Клиент | ФИО, телефон; по умолчанию — автор заявки |
| Пожелания по договору | Клиент | Оферта / типовой договор / договор по форме клиента |
| Комментарий клиента | Клиент | Например, запрос индивидуальной цены |
| Тариф | Менеджер | Типовой / индивидуальная цена |
| Скидка | Менеджер | % (только при индивидуальной цене) |
| Тип договора | Менеджер | Подтверждает или меняет пожелание клиента |
| Сегмент клиента | Система (CRM) | МСБ / крупный / стратегический |
| Закреплённый менеджер | Система (CRM) | Пользователь с ролью менеджера или пусто |
| Госзаказчик | Система (справочник) | Да / нет |
| Задолженность | Система (биллинг) | Сумма, ₽ |
| Результат ТВ | Технический специалист | Есть / есть со стройкой / нет |
| Затраты на стройку (CAPEX) | Технический специалист | ₽ (только при стройке) |
| Исходная заявка (`parentRequestId`) | Система | Ссылка, если заявка создана на основе отклонённой |

### 2.4. Как параметры определяют сценарий

| Признак | Стандартная | С согласованиями | Крупная |
|---|---|---|---|
| Скорость | ≤ 100 Мбит/с | > 100 Мбит/с | Любая |
| Тариф | Типовой | Индивидуальная цена / скидка | Любой |
| Договор | Оферта / типовой | Договор клиента, госзаказчик | Любой |
| Задолженность | Нет | Есть | Любая |
| Результат ТВ | Есть | Есть | **Есть со стройкой** |
| Сегмент | МСБ / крупный | МСБ / крупный | **Стратегический** или затраты выше порога |
| Согласования | Нет | Юрист и/или финансы | Закупки + финансы (+ юрист) → руководитель |

Порог управленческого согласования: **CAPEX > 500 000 ₽** или стратегический клиент. Финальные значения — в [routing-rules.md](../system/routing-rules.md).

## 3. SC-00. Регистрация компании и добавление сотрудников

**Цель:** подготовить компанию-клиента к подаче заявок. Это предусловие для SC-01…SC-03.

**Пример:** АО «Агрохолдинг Заря» впервые приходит на платформу.

### Основной поток

| № | Кто | Действие | Результат |
|---|---|---|---|
| 1 | Татьяна Морозова | Регистрируется на платформе | Аккаунт без компании |
| 2 | Татьяна Морозова | Регистрирует компанию: название, ИНН, КПП, ОГРН, юр. адрес | Компания «На подтверждении», администратор уведомлён |
| 3 | Системный администратор | Сверяет ИНН со справочником клиентов, **подтверждает** компанию | Компания «Активна», Татьяна — владелец, уведомление ей |
| 4 | Олег Никитин, Ирина Павлова | Сами регистрируются на платформе | Аккаунты без компании |
| 5 | Татьяна Морозова | Добавляет Олега по логину, отмечает роль «Администратор компании» | Олег видит компанию, может добавлять сотрудников |
| 6 | Олег Никитин | Добавляет Ирину по логину, отмечает роль «Инициатор заявок» | Ирина может подавать заявки от имени компании |

**Постусловия:** компания активна, у неё три представителя с разными ролями; все действия в истории.

### Альтернативный поток A1. Отказ в регистрации

На шаге 3 администратор **отклоняет** компанию с причиной («ИНН не найден в справочнике клиентов»). Компания «Отклонена», представитель уведомлён и может подать регистрацию повторно с исправленными данными.

## 4. SC-01. Стандартная заявка

**Цель:** показать самый короткий путь — без согласований.

**Пример:** ИП Соколов А. В. (кофейня, сегмент МСБ) хочет интернет 100 Мбит/с, договор — оферта. Адрес уже подключён к сети оператора. За клиентом в CRM закреплена менеджер Анна Смирнова.

**Предусловия:** компания активна (SC-00), задолженности нет.

**Маршрут:** Проверка ТВ → Монтаж и настройка → Активация → Закрытие.

### Основной поток

| № | Кто | Действие | Результат |
|---|---|---|---|
| 1 | Представитель клиента | Создаёт заявку: адрес, скорость, дата, контакт, пожелание «оферта» | Статус «Черновик» |
| 2 | Представитель клиента | Отправляет заявку оператору | Статус «Проверка данных» |
| 3 | Система | Запрашивает CRM, биллинг, справочник: долга нет, сегмент МСБ, закреплённый менеджер — Анна Смирнова | Данные подтянуты, заявка назначена менеджеру, статус «У менеджера» |
| 4 | Менеджер | Проверяет заявку, фиксирует типовой тариф и оферту, отправляет в работу | Система строит маршрут: согласования не нужны |
| 5 | Система | Создаёт этап «Проверка ТВ» в очереди технических специалистов, запускает SLA | Статус «Проверка ТВ» |
| 6 | Тех. специалист | Берёт этап, вносит результат ТВ: **есть** | Создан этап «Монтаж и настройка» в очереди инженеров, статус «В исполнении» |
| 7 | Инженер | Берёт этап, выполняет монтаж и настройку, отмечает выполненным | Создан этап «Активация» |
| 8 | Инженер | Тестирует канал, отмечает «Услуга активирована» | Статус «Услуга активирована» |
| 9 | Менеджер | Подтверждает, что клиент подписал акт, закрывает заявку | Статус «Закрыта» |

**Постусловия:** услуга активирована, заявка закрыта; в истории — все шаги, исполнители и время.

**Уведомления:** представителю клиента — о смене статусов; менеджеру — о назначении заявки и смене статусов; очереди роли — о новом этапе; исполнителю — о назначении.

## 5. SC-02. Заявка с дополнительными согласованиями

**Цель:** показать, как параметры заявки добавляют согласования, как работают параллельные согласования и возврат на доработку.

**Пример:** ООО «Логистик Плюс» (сегмент «крупный») подключает склад: 500 Мбит/с, договор по форме клиента. В комментарии клиент просит скидку. Менеджер фиксирует индивидуальную цену со скидкой 15%. Адрес подключён к сети.

**Предусловия:** компания активна, задолженности нет.

**Почему нужны согласования:**
- скорость > 100 Мбит/с и скидка → **финансовое согласование**;
- договор по форме клиента → **юридическое согласование**.

**Маршрут:** Проверка ТВ → (Юридическое ‖ Финансовое) → Монтаж и настройка → Активация → Закрытие.

### Основной поток

| № | Кто | Действие | Результат |
|---|---|---|---|
| 1–3 | Представитель клиента, Система | Как в SC-01 | Статус «У менеджера» |
| 4 | Менеджер | Фиксирует индивидуальную цену, скидку 15%, тип договора «по форме клиента», отправляет в работу | Система строит маршрут: нужны юридическое и финансовое согласования |
| 5 | Тех. специалист | Вносит результат ТВ: **есть** | Параллельно созданы этапы «Юридическое согласование» и «Финансовое согласование»; статус «На согласовании» |
| 6 | Финансовый контролёр | Проверяет цену и скидку, **согласует** | Этап завершён, ждём юриста |
| 7 | Юрист | Проверяет договор клиента, **согласует** | Все согласования пройдены. Создан этап «Монтаж и настройка», статус «В исполнении» |
| 8–10 | Инженер, Менеджер | Как шаги 7–9 в SC-01 | Статус «Закрыта» |

### Альтернативный поток A1. Возврат на доработку юристом

| № | Кто | Действие | Результат |
|---|---|---|---|
| 7а | Юрист | **Возвращает на доработку**: «Нужен протокол разногласий по п. 5.2 об ответственности» | Статус «На доработке», SLA этапа юриста приостановлен, менеджер уведомлён, клиент видит статус |
| 7б | Менеджер | Запрашивает у клиента протокол разногласий комментарием, получает его, отправляет заявку повторно | Параметры маршрута не изменились — заявка возвращается на этап юриста, SLA возобновлён |
| 7в | Юрист | **Согласует** | Продолжение с шага 8 |

Решение финансового контролёра сохраняется: цена и скидка не менялись.

### Альтернативный поток A2. Изменение параметров при доработке

Если при доработке менеджер меняет параметр, влияющий на маршрут (например, клиент согласился на типовой тариф без скидки), система **пересобирает маршрут**: финансовое согласование больше не нужно и отменяется (если ещё не завершено), пройденные этапы остаются в истории.

## 6. SC-03. Крупная / нестандартная заявка

**Цель:** показать полный маршрут — стройку, все виды согласований и управленческое решение.

**Пример:** АО «Агрохолдинг Заря» (сегмент «стратегический») подключает новый логистический центр за городом: 1 Гбит/с, договор по форме клиента. Заявку подаёт Ирина Павлова. Сети оператора до объекта нет — нужна прокладка оптики.

**Предусловия:** компания активна (SC-00), задолженности нет.

**Почему такой маршрут:**
- договор клиента → **юридическое**;
- индивидуальная цена + стройка → **финансовое**;
- стройка (подрядчик, оборудование) → **закупочное**;
- стратегический клиент и CAPEX > порога → **управленческое**.

**Маршрут:** Проверка ТВ → (Юридическое ‖ Финансовое ‖ Закупочное) → Управленческое → Стройка → Монтаж и настройка → Активация → Закрытие.

### Основной поток

| № | Кто | Действие | Результат |
|---|---|---|---|
| 1–3 | Представитель клиента, Система | Как в SC-01; CRM возвращает сегмент «стратегический»; закреплённого менеджера нет | Заявка в очереди менеджеров |
| 4 | Менеджер | Берёт заявку из очереди, фиксирует индивидуальную цену и договор клиента, отправляет в работу | Предварительный маршрут: юридическое, финансовое, управленческое (стратегический клиент) |
| 5 | Тех. специалист | Вносит результат ТВ: **есть со стройкой**, CAPEX 1 200 000 ₽, срок стройки 30 дней | Система **дополняет маршрут** закупочным согласованием. Параллельно созданы три этапа согласования; статус «На согласовании» |
| 6 | Специалист по закупкам | Подтверждает оборудование и подрядчика, **согласует** | Этап завершён |
| 7 | Финансовый контролёр | Оценивает окупаемость, **согласует** | Этап завершён |
| 8 | Юрист | Проверяет договор, **согласует** | Профильные согласования пройдены. Создан этап «Управленческое согласование» |
| 9 | Руководитель B2B | Видит в карточке все решения и комментарии, **согласует** | Создан этап «Стройка», статус «В исполнении» |
| 10 | Инженер | Фиксирует завершение стройки (силами подрядчика) | Создан этап «Монтаж и настройка» |
| 11–13 | Инженер, Менеджер | Как шаги 7–9 в SC-01 | Статус «Закрыта» |

### Альтернативный поток A1. Отклонение руководителем

На шаге 9 руководитель **отклоняет** заявку с причиной («Окупаемость больше 5 лет»). Заявка «Отклонена», менеджер и клиент уведомлены. Профильные согласования остаются в истории. Клиент может создать новую заявку на основе отклонённой (например, на LTE-решение) — см. EC-01.

### 7.2. Описание

**EC-01. Нет технической возможности.**
Тех. специалист вносит результат ТВ «нет» с причиной («до здания нет кабельной канализации, стройка невозможна»). Система автоматически переводит заявку в «Отклонена», причина сохраняется в истории, менеджер и клиент уведомлены. Клиент может создать **новую заявку на основе отклонённой** (например, на LTE-решение): данные копируются, новая заявка ссылается на исходную через `parentRequestId`.

**EC-02. Некорректные данные заявки.**
Не заполнены обязательные поля или неверный формат (например, скорость 0) — система не даёт отправить заявку оператору. Если ошибку замечает менеджер на этапе «У менеджера» (например, неточный адрес), он уточняет у клиента комментарием и исправляет данные сам.

**EC-03. У клиента задолженность.**
Стандартная по параметрам заявка (100 Мбит/с, типовой тариф), но биллинг возвращает долг 45 000 ₽. Система добавляет в маршрут **финансовое согласование** — фактически заявка идёт по SC-02. Финансовый контролёр решает: согласовать, вернуть или отклонить.

**EC-04. Стройка у «стандартной» заявки.**
Маршрут был коротким (как SC-01), но тех. специалист вносит «есть со стройкой». Система пересобирает маршрут: добавляются закупочное и финансовое согласования, а при CAPEX выше порога — управленческое. Маршрут **динамический**.

**EC-05. Отклонение одного из параллельных согласований.**
В SC-02 финансы согласовали, а юрист отклонил («клиент требует неограниченную ответственность оператора»). Заявка «Отклонена»; незавершённые параллельные согласования **отменяются**, их исполнители уведомлены.

**EC-06. Этап никто не взял.**
SLA этапа идёт с момента попадания в очередь. При приближении срока уведомление получает вся очередь роли и координатор; координатор назначает исполнителя вручную.

**EC-07. Нарушение SLA.**
Юрист не принял решение в срок. При приближении — уведомление юристу. При нарушении — уведомление юристу и координатору, этап помечен как просроченный. Координатор переназначает этап или выясняет причину. При повторном нарушении — уведомление руководителю B2B. Заявка **не отклоняется** автоматически.

**EC-08. Клиент отказался в процессе.**
Представитель клиента сам отменяет заявку с причиной (или просит менеджера). Все активные этапы отменяются, исполнители уведомлены, статус «Отменена».

**EC-09. Попытка отменить после активации.**
После отметки «Услуга активирована» отмена недоступна: прекращение услуги — это расторжение договора, которое вне границ проекта (см. [scope.md](../scope.md)).

**EC-10. Внешняя система недоступна.**
Mock CRM отвечает ошибкой. Система повторяет запрос (retry). Если ответ не получен — заявка остаётся в «Проверке данных» с пометкой об ошибке интеграции, координатор уведомлён, проверку можно запустить повторно. Заявка **не отклоняется** из-за технического сбоя.

**EC-11. Проблема на объекте.**
У клиента нет доступа в серверную. Инженер сообщает о проблеме, координатор **приостанавливает SLA** этапа, менеджер договаривается с клиентом о новой дате, затем координатор возобновляет SLA.

**EC-12. Дубль заявки.**
По той же компании и адресу уже есть незакрытая заявка. Система предупреждает, но не запрещает (бывает второй канал). Если это ошибка — координатор отменяет дубль с причиной «Дубль».

**EC-13. Повторный возврат на доработку.**
Ограничения на число возвратов нет; каждая итерация (кто вернул, причина, что исправлено) сохраняется в истории.

**EC-14. Компания не подтверждена.**
Представитель компании в статусе «На подтверждении» не может создать заявку: кнопка недоступна, в интерфейсе плашка «Компания ожидает подтверждения».

**EC-15. Компания с таким ИНН уже есть.**
При регистрации компании система находит активную компанию с тем же ИНН и не даёт зарегистрировать дубль. Пользователю предлагается обратиться к владельцу компании, чтобы тот добавил его.

**EC-16. Доступ к заявке чужой компании.**
Представитель ООО «Логистик Плюс» открывает ссылку на заявку АО «Агрохолдинг Заря». Система отказывает в доступе (изоляция данных между компаниями); попытка пишется в лог.

**EC-17. Сотрудник удалён из компании.**
Владелец удаляет инициатора, у которого есть незакрытая заявка. Сотрудник теряет доступ к данным компании; заявка продолжает обработку и остаётся видна другим представителям компании; история его действий сохраняется.

**EC-18. Менеджер с ролью согласующего на своей заявке.**
У менеджера есть ещё роль финансового контролёра. На заявке, где он менеджер, этап финансового согласования ему недоступен — его берёт другой финансовый контролёр (разделение обязанностей).

**EC-19. Менеджер не назначен.**
За клиентом не закреплён менеджер, а из очереди менеджеров заявку никто не взял. Работает тот же механизм, что в EC-06: предупреждение очереди и координатору, координатор назначает менеджера.

## 10. Сценарий демонстрации

Предлагаемая последовательность на защите (~15 минут). Для демо включается профиль с нормативами SLA в минутах.

1. **SC-00 коротко** — подтверждение ООО «Вектор» администратором и добавление сотрудника по логину (остальные компании уже созданы сидом).
2. **SC-01** — клиент подаёт заявку, менеджер отправляет в работу, заявка быстро проходит без согласований. Показать, что клиент видит статус у себя.
3. **SC-03** с переключением пользователей — динамическое дополнение маршрута после ТВ (стройка), параллельные согласования, решение руководителя. На Игоре Киме показать **переключатель ролей** (тех. специалист → инженер).
4. **SC-02, поток A1** — возврат на доработку и пауза SLA.
5. **EC-07** — заранее подготовленная заявка с истекающим сроком: предупреждение, нарушение, эскалация координатору.
6. **EC-01** — отказ по ТВ и создание новой заявки на основе отклонённой.
7. Карточка заявки — **история** всех действий.

## 11. Принятые решения

Ответы тимлида на открытые вопросы, 2026-10-13.

| № | Вопрос | Решение |
|---|---|---|
| 1 | Параллельные или последовательные профильные согласования | Параллельные; управленческое — после них |
| 2 | Сохраняются ли решения других согласующих после возврата | Да, если не изменились параметры, на которые они влияют |
| 3 | Порог управленческого согласования | CAPEX > 500 000 ₽ или стратегический клиент |
| 4 | Недоступность внешней системы | Ждать с повторной проверкой, не пропускать и не отклонять |
| 5 | Ускорение SLA для демо | Отдельный профиль с нормативами в минутах |
| 6 | Ограничение на число возвратов | Нет |
| 7 | Кто подаёт заявку | Представитель зарегистрированной компании-клиента |
| 8 | ТВ «нет» | Автоматический отказ; новая заявка ссылается на исходную (`parentRequestId`) |
