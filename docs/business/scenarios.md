# Сценарии обработки заявки

## 1. Назначение

Документ описывает, как заявка на подключение ШПД проходит через систему в трёх базовых сценариях, которые требует ТЗ, и в крайних случаях.

Документ — вход для:
- [бизнес-процесса](business-process.md) — сценарии являются его конкретными прохождениями;
- [статусной модели](../system/status-model.md) и [правил маршрутизации](../system/routing-rules.md) — какие переходы и маршруты должны поддерживаться;
- [SLA](../system/sla.md) и [уведомлений](../system/notifications.md) — где запускаются сроки и какие события возникают;
- QA — каждый сценарий и крайний случай имеет идентификатор (`SC-xx`, `EC-xx`) и может стать автотестом;
- демонстрации на защите.

Роли и их коды — по [roles.md](roles.md). Обоснование признаков маршрута — [research-b2b.md](research-b2b.md), раздел 9.

## 2. Общие условия

### 2.1. Допущения

- Услуга — ШПД для юрлица или ИП.
- **Одна заявка = один клиент + один адрес подключения.**
- Заявку создаёт менеджер по продажам от имени клиента.
- Данные о клиенте (реквизиты, сегмент, признак госзаказчика, задолженность) система получает из mock CRM, mock биллинга и mock справочника клиентов.
- Профильные согласования (юридическое, финансовое, закупочное) идут **параллельно**; управленческое — **после** них. Это предложение, финально — в [routing-rules.md](../system/routing-rules.md).
- Названия статусов ниже — **рабочие**. Финальные коды и переходы задаёт [статусная модель](../system/status-model.md).

### 2.2. Рабочие статусы заявки

| Статус | Смысл |
|---|---|
| Черновик | Заявка создаётся менеджером, ещё не отправлена |
| Проверка данных | Система проверяет клиента во внешних системах |
| Проверка ТВ | Технический специалист проверяет возможность подключения |
| На согласовании | Идут одно или несколько согласований |
| На доработке | Заявка возвращена менеджеру для исправления |
| В исполнении | Стройка, монтаж, настройка |
| Услуга активирована | Канал работает, ждём подписания акта |
| Закрыта | Услуга сдана клиенту — успешный финал |
| Отклонена | Отказ: нет ТВ или согласование отклонено |
| Отменена | Отменена клиентом или координатором |

### 2.3. Параметры заявки

| Параметр | Кто заполняет | Значения |
|---|---|---|
| Клиент (ИНН) | Менеджер | Из справочника клиентов |
| Адрес подключения | Менеджер | Текст / адрес из справочника |
| Скорость | Менеджер | Мбит/с |
| Тариф | Менеджер | Типовой / индивидуальная цена |
| Скидка | Менеджер | % (только при индивидуальной цене) |
| Тип договора | Менеджер | Оферта / типовой договор / договор по форме клиента |
| Желаемая дата подключения | Менеджер | Дата |
| Контактное лицо клиента | Менеджер | ФИО, телефон |
| Сегмент клиента | Система (CRM) | МСБ / крупный / стратегический |
| Госзаказчик | Система (справочник) | Да / нет |
| Задолженность | Система (биллинг) | Сумма, ₽ |
| Результат ТВ | Технический специалист | Есть / есть со стройкой / нет |
| Затраты на стройку (CAPEX) | Технический специалист | ₽ (только при стройке) |

### 2.4. Как параметры определяют сценарий

| Признак | Стандартная | С согласованиями | Крупная |
|---|---|---|---|
| Скорость | ≤ 100 Мбит/с | > 100 Мбит/с | Любая |
| Тариф | Типовой | Индивидуальная цена / скидка | Любой |
| Договор | Оферта / типовой | Договор клиента, госзаказчик | Любой |
| Задолженность | Нет | Есть | Любая |
| Результат ТВ | Есть | Есть | **Есть со стройкой** |
| Сегмент | МСБ / крупный | МСБ / крупный | **Стратегический** или затраты выше порога |
| Согласования | Нет | Юрист и/или финансы | Закупки + финансы (+ юрист) → руководитель |

Пороговые значения для примеров: управленческое согласование нужно, если **CAPEX > 500 000 ₽** или клиент стратегический. Значения условные; финальные — в [routing-rules.md](../system/routing-rules.md).

## 3. SC-01. Стандартная заявка

**Цель:** показать самый короткий путь — без согласований.

**Пример:** ИП Соколов А. В. (кофейня, сегмент МСБ) хочет интернет 100 Мбит/с по типовому тарифу, договор — оферта. Адрес уже подключён к сети оператора.

**Предусловия:** клиент есть в справочнике, задолженности нет.

**Маршрут:** Проверка ТВ → Монтаж и настройка → Активация → Закрытие.

### Основной поток

| № | Кто | Действие | Результат |
|---|---|---|---|
| 1 | Менеджер | Создаёт заявку, заполняет параметры | Статус «Черновик» |
| 2 | Менеджер | Отправляет заявку в работу | Статус «Проверка данных» |
| 3 | Система | Запрашивает CRM, биллинг, справочник: клиент найден, долга нет, сегмент МСБ | Данные клиента подтянуты в заявку |
| 4 | Система | Строит маршрут по правилам: согласования не нужны | Создан этап «Проверка ТВ» в очереди технических специалистов, запущен SLA этапа, статус «Проверка ТВ» |
| 5 | Тех. специалист | Берёт этап в работу | Назначен исполнитель |
| 6 | Тех. специалист | Вносит результат ТВ: **есть** | Маршрут не меняется. Создан этап «Монтаж и настройка» в очереди инженеров, статус «В исполнении» |
| 7 | Инженер | Берёт этап, выполняет монтаж и настройку, отмечает выполненным | Создан этап «Активация» |
| 8 | Инженер | Тестирует канал, отмечает «Услуга активирована» | Статус «Услуга активирована» |
| 9 | Менеджер | Подтверждает, что клиент подписал акт, закрывает заявку | Статус «Закрыта» |

**Постусловия:** услуга активирована, заявка закрыта, в истории — все шаги, исполнители и время.

**Уведомления:** менеджеру — о смене статусов; очереди роли — о новом этапе; исполнителю — о назначении.

## 4. SC-02. Заявка с дополнительными согласованиями

**Цель:** показать, как параметры заявки добавляют согласования, и как работают параллельные согласования и возврат на доработку.

**Пример:** ООО «Логистик Плюс» (сегмент «крупный») подключает склад: 500 Мбит/с, индивидуальная цена со скидкой 15%, договор по форме клиента. Адрес подключён к сети.

**Предусловия:** клиент есть в справочнике, задолженности нет.

**Почему нужны согласования:**
- скорость > 100 Мбит/с и скидка → **финансовое согласование**;
- договор по форме клиента → **юридическое согласование**.

**Маршрут:** Проверка ТВ → (Юридическое ‖ Финансовое) → Монтаж и настройка → Активация → Закрытие.

### Основной поток

| № | Кто | Действие | Результат |
|---|---|---|---|
| 1–3 | Менеджер, Система | Как в SC-01 | Данные клиента подтянуты |
| 4 | Система | Строит маршрут: нужны юридическое и финансовое согласования | Этап «Проверка ТВ», статус «Проверка ТВ» |
| 5 | Тех. специалист | Вносит результат ТВ: **есть** | Созданы параллельно этапы «Юридическое согласование» и «Финансовое согласование» в очередях ролей; статус «На согласовании» |
| 6 | Финансовый контролёр | Проверяет цену и скидку, **согласует** | Этап завершён, ждём юриста |
| 7 | Юрист | Проверяет договор клиента, **согласует** | Все согласования пройдены. Создан этап «Монтаж и настройка», статус «В исполнении» |
| 8–10 | Инженер, Менеджер | Как шаги 7–9 в SC-01 | Статус «Закрыта» |

### Альтернативный поток A1. Возврат на доработку юристом

| № | Кто | Действие | Результат |
|---|---|---|---|
| 7а | Юрист | **Возвращает на доработку**: «Нужен протокол разногласий по п. 5.2 об ответственности» | Статус «На доработке», SLA этапа юриста приостановлен, менеджер уведомлён |
| 7б | Менеджер | Согласует с клиентом, прикладывает протокол разногласий, отправляет повторно | Параметры маршрута не изменились — заявка возвращается на этап юриста, SLA возобновлён, статус «На согласовании» |
| 7в | Юрист | **Согласует** | Продолжение с шага 8 |

Решение финансового контролёра, принятое до возврата, сохраняется — повторно согласовывать не нужно, так как цена и скидка не менялись.

### Альтернативный поток A2. Изменение параметров при доработке

Если при доработке менеджер меняет параметр, влияющий на маршрут (например, клиент согласился на типовой тариф без скидки), система **пересобирает маршрут**: финансовое согласование больше не требуется и отменяется (если ещё не завершено), уже пройденные этапы остаются в истории.

## 5. SC-03. Крупная / нестандартная заявка

**Цель:** показать полный маршрут — стройку, все виды согласований и управленческое решение.

**Пример:** АО «Агрохолдинг Заря» (сегмент «стратегический») подключает новый логистический центр за городом: 1 Гбит/с, индивидуальная цена, договор по форме клиента. Сети оператора до объекта нет — нужна прокладка оптики.

**Предусловия:** клиент есть в справочнике, задолженности нет.

**Почему такой маршрут:**
- договор клиента → **юридическое**;
- индивидуальная цена + стройка → **финансовое**;
- стройка (подрядчик, оборудование) → **закупочное**;
- стратегический клиент и CAPEX > порога → **управленческое**.

**Маршрут:** Проверка ТВ → (Юридическое ‖ Финансовое ‖ Закупочное) → Управленческое → Стройка → Монтаж и настройка → Активация → Закрытие.

### Основной поток

| № | Кто | Действие | Результат |
|---|---|---|---|
| 1–3 | Менеджер, Система | Как в SC-01; CRM возвращает сегмент «стратегический» | Данные клиента подтянуты |
| 4 | Система | Строит предварительный маршрут: юридическое, финансовое, управленческое (стратегический клиент) | Этап «Проверка ТВ» |
| 5 | Тех. специалист | Вносит результат ТВ: **есть со стройкой**, CAPEX 1 200 000 ₽, срок стройки 30 дней | Система **дополняет маршрут** закупочным согласованием. Параллельно созданы три этапа согласования; статус «На согласовании» |
| 6 | Специалист по закупкам | Подтверждает оборудование и подрядчика, **согласует** | Этап завершён |
| 7 | Финансовый контролёр | Оценивает окупаемость, **согласует** | Этап завершён |
| 8 | Юрист | Проверяет договор, **согласует** | Все профильные согласования пройдены. Создан этап «Управленческое согласование» |
| 9 | Руководитель B2B | Видит в карточке все решения и комментарии, **согласует** | Создан этап «Стройка», статус «В исполнении» |
| 10 | Инженер | Фиксирует завершение стройки (силами подрядчика) | Создан этап «Монтаж и настройка» |
| 11–13 | Инженер, Менеджер | Как шаги 7–9 в SC-01 | Статус «Закрыта» |

### Альтернативный поток A1. Отклонение руководителем

На шаге 9 руководитель **отклоняет** заявку с причиной («Окупаемость больше 5 лет, предложить клиенту LTE-решение»). Заявка переходит в «Отклонена», менеджер уведомлён. Профильные согласования остаются в истории.

## 6. Крайние случаи

### 6.1. Сводная таблица

| ID | Ситуация | Где возникает | Чем заканчивается |
|---|---|---|---|
| EC-01 | Нет технической возможности | Проверка ТВ | Отклонена |
| EC-02 | Клиент не найден / некорректные данные | Проверка данных | Возврат менеджеру до запуска маршрута |
| EC-03 | У клиента задолженность | Проверка данных | В маршрут добавляется финансовое согласование |
| EC-04 | Стройка выявлена у «стандартной» заявки | Проверка ТВ | Маршрут пересобирается |
| EC-05 | Одно из параллельных согласований отклонено | На согласовании | Отклонена, остальные согласования отменены |
| EC-06 | Этап никто не взял из очереди | Любой этап | Предупреждение очереди → координатор назначает |
| EC-07 | Нарушен SLA этапа | Любой этап | Эскалация координатору, затем руководителю |
| EC-08 | Клиент отказался в процессе | До активации | Отменена |
| EC-09 | Попытка отменить после активации | После активации | Запрещено системой |
| EC-10 | Внешняя система недоступна | Проверка данных | Повтор запросов, при неудаче — ожидание и уведомление |
| EC-11 | Проблема на объекте при монтаже | В исполнении | Ожидание клиента, SLA приостановлен |
| EC-12 | Дубль заявки | Создание | Предупреждение; координатор отменяет дубль |
| EC-13 | Повторный возврат на доработку | На согласовании | Допустим; все итерации видны в истории |

### 6.2. Описание

**EC-01. Нет технической возможности.**
Тех. специалист вносит результат ТВ «нет» с причиной («до здания нет кабельной канализации, стройка невозможна»). Система переводит заявку в «Отклонена». Менеджер получает уведомление и может предложить клиенту альтернативу отдельной заявкой.

**EC-02. Клиент не найден или данные некорректны.**
При отправке заявки справочник не находит клиента по ИНН (или ИНН неверного формата). Маршрут **не строится**, заявка остаётся в «Черновике» с сообщением об ошибке. Согласования по заведомо некорректной заявке не запускаются.

**EC-03. У клиента задолженность.**
Стандартная по параметрам заявка (100 Мбит/с, типовой тариф), но биллинг возвращает долг 45 000 ₽. Система добавляет в маршрут **финансовое согласование** — фактически заявка идёт по SC-02. Финансовый контролёр решает: согласовать (например, при гарантии оплаты), вернуть или отклонить.

**EC-04. Стройка у «стандартной» заявки.**
Маршрут при создании был коротким (как SC-01), но тех. специалист вносит «есть со стройкой». Система пересобирает маршрут: добавляются закупочное и финансовое согласования, а при CAPEX выше порога — управленческое. Это показывает, что маршрут **динамический** и может меняться по результатам этапов.

**EC-05. Отклонение одного из параллельных согласований.**
В SC-02 финансы согласовали, а юрист отклонил («клиент требует неограниченную ответственность оператора»). Заявка переходит в «Отклонена»; если какие-то параллельные согласования ещё не завершены, они **отменяются**, их исполнители получают уведомление.

**EC-06. Этап никто не взял.**
Этап лежит в очереди роли без исполнителя. SLA этапа идёт с момента попадания в очередь. При приближении срока уведомление получает вся очередь роли и координатор; координатор назначает исполнителя вручную.

**EC-07. Нарушение SLA.**
Юрист не принял решение в срок. При приближении срока — уведомление юристу. При нарушении — уведомление юристу и координатору, этап помечается как просроченный. Координатор переназначает этап на другого юриста или выясняет причину. При повторном нарушении — уведомление руководителю B2B. Заявка при этом **не отклоняется** автоматически.

**EC-08. Клиент отказался в процессе.**
На этапе согласований клиент сообщает менеджеру, что передумал. Менеджер отменяет заявку с причиной. Все активные этапы отменяются, их исполнители уведомлены, статус «Отменена».

**EC-09. Попытка отменить после активации.**
После отметки «Услуга активирована» отмена недоступна: прекращение услуги — это расторжение договора, которое вне границ проекта (см. [scope.md](../scope.md)).

**EC-10. Внешняя система недоступна.**
Mock CRM отвечает ошибкой. Система повторяет запрос несколько раз (retry). Если ответ так и не получен — заявка остаётся в «Проверке данных» с пометкой об ошибке интеграции, координатор уведомлён, проверку можно запустить повторно. Заявка **не отклоняется** из-за технического сбоя.

**EC-11. Проблема на объекте.**
Инженер приехал на монтаж, но у клиента нет доступа в серверную. Инженер сообщает о проблеме, координатор **приостанавливает SLA** этапа (ожидание клиента), менеджер договаривается о новой дате. После этого координатор возобновляет SLA.

**EC-12. Дубль заявки.**
Менеджер создаёт заявку на клиента и адрес, по которым уже есть незакрытая заявка. Система предупреждает о возможном дубле, но не запрещает (бывают легитимные случаи, например второй канал). Если это ошибка — координатор отменяет дубль с причиной «Дубль».

**EC-13. Повторный возврат на доработку.**
Согласующий может вернуть заявку несколько раз. Ограничения на число возвратов нет; каждая итерация (кто вернул, причина, что исправлено) сохраняется в истории.

## 9. Сценарий демонстрации

Предлагаемая последовательность на защите (~10–15 минут):

1. **SC-01** целиком — показать, что простая заявка проходит быстро и без лишних участников.
2. **SC-03** с переключением между ролями — показать динамическое дополнение маршрута после ТВ (стройка), параллельные согласования и решение руководителя.
3. **SC-02, поток A1** — возврат на доработку и паузу SLA.
4. **EC-07** — заранее подготовленная заявка с истекающим сроком: предупреждение и нарушение SLA, эскалация координатору.
5. Карточка заявки — **история** всех действий.

Для пункта 4 нужна возможность ускорить время или задать короткие нормативы SLA в демо-конфигурации — согласовать с Димой и Салаватом.
