# Исследование B2B-телеком и аналогов

## 1. Цель и метод

**Цель:** понять, как устроена обработка заявок на подключение B2B-услуг у операторов связи и в промышленных OSS/BSS-системах, и выделить, что из этого берём в учебный прототип B2B-Order-Flow.

**Что изучено:**
- предметная область — процесс подключения корпоративного клиента (на примере ШПД);
- отраслевые стандарты TM Forum (eTOM, Open API);
- четыре аналога: Netcracker, Amdocs, CSG, Salesforce Communications Cloud;
- российский контекст — практика МТС и импортозамещение OSS/BSS.

**Метод:** анализ открытых материалов вендоров, стандартов TM Forum и отраслевых публикаций (см. раздел 10). Внутренняя документация вендоров недоступна, поэтому сравнение идёт на уровне функциональных возможностей, а не реализации.

## 2. Предметная область: B2B-подключение в телекоме

### 2.1. Чем B2B отличается от B2C

| Аспект | B2C (физлица) | B2B (юрлица) |
|---|---|---|
| Клиент | Физлицо | Юрлицо / ИП, часто группа компаний |
| Договор | Публичная оферта | Оферта для типовых услуг, индивидуальный договор для крупных |
| Условия | Типовой тариф | Индивидуальные цена, скорость, SLA, скидки |
| Адреса | Один | Один или несколько (филиальная сеть) |
| Участники со стороны оператора | Продажи + монтаж | Продажи, техника, юристы, финансы, закупки, руководство |
| Сроки подключения | Дни | От дней до месяцев (если нужна стройка) |
| Обязательства | Минимальные | SLA по доступности и сроку подключения, штрафы |
| Решение о сделке | Сразу | Через согласования внутри оператора |

Главное следствие для проекта: **в B2B маршрут заявки не фиксирован**. Одна и та же услуга (ШПД) может пройти по короткому пути «проверка → подключение» или по длинному — через юристов, финансы, закупки и руководство. Именно это и требует ТЗ.

### 2.2. Сквозной процесс у оператора

В отрасли процесс от интереса клиента до выставления счёта называют **Lead-to-Cash**, а его исполнительную часть — **Order-to-Activate (O2A)**.

```text
Лид → Сделка → Расчёт/КП → Договор → Заказ → Исполнение → Активация → Биллинг → Обслуживание
                                      └──────── фокус B2B-Order-Flow ────────┘
```

Наш проект покрывает отрезок **от создания заявки до активации услуги и закрытия заявки** (см. [scope.md](../scope.md)). Продажи, биллинг и обслуживание — вне границ.

### 2.3. Типовые этапы подключения ШПД для юрлица

| № | Этап | Что происходит | Кто выполняет |
|---|---|---|---|
| 1 | Приём заявки | Фиксация клиента, адреса, услуги, параметров | Менеджер по продажам |
| 2 | Проверка данных клиента | Сверка реквизитов, статус клиента, задолженность | Менеджер / автоматически (CRM, биллинг) |
| 3 | Проверка технической возможности (ТВ) | Есть ли «последняя миля» до адреса, свободные порты, нужна ли стройка | Технический специалист |
| 4 | Обследование объекта | Выезд на адрес — только если ТВ неочевидна | Инженер |
| 5 | Согласования | Юридическое, финансовое, закупочное, управленческое — по необходимости | Профильные подразделения |
| 6 | Договор | Типовой (оферта) или индивидуальный | Менеджер + юрист |
| 7 | Строительство | Прокладка кабеля, закупка оборудования — если нет ТВ «из коробки» | Подрядчик / эксплуатация |
| 8 | Монтаж и настройка | Установка оборудования, настройка канала | Монтажник / инженер |
| 9 | Активация и сдача | Тест канала, акт приёма-передачи, запуск в биллинге | Инженер + менеджер |
| 10 | Закрытие заявки | Фиксация результата | Система / менеджер |

**Результаты проверки ТВ** на практике бывают трёх видов, и это ключевой параметр маршрута:
- **есть** — адрес подключён к сети, нужен только монтаж;
- **есть со стройкой** — нужна прокладка «последней мили», закупка, затраты (CAPEX);
- **нет** — подключение невозможно или экономически нецелесообразно → отказ или альтернатива (например, LTE).

## 3. Российский контекст

### 3.1. Кейс МТС: онлайн-подключение ШПД для бизнеса

В ноябре 2025 МТС запустила онлайн-подключение интернета для малого и среднего бизнеса и ИП:
1. клиент вводит адрес офиса → проверка технической возможности;
2. выбирает предложение по скорости и цене;
3. принимает оферту;
4. оплачивает автоматически сформированный счёт.

Онлайн доступно для скоростей **до 100 Мбит/с**; большие скорости и особые требования оформляются **через менеджера**.

**Вывод для проекта:** у самого заказчика уже есть граница между «стандартной» заявкой (типовой тариф, оферта, без участия людей) и «нестандартной» (индивидуальные условия, менеджер, согласования). Эту границу логично взять за основу правил маршрутизации.

### 3.2. Рынок OSS/BSS в России

- Крупные российские операторы исторически использовали западные OSS/BSS (Netcracker, Amdocs, Oracle и др.).
- В 2022 Netcracker объявил об уходе из России; при этом, по открытым данным, его российское юрлицо продолжает работать.
- Операторы ведут импортозамещение; российские вендоры (например, Nexign) заявляют соответствие стандартам TM Forum.

**Вывод для проекта:** стандарты TM Forum остаются общим языком отрасли и для российских систем. Ориентироваться на них — правильно: это понятно заказчику и не привязывает к конкретному вендору.

## 4. Отраслевые стандарты TM Forum

TM Forum — международная ассоциация операторов и вендоров, которая задаёт эталонные процессы, модели данных и API для OSS/BSS.

### 4.1. eTOM — карта процессов

В eTOM наш процесс относится к вертикали **Fulfillment** (исполнение): приём заказа (Order Handling) → конфигурация и активация сервиса → настройка ресурсов. Согласования и SLA — часть Order Handling.

### 4.2. Open API, полезные проекту

| API | Назначение | Аналог в нашем проекте |
|---|---|---|
| TMF622 Product Ordering | Коммерческий заказ клиента | Заявка |
| TMF641 Service Ordering | Технический заказ на сервис | Этапы исполнения |
| TMF645 Service Qualification | Проверка технической возможности | Этап «Проверка ТВ» |
| TMF629 Customer Management | Данные клиента | Mock CRM / справочник клиентов |
| TMF620 Product Catalog | Каталог услуг и предложений | Справочник услуг (упрощённо) |
| TMF648 Quote Management | Коммерческое предложение | Не берём (CPQ вне границ) |
| TMF681 Communication | Отправка сообщений | Уведомления |

### 4.3. Жизненный цикл заказа (TMF622)

Стандарт задаёт состояния заказа: `acknowledged` (принят), `inProgress` (в работе), `pending` (ждёт действия), `held` (приостановлен), `completed` (выполнен), `rejected` (отклонён), `cancelled` (отменён), `failed` (ошибка), `partial` (выполнен частично), а также `assessingCancellation` / `pendingCancellation` (обработка отмены).

**Вывод:** полный набор избыточен для прототипа, но он показывает, какие **классы состояний** должны быть: приём, работа, ожидание, приостановка, успешное завершение, отказ, отмена. Это вход для [статусной модели](../system/status-model.md).

## 5. Аналоги

### 5.1. Netcracker

**Что это:** вендор OSS/BSS полного цикла (дочерняя компания NEC). Сильная позиция в B2B у крупных операторов, например у Vivo (Telefónica, Бразилия) — проект по Service Order Management для B2B.

**Ключевые возможности по нашей теме:**
- разделение **коммерческого заказа** (Customer Order Management) и **технического заказа** (Service Order Management);
- **каталог** продуктов и сервисов — маршрут исполнения строится из описания продукта в каталоге;
- **оркестрация**: заказ раскладывается на задачи, задачи выполняются в нужном порядке разными системами и подразделениями;
- проверка технической возможности до оформления заказа;
- контроль сроков задач и предупреждение о рисках срыва (jeopardy management).

**Берём:** разделение «заявка ↔ этапы»; маршрут как набор этапов, который строится автоматически по параметрам; проверку ТВ как отдельный ранний этап.
**Не берём:** каталог-ориентированную декомпозицию в полном виде, инвентаризацию ресурсов, оркестрацию сетевого оборудования.

### 5.2. Amdocs

**Что это:** крупнейший вендор BSS. Для B2B — **Amdocs CPQ Pro** и Customer Engagement Platform (совместно с Microsoft Dynamics 365).

**Ключевые возможности по нашей теме:**
- конфигурация и расчёт сложных B2B-предложений по каталогу (CPQ);
- **проверка обслуживаемости** (serviceability) и совместимости ещё на этапе оформления;
- поддержка всех сегментов — от МСБ до крупного бизнеса и госсектора;
- **единая точка приёма заказов** из всех каналов — снижает долю «зависших» заказов (order fallout);
- поддержка изменений, переносов и продлений (moves, changes, renewals).

**Берём:** валидацию данных заявки **до** запуска маршрута (данные клиента, адрес, обязательные поля) — чтобы не запускать согласования по заведомо некорректной заявке; сегментацию клиентов как параметр маршрута.
**Не берём:** CPQ и ценообразование, изменения/переносы/продления (вне границ — только новое подключение), AI-агентов (явно исключены в scope).

### 5.3. CSG

**Что это:** вендор биллинга и Quote-to-Cash. Для B2B — **CSG Quote & Order**: CPQ и управление заказами, позиционируется как CPQ, созданный специально для B2B-телекома.

**Ключевые возможности по нашей теме:**
- путь «расчёт → заказ → исполнение» без повторного ввода данных;
- поддержка стандартов **TM Forum Open API**;
- работа из CRM продавца и самообслуживание клиента;
- в Gartner Magic Quadrant по CPQ (2023) — нишевый игрок.

**Берём:** ориентацию API-контрактов на TM Forum (имена сущностей и статусов — ближе к стандарту); принцип «данные вводятся один раз» — заявка подтягивает данные клиента из CRM, а не набирает их заново.
**Не берём:** CPQ, клиентское самообслуживание (портал клиента вне границ).

### 5.4. Salesforce Communications Cloud

**Что это:** отраслевое решение Salesforce для операторов связи (на базе платформы Salesforce и бывшего Vlocity).

**Ключевые возможности по нашей теме:**
- **Enterprise Sales Management** — крупные B2B-сделки, много адресов у одного клиента, цена по каждому адресу, сложные пакеты;
- **Industries Order Management** — декомпозиция заказа, **план оркестрации**: система сама формирует, упорядочивает и отслеживает задачи, взаимодействует с биллингом, выездными службами, инвентарём;
- проверка возможности назначить дату подключения при оформлении сделки;
- на уровне платформы — **процессы согласования (Approval Processes)** с правилами входа, последовательными шагами и решениями «одобрить / отклонить»;
- контроль сроков обращений через **Entitlements и Milestones** (целевое время, предупреждение, нарушение).

**Берём:**
- **механику согласований**: условие входа → шаги → решение (согласовано / возвращено на доработку / отклонено) с обязательным комментарием при отказе;
- **SLA по этапам** в духе Milestones: у этапа есть нормативный срок, порог предупреждения и факт нарушения;
- **план этапов**, который виден в карточке заявки целиком — какие этапы пройдены, какой текущий, какие впереди.

**Не берём:** CRM-часть (сделки, воронка), мультиадресные заказы с ценой по адресам, low-code конструктор процессов.

## 6. Сравнение аналогов

Оценка: ● — сильная сторона решения, ◐ — есть, ○ — не фокус решения / нет данных.

| Возможность | Netcracker | Amdocs | CSG | Salesforce | **B2B-Order-Flow** |
|---|---|---|---|---|---|
| Каталог продуктов | ● | ● | ● | ● | Упрощённый справочник услуг |
| CPQ, ценообразование | ◐ | ● | ● | ● | Нет |
| Проверка ТВ | ● | ● | ◐ | ◐ | **Да**, отдельный этап |
| Динамический маршрут | ● | ◐ | ◐ | ● | **Да**, по правилам |
| Межфункциональные согласования | ◐ | ◐ | ◐ | ● | **Да**, 4 вида |
| SLA этапов и предупреждения | ● | ◐ | ○ | ● | **Да** |
| Уведомления участников | ◐ | ◐ | ◐ | ● | **Да** |
| История и аудит | ● | ● | ◐ | ● | **Да** |
| TM Forum Open API | ● | ● | ● | ◐ | Ориентир для контрактов |
| Самообслуживание клиента | ◐ | ● | ● | ● | Нет (вне границ) |

**Наблюдение:** промышленные решения сильны в каталоге и CPQ (продажная часть), а **межфункциональные согласования** у них обычно реализуются настройкой платформы, а не «из коробки». Для нашего прототипа именно маршрутизация и согласования — центральная ценность, поэтому их стоит сделать наглядными и хорошо проработанными.

## 8. Что не берём и почему

| Что | Почему |
|---|---|
| CPQ, расчёт цены, коммерческие предложения | Продажная часть до заявки, вне границ процесса |
| Полноценный каталог продуктов | Одна базовая услуга (ШПД) — хватит справочника |
| Биллинг, выставление счетов | Вне границ (scope), биллинг — только mock для проверки баланса |
| Инвентаризация и активация сетевых ресурсов | Нет реальной сети — активация фиксируется действием исполнителя |
| Портал клиента, самообслуживание | Вне границ (scope) |
| Изменения, переносы, продления, расторжение | Вне границ — только новое подключение |
| Мультиадресные заказы | Усложняет модель; заявка = один адрес. Количество адресов клиента — максимум параметр «крупности» |
| AI-агенты, генерация предложений | Явно исключены в scope |
| Low-code конструктор процессов | Правила маршрутизации задаются в коде / конфигурации |

| Госзаказчик (44-ФЗ / 223-ФЗ) | CRM / справочник | → юрист |
| Задолженность клиента | Mock биллинг | Есть долг → финансы |
| Сумма контракта / затраты на стройку выше порога | Заявка / этап ТВ | → управленческое согласование |
| Стратегический клиент (сегмент) | Mock CRM | → управленческое согласование |

Пороговые значения (сумма, затраты) — определить вместе с системным аналитиком.

### 9.3. Сценарии → [scenarios.md](scenarios.md)

| Сценарий | Пример | Маршрут (упрощённо) |
|---|---|---|
| Стандартная заявка | МСБ, 100 Мбит/с, типовой тариф, ТВ есть | ТВ → монтаж → активация → закрытие |
| С дополнительными согласованиями | 500 Мбит/с, скидка, договор клиента | ТВ → юрист + финансы → монтаж → активация → закрытие |
| Крупная / нестандартная | Нужна стройка, сумма выше порога, стратегический клиент | ТВ → закупки + финансы + юрист → руководство → стройка/монтаж → активация → закрытие |

Плюс негативные ветки: ТВ нет → отказ; согласование отклонено → отказ; возврат на доработку → менеджер исправляет → повторное согласование.

### 9.4. SLA → [sla.md](../system/sla.md)

- SLA задаётся **на этап**, а не только на заявку целиком.
- У этапа: норматив, порог предупреждения (например, осталось 25% времени), факт нарушения.
- SLA приостанавливается, пока ждём клиента (например, при возврате на доработку из-за данных клиента).
- При нарушении — эскалация координатору / руководителю.
- Нормативы считаются в рабочих часах.

### 9.5. Уведомления → [notifications.md](../system/notifications.md)

События: заявка создана; этап назначен исполнителю; статус изменён; заявка возвращена на доработку; согласование отклонено; приближение SLA; нарушение SLA; заявка закрыта.
