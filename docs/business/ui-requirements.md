# Требования к интерфейсу

## 1. Назначение

Документ описывает веб-интерфейс прототипа B2B-Order-Flow: какие экраны есть у каждой роли, какие на них поля и кнопки, когда кнопка видна, какие состояния показывает экран и какие тексты получает пользователь при ошибках.

Документ — вход для:
- реализации `ui/` (React, Vite, TanStack Query) — экраны, маршруты, слой запросов, тексты;
- внешнего контракта шлюза `bff-gateway/openapi/external-api.yaml` — каких полей и операций ждёт интерфейс;
- сквозных тестов Playwright — порядок экранов в сценариях и `data-testid` (раздел 11);
- демонстрации на защите — [scenarios.md](scenarios.md), раздел 10.

Основа:
- [roles.md](roles.md) — роли и матрица прав: видимость кнопок определяется ей;
- [scenarios.md](scenarios.md) — SC-00 и SC-01 задают порядок экранов;
- [business-process.md](business-process.md) — фазы и названия статусов для пользователя;
- [status-model.md](../system/status-model.md) — коды статусов, этапов и переходов;
- [api-contract.md](../system/api-contract.md) — операции, формат ошибок, пагинация, версии;
- [sla.md](../system/sla.md), раздел 10 — индикатор SLA;
- [nfr.md](../system/nfr.md), разделы 7 и 10 — лимиты, браузеры, язык, время;
- внутренний контракт ядра недели 1 `core-api.yaml` (PR ядра) — поля форм и представлений.

Объём по неделям ([dev-plan.md](../dev-plan.md)): экраны недель 1 и 2 (SC-00, SC-01) описаны полностью; экраны недели 3 (согласования, доработка, отмена) — перечнем в разделе 9, детализация до 22.11.

## 2. Принципы

1. **Одно приложение, два контура.** Клиентский контур (представители компании) и операторский (сотрудники оператора, администратор) — одно React-приложение. Что показать, решают активная роль и права из ответа ядра.
2. **Интерфейс не решает за ядро.** Видимость кнопок следует матрице [roles.md](roles.md), но итоговую проверку прав, статуса и версии делает ядро. Если ядро отказало, интерфейс показывает понятный текст (раздел 10) и перезапрашивает данные.
3. **Данные — только с сервера.** Состояние заявок не хранится в интерфейсе дольше, чем нужно для показа: TanStack Query кэширует ответы и перезапрашивает их после каждого действия. После любого изменяющего действия перезапрашиваются карточка, список и уведомления.
4. **Каждое изменяющее действие передаёт `version`**, которую пользователь видел ([api-contract.md](../system/api-contract.md), 5.2). Создающие запросы передают `Idempotency-Key` (5.1).
5. **Автоповторов записи нет.** Повторяются только чтения. При сбое связи на записи интерфейс просит обновить страницу и посмотреть актуальное состояние.
6. **Решение «против» — с причиной.** Отклонение компании, отказ по ТВ, возврат, отклонение, отмена открывают окно с обязательным полем причины.
7. **Клиент видит только своё.** Клиенту не показываются исполнители, внутренние комментарии и SLA ([roles.md](roles.md), 5.1). Ядро не отдаёт эти поля, интерфейс дополнительно не рисует для клиента соответствующие блоки.
8. **Все тексты интерфейса — в одном месте** (файл словаря в `ui/`), а не в разметке экранов ([nfr.md](../system/nfr.md), раздел 10).
9. **Десктоп.** Последние Chrome, Firefox, Edge; от 1366×768; мобильная вёрстка не требуется. Язык — русский. Даты в API — UTC, на экране — локальное время пользователя.

## 3. Каркас приложения

### 3.1. Шапка

| Элемент | Кто видит | Поведение |
|---|---|---|
| Название системы | Все | Ссылка на главный экран активной роли |
| Компания | Представители компании | Название и статус компании. Пока компания «На подтверждении» — плашка «Компания ожидает подтверждения» (EC-14) |
| Переключатель ролей | Пользователь с двумя и более ролями | Список ролей пользователя (раздел 3.3). Выбор роли меняет меню и главный экран |
| Уведомления | Все, кроме гостя без компании | Колокольчик со счётчиком непрочитанных, по клику — список (экран UI-14) |
| Пользователь | Все | ФИО, логин, кнопка «Выйти» |

| Активная роль | Пункты меню | Главный экран |
|---|---|---|
| Гость (нет компании и ролей оператора) | Регистрация компании | UI-03 «Регистрация компании» или статус поданной компании |
| `CLIENT_OWNER`, `CLIENT_REQUESTER` | Заявки, Новая заявка, Моя компания | UI-05 «Заявки» |
| `CLIENT_ADMIN` | Моя компания | UI-04 «Моя компания» |
| `SALES_MANAGER` | Мои заявки, Очередь менеджеров | UI-05 «Заявки» (свои) |
| `TECH_SPECIALIST`, `ENGINEER` | Мои задачи, Очередь роли, Заявки | UI-12 «Мои задачи» |
| `LAWYER`, `FINANCE_CONTROLLER`, `PROCUREMENT_SPECIALIST` | Мои задачи, Очередь роли, Заявки | UI-12 «Мои задачи» (неделя 3) |
| `B2B_HEAD` | Заявки, Мои задачи | UI-05 «Заявки» (все) |

### 3.3. Переключатель ролей

- Список строится из `companyRoles` и `operatorRoles` ответа `GET /me`.
- Подписи ролей:

| Код | Подпись |
|---|---|
| `CLIENT_OWNER` | Владелец компании |
| `CLIENT_ADMIN` | Администратор компании |
| `CLIENT_REQUESTER` | Инициатор заявок |
| `SALES_MANAGER` | Менеджер по продажам |
| `TECH_SPECIALIST` | Технический специалист |
| `LAWYER` | Юрист |
| `FINANCE_CONTROLLER` | Финансовый контролёр |
| `PROCUREMENT_SPECIALIST` | Специалист по закупкам |
| `B2B_HEAD` | Руководитель B2B |
| `ENGINEER` | Инженер-монтажник |
| `COORDINATOR` | Координатор заявок |
| `ADMIN` | Системный администратор |

- Выбранная роль уходит в заголовке `X-Active-Role` с каждым запросом ([api-contract.md](../system/api-contract.md), 4.2).
- Роль по умолчанию: единственная роль; если ролей несколько — последняя выбранная в этой вкладке, иначе первая по порядку таблицы.
- При смене роли кэш запросов сбрасывается, открывается главный экран новой роли.
- Если ядро ответило `ACCESS_DENIED` на активную роль (роль отозвали), интерфейс перечитывает `GET /me` и предлагает выбрать роль заново.

### 3.5. Сессия

- После входа токен хранится в `sessionStorage` вкладки: обновление страницы не разлогинивает, закрытие вкладки завершает сессию. Токен не пишется в лог и в адресную строку.
- Срок токена — 8 часов, обновления нет ([api-contract.md](../system/api-contract.md), 4.1). Любой ответ `401` на защищённый запрос очищает сессию и открывает `/login` с текстом «Сессия истекла, войдите снова». Введённые в форму данные при этом теряются — это осознанное упрощение MVP.
- «Выйти» очищает сессию и кэш и открывает `/login`.

## 4. Общие компоненты и состояния

### 4.1. Состояния экрана

| Состояние | Что показывать |
|---|---|
| Загрузка | Скелетон таблицы или карточки; кнопки действий недоступны |
| Пусто | Текст по экрану (например, «Заявок пока нет») и, если есть, главная кнопка («Создать заявку») |
| Ошибка загрузки | Блок с текстом из раздела 10 и кнопкой «Обновить» |
| Сбой связи с сервером | Плашка вверху экрана: «Сервис временно недоступен. Нажмите «Обновить» через несколько секунд» и кнопка «Обновить» |
| Нет доступа или объекта | Страница «Заявка не найдена или у вас нет к ней доступа» и ссылка на список (EC-16) |
| Действие выполняется | Кнопка действия с индикатором, повторное нажатие заблокировано |
| Действие выполнено | Короткое сообщение (тост) и обновлённые данные экрана |

### 4.2. Формы

- Обязательные поля отмечены звёздочкой. Интерфейс проверяет обязательность, длину и формат до отправки; правила — из раздела 6 и таблицы правил формата полей ([api-contract.md](../system/api-contract.md), готовит Дима).
- Ошибки ядра `422 VALIDATION_FAILED` раскладываются по полям из `violations` (`field` → поле формы, `message` → текст под полем). Нераспознанные поля — общим текстом над формой.
- При уходе со страницы с несохранёнными изменениями — окно «Есть несохранённые изменения. Уйти без сохранения?».
- `Idempotency-Key` генерируется один раз на попытку создания (при открытии формы) и переиспользуется при повторной отправке той же формы; после успеха — новый.

### 4.3. Окно подтверждения

Для необратимых и «отрицательных» действий: заголовок, что произойдёт, поле причины или комментария (если нужно), кнопки «Подтвердить» и «Отмена». Кнопка «Подтвердить» недоступна, пока обязательное поле пустое.

### 4.4. Таблицы и пагинация

- Списки страничные: `page`, `size` (20 по умолчанию, выбор 20 / 50 / 100), `sort` ([api-contract.md](../system/api-contract.md), 2.1). Внизу — «Показано 1–20 из 137» и переключатель страниц.
- Сортировка — по клику на заголовок колонки, только по полям, которые разрешает ядро.
- Состояние фильтров, страницы и сортировки хранится в адресной строке, чтобы ссылку можно было отправить и обновить страницу без потери.
- Строка таблицы — ссылка на карточку заявки.

### 4.5. Форматы

| Что | Формат на экране |
|---|---|
| Дата и время | `11.11.2026 14:05`, локальное время |
| Дата | `11.11.2026` |
| Деньги | `1 200 000,00 ₽` (в API — строка `"1200000.00"`) |
| Скорость | `100 Мбит/с` |
| Номер заявки | `REQ-2026-000123` — показывается везде вместо идентификатора |
| Длительность SLA | `2 р.д. 3 ч` для рабочего времени, `5 мин` в профиле `DEMO`; календарное — `3 дн. 4 ч` |

## 5. Справочник отображения

### 5.1. Статусы заявки

Названия — по [status-model.md](../system/status-model.md), раздел 3. Подсказка показывается под статусом в карточке; для клиента — своя формулировка.

| Код | Название | Цвет бейджа | Подсказка клиенту | Подсказка оператору |
|---|---|---|---|---|
| `DRAFT` | Черновик | Серый | Заполните заявку и отправьте оператору | — |
| `DATA_CHECK` | Проверка данных | Синий | Проверяем данные компании и назначаем менеджера | Проверка во внешних системах; если менеджер не определён — заявка в очереди менеджеров |
| `WITH_MANAGER` | У менеджера | Синий | Менеджер готовит условия подключения | Зафиксируйте коммерческие условия и отправьте в работу |
| `TECH_CHECK` | Проверка ТВ | Синий | Проверяем техническую возможность подключения | Этап «Проверка ТВ» в очереди технических специалистов |
| `IN_APPROVAL` | На согласовании | Фиолетовый | Условия согласуются внутри оператора | Идут согласования маршрута |
| `REWORK` | На доработке | Оранжевый | Менеджер уточняет данные заявки | Заявка возвращена менеджеру |
| `CONTRACT_SIGNING` | Подписание договора | Жёлтый | Ознакомьтесь с условиями и подпишите договор | Ожидается акцепт оферты или подписанный договор |
| `IN_EXECUTION` | В исполнении | Синий | Идут работы по подключению | Стройка, монтаж, активация |
| `ACTIVATED` | Услуга активирована | Зелёный | Услуга работает; подпишите акт или сообщите о проблеме | Ожидается акт или истечение срока приёмки |
| `CANCEL_REQUESTED` | Запрос на отмену | Оранжевый | Рассматривается запрос на отмену | Работы и SLA приостановлены |
| `CLOSED` | Закрыта | Зелёный, контурный | Услуга подключена, заявка закрыта | — |
| `REJECTED` | Отклонена | Красный | Подключение невозможно; причина — в истории | — |
| `CANCELLED` | Отменена | Тёмно-серый | Заявка отменена | — |

Если у заявки `integrationError = true`, рядом со статусом оператору показывается метка «Ошибка проверки данных», клиенту — подсказка «Данные уточняются, это может занять больше времени».

### 5.2. Прочие значения

| Поле | Код → подпись |
|---|---|
| Статус компании | `PENDING` — На подтверждении; `ACTIVE` — Активна; `REJECTED` — Отклонена |
| Тип договора | `OFFER` — Оферта; `STANDARD` — Типовой договор; `CLIENT_FORM` — Договор по форме клиента |
| Тип тарифа | `STANDARD` — Типовой тариф; `INDIVIDUAL` — Индивидуальная цена |
| Сегмент | `SMB` — МСБ; `LARGE` — Крупный; `STRATEGIC` — Стратегический |
| Результат ТВ | `AVAILABLE` — Есть; `WITH_CONSTRUCTION` — Есть со стройкой; `NONE` — Нет |
| Класс заявки | `STANDARD` — Стандартная; `EXTENDED` — С согласованиями; `LARGE` — Крупная |
| Уровень обязательств | 0 — До договора; 1 — Договор заключён; 2 — Работы начаты; 3 — Услуга активирована |
| Статус этапа | `QUEUED` — В очереди; `IN_PROGRESS` — В работе; `DONE` — Выполнен; `RETURNED` — Возвращён; `REJECTED` — Отклонён; `SUPERSEDED` — Заменён; `CANCELLED` — Отменён |

Типы этапов — названия из [status-model.md](../system/status-model.md), раздел 4.1 («Проверка ТВ», «Подписание договора», «Монтаж и настройка» и т. д.).

### 5.3. Индикатор SLA

По [sla.md](../system/sla.md), раздел 10. Показывается только оператору.

| Цвет | Условие | Подпись |
|---|---|---|
| Зелёный | Израсходовано меньше 75% норматива | «Осталось 1 р.д. 4 ч» |
| Жёлтый | От 75% до 100% | «Осталось 2 ч» |
| Красный | Норматив нарушен | «Просрочено на 3 ч» |
| Серый | Таймер на паузе | «На паузе: <причина>» |

Рядом с индикатором — два времени: «по SLA» (без пауз) и «календарное». Очереди и «Мои задачи» сортируются по остатку времени.

## 6. Экраны недели 1

### 6.1. UI-01. Вход

**Кто:** все. **Операция:** `POST /auth/login`.

| Поле | Обязательно | Правило |
|---|---|---|
| Логин | Да | — |
| Пароль | Да | Скрыт, кнопка «Показать» |

- Кнопки: «Войти»; ссылка «Зарегистрироваться» → UI-02.
- После входа: `GET /me`, выбор роли по разделу 3.3, переход на главный экран роли.
- Ошибки: `INVALID_CREDENTIALS` — «Неверный логин или пароль»; `UNAUTHORIZED` (учётная запись деактивирована) — «Вход недоступен. Обратитесь к администратору»; `429` — «Слишком много попыток входа. Подождите минуту».

### 6.2. UI-02. Регистрация пользователя

**Кто:** гость. **Операция:** `POST /auth/register`.

| Поле | Обязательно | Правило |
|---|---|---|
| Логин | Да | 3–100 символов |
| Пароль | Да | 8–100 символов |
| Повтор пароля | Да | Совпадает с паролем (проверка только в интерфейсе) |
| ФИО | Да | До 255 символов |
| Email | Да | Формат email, до 255 символов |

- После успеха — автоматический вход и экран UI-03 с подсказкой: «Зарегистрируйте компанию или сообщите свой логин владельцу компании, чтобы он добавил вас».
- Логин показывается на UI-03 с кнопкой «Скопировать» — его сотрудник передаёт владельцу компании (SC-00, шаг 4).
- Ошибки: занятый логин — текст из ответа ядра под полем «Логин».

### 6.3. UI-03. Регистрация компании

**Кто:** пользователь без компании. **Операция:** `POST /companies` с `Idempotency-Key`.

| Поле | Обязательно | Правило |
|---|---|---|
| Название | Да | До 500 символов |
| ИНН | Да | 10 цифр (организация) или 12 (ИП); проверка контрольной суммы |
| КПП | Нет | 9 цифр |
| ОГРН | Нет | 13 цифр (организация) или 15 (ИП) |
| Юридический адрес | Да | До 500 символов |

- После отправки компания «На подтверждении». Экран показывает статус: «Компания отправлена на подтверждение. Создавать заявки и добавлять сотрудников можно после подтверждения администратором» (EC-14).

### 6.6. UI-06. Подтверждение компаний

### 6.7. UI-07. Форма заявки

**Кто:** `CLIENT_OWNER`, `CLIENT_REQUESTER` активной компании. **Операции:** `POST /requests` (создание черновика, `Idempotency-Key`), `PATCH /requests/{id}` (правка, `version`), `POST /requests/{id}/submit` (отправка, `version`), `DELETE /requests/{id}?version=N` (удаление черновика).

| Поле | При сохранении черновика | При отправке | Правило |
|---|---|---|---|
| Адрес подключения | Нет | Да | До 500 символов |
| Скорость, Мбит/с | Нет | Да | Целое 1–100 000 |
| Желаемая дата подключения | Нет | Да | Дата, не раньше сегодняшней |
| Контактное лицо | Нет | Да | До 255 символов; по умолчанию — ФИО автора заявки |
| Телефон контактного лица | Нет | Да | До 32 символов, формат — по таблице правил формата полей |
| Пожелания по договору | Нет | Нет | Оферта / типовой договор / договор по форме клиента |
| Комментарий | Нет | Нет | До 4 000 символов, счётчик символов; подсказка: «Например, запрос индивидуальной цены» |

- Черновик сохраняется только кнопкой «Сохранить черновик», без автосохранения. Обязательность бизнес-полей ядро проверяет при отправке (T01), поэтому черновик можно сохранить частично заполненным.
- Кнопки: «Сохранить черновик», «Отправить оператору», «Удалить черновик» (только у сохранённого черновика), «Отмена».
- «Отправить оператору» сначала сохраняет несохранённые изменения, затем отправляет. После успеха — переход в карточку заявки с тостом «Заявка отправлена».
- «Удалить черновик» — окно «Удалить черновик? Действие нельзя отменить». После удаления — список заявок.
- **Варианты услуги.** В модели у заявки может быть несколько вариантов (`service_offer`), но в MVP вариант один и выбирается автоматически ([domain-model.md](../system/domain-model.md), 4.2). Форма недели 1 не показывает варианты; экран выбора варианта появится после описания процесса вариантов (до 22.11).
- **Предупреждения в ответе** (не ошибки, `warnings`):
  - `DUPLICATE_REQUEST_WARNING` — плашка «По этому адресу у компании уже есть незакрытая заявка. Если это ошибка, координатор отменит дубль» (EC-12);
  - `EXTERNAL_SYSTEM_UNAVAILABLE` после отправки — плашка в карточке «Данные уточняются, это может занять больше времени» (EC-10).
- Ошибки: `VALIDATION_FAILED` — подсветка полей из `violations` и текст «Заявка заполнена не полностью»; `COMPANY_NOT_CONFIRMED` — «Компания ещё не подтверждена, отправить заявку нельзя»; `VERSION_CONFLICT` — раздел 10.

## 10. Тексты ошибок

Интерфейс ветвится по `code` из ответа ([api-contract.md](../system/api-contract.md), 3.1), а не по тексту. Для кодов, которых нет в таблице, показывается `title` из ответа, а если его нет — общий текст «Не удалось выполнить действие».

| Код | HTTP | Текст пользователю | Поведение |
|---|---|---|---|
| `VALIDATION_FAILED` | 422 | «Проверьте выделенные поля» | Ошибки по полям из `violations` |
| `MALFORMED_REQUEST` | 400 | «Не удалось обработать запрос. Код для обращения: <correlationId>» | Ошибка интерфейса, повтор не поможет |
| `INVALID_CREDENTIALS` | 401 | «Неверный логин или пароль» | Только на входе |
| `UNAUTHORIZED` | 401 | «Сессия истекла, войдите снова» | Очистить сессию, открыть `/login` |
| `ACCESS_DENIED` | 403 | «Недостаточно прав для этого действия» | Перечитать `GET /me`, обновить экран |
| `MEMBERSHIP_REVOKED` | 403 | «Вы больше не состоите в компании. Обратитесь к её владельцу» | Перечитать `GET /me`, открыть главный экран (EC-17) |
| `NOT_FOUND` | 404 | «Заявка не найдена или у вас нет к ней доступа» | Страница-заглушка со ссылкой на список (EC-16) |
| `ACTIVE_ROLE_REQUIRED` | 422 | «Выберите роль» | Открыть переключатель ролей |
| `ACTIVE_COMPANY_REQUIRED` | 422 | «Не удалось определить компанию. Обратитесь к администратору» | В MVP у пользователя одна компания |
| `COMPANY_NOT_CONFIRMED` | 422 | «Компания ещё не подтверждена администратором» | EC-14 |
| `COMPANY_INN_EXISTS` | 409 | «Компания с таким ИНН уже зарегистрирована. Попросите её владельца добавить вас по логину» | EC-15 |
| `COMPANY_INN_NOT_FOUND` | 422 | Регистрация: «ИНН не найден в справочнике клиентов. Проверьте ИНН». Подтверждение: «ИНН не найден в справочнике клиентов. Отклоните компанию с этой причиной» | SC-00 A1 |
| `EXTERNAL_SYSTEM_UNAVAILABLE` | 503 | «Справочник клиентов временно недоступен. Повторите через минуту» | Кнопка «Повторить» |
| `EXTERNAL_SYSTEM_UNAVAILABLE` | 200 | «Данные уточняются, это может занять больше времени» | Предупреждение, не ошибка (EC-10) |
| `DUPLICATE_REQUEST_WARNING` | 200 | «По этому адресу у компании уже есть незакрытая заявка. Если это ошибка, координатор отменит дубль» | Предупреждение, не ошибка (EC-12) |
| `ILLEGAL_TRANSITION` | 409 | «Действие уже недоступно: статус заявки изменился» | Перечитать заявку |
| `VERSION_CONFLICT` | 409 | «Заявку изменили, пока вы её смотрели. Данные обновлены — проверьте и повторите действие» | Перечитать заявку, введённые в окно данные сохранить |
| `CONFLICT` | 409 | «Действие уже выполняется. Подождите и обновите страницу» | — |
| `IDEMPOTENCY_KEY_REUSED` | 409 | «Не удалось выполнить действие. Обновите страницу и повторите» | Сгенерировать новый ключ |
| `STAGE_ALREADY_DECIDED` | 409 | «Этап уже закрыт другим пользователем» | Перечитать заявку |
| `STAGE_NOT_IN_YOUR_QUEUE` | 403 | «Этот этап не в очереди вашей активной роли» | Перечитать очередь |
| `SELF_APPROVAL_FORBIDDEN` | 403 | «Нельзя согласовать заявку, в которой вы менеджер» | Неделя 3 (EC-18) |
| `CANCEL_AFTER_ACTIVATION` | 409 | «После активации услуги отменить заявку нельзя» | Неделя 3 (EC-09) |
| `CORE_UNAVAILABLE` | 503 | «Сервис временно недоступен. Нажмите «Обновить» через несколько секунд» | Плашка и кнопка «Обновить» |

| Нет ответа (сеть) | — | Как `CORE_UNAVAILABLE` | — |

### 11.3. Метки для автотестов

Стабильные `data-testid` ставятся на элементы, по которым ходят сценарии Playwright (П2 недели 2, по договорённости с QA):
- формат — `<экран>-<элемент>` в нижнем регистре через дефис: `login-submit`, `request-form-address`, `request-card-status`;
- кнопки действий в карточке — `action-<операция>`: `action-submit`, `action-claim`, `action-accept-offer`, `action-activate`;
- строки таблиц — `<экран>-row-<номер заявки>`.
