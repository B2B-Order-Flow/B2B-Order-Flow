# Роли участников процесса

## 1. Назначение

Документ определяет:
- **кто** участвует в обработке заявки на подключение B2B-услуги;
- **как** компании-клиенты и их сотрудники попадают на платформу;
- **за что** отвечает каждый участник и **какие действия** ему доступны.

Документ — вход для:
- [бизнес-процесса](business-process.md) и [сценариев](scenarios.md) — кто выполняет каждый шаг;
- [доменной модели](../system/domain-model.md) — пользователи, компании, роли, участники заявки;
- [статусной модели](../system/status-model.md) — кто инициирует переходы;
- [правил маршрутизации](../system/routing-rules.md) — на какую роль назначается этап;
- [уведомлений](../system/notifications.md) — кому что приходит;
- [UI-требований](ui-requirements.md) — что видит и что может нажать каждая роль;
- ролевой модели доступа в API (Spring Security + JWT).

Основа — исследование [research-b2b.md](research-b2b.md), раздел 9.1, и ответы тимлида на открытые вопросы (раздел 11).

## 2. Принципы

1. **Роль ≠ должность.** Роль — набор обязанностей и прав в системе.
2. **Два вида ролей.**
   - **Роли в компании** — что представитель компании-клиента может делать внутри своей компании: добавлять сотрудников, подавать заявки.
   - **Роли в процессе** — что сотрудник оператора делает с заявкой: проверяет ТВ, согласует, монтирует.

   Это разные наборы ролей, они не пересекаются.
3. **У пользователя может быть несколько ролей.** Активная роль выбирается **переключателем ролей** в интерфейсе; для каждой роли — свой интерфейс.
4. **Клиент работает в системе сам.** Компания-клиент регистрируется на платформе, её представители сами подают заявки и следят за ними. Сотрудники оператора обрабатывают заявки.
5. **Изоляция данных между компаниями.** Представитель видит только заявки и сотрудников своей компании.
6. **Этап назначается на роль, а не на человека.** Этап попадает в **очередь роли**; любой пользователь с этой ролью берёт его в работу, координатор может назначить исполнителя вручную.
7. **Разделение обязанностей.** Согласующий решает только по своему виду согласования. Менеджер — владелец заявки не может её согласовать, даже если у него есть роль согласующего.
8. **Решение «против» всегда с причиной.** Возврат на доработку, отклонение, отмена, отказ в регистрации компании — с обязательным комментарием.
9. **Минимум прав.** Роль видит и делает только то, что нужно для её работы. Системный администратор не видит заявки и бизнес-данные клиентов.

## 3. Участники

### 3.1. Стороны

| Сторона | Как появляется в системе |
|---|---|
| **Оператор связи** | Служебная организация, создаётся при развёртывании. Сотрудники оператора не регистрируются публично — создаются через сид (MVP) |
| **Компания-клиент** (юрлицо / ИП) | Регистрируется на платформе своим представителем и подтверждается системным администратором |
| **Подрядчик** | Не работает в системе. Его работу (стройку) фиксирует инженер |
| **Внешние системы** (mock CRM, mock биллинг, mock справочник клиентов) | Источники данных о клиенте: реквизиты, сегмент, закреплённый менеджер, признак госзаказчика, задолженность |

### 3.2. Системный актор

| Участник | Что делает автоматически |
|---|---|
| **Система** | Проверяет данные заявки и клиента во внешних системах; назначает менеджера на заявку; строит маршрут по правилам; назначает этапы в очереди ролей; переводит заявку по статусам; запускает, приостанавливает и контролирует SLA; рассылает уведомления; ведёт историю |

### 3.3. Роли в компании-клиенте

| Код роли | Роль | Коротко |
|---|---|---|
| `CLIENT_OWNER` | Владелец компании | Первый представитель, зарегистрировавший компанию. Все права в компании |
| `CLIENT_ADMIN` | Администратор компании | Добавляет сотрудников, назначает и меняет их роли |
| `CLIENT_REQUESTER` | Инициатор заявок | Создаёт заявки от имени компании, следит за ними, отменяет |

### 3.4. Роли в процессе (сотрудники оператора)

| Код роли | Роль | Коротко |
|---|---|---|
| `SALES_MANAGER` | Менеджер по продажам | Владелец заявки со стороны оператора, связь с клиентом |
| `TECH_SPECIALIST` | Технический специалист | Проверка технической возможности (ТВ) |
| `LAWYER` | Юрист | Юридическое согласование |
| `FINANCE_CONTROLLER` | Финансовый контролёр | Финансовое согласование |
| `PROCUREMENT_SPECIALIST` | Специалист по закупкам | Закупочное согласование |
| `B2B_HEAD` | Руководитель B2B-направления | Управленческое согласование, эскалации |
| `ENGINEER` | Инженер-монтажник | Стройка, монтаж, настройка, активация |
| `COORDINATOR` | Координатор заявок | Контроль очередей и SLA, переназначения |

### 3.5. Системная роль

| Код роли | Роль | Коротко |
|---|---|---|
| `ADMIN` | Системный администратор | Подтверждение компаний, справочники и пороги. Не видит заявки |

Коды — предложение для API и ролевой модели; финально согласовать с Кириллом и Денисом.

## 4. Регистрация и доступ

### 4.1. Вход

- Аутентификация по логину и паролю, сессия — JWT (Spring Security).
- Один аккаунт пользователя на всю платформу.
- Публичная регистрация доступна всем; права появляются только после привязки к компании.

### 4.2. Регистрация компании-клиента

1. Представитель регистрируется на платформе (ФИО, email, пароль).
2. Создаёт компанию: название, ИНН, КПП, ОГРН, юридический адрес. Компания получает статус **«На подтверждении»**.
3. Системный администратор проверяет данные (сверка ИНН со справочником клиентов) и **подтверждает** компанию или **отклоняет** с причиной.
4. После подтверждения компания **«Активна»**, представитель получает роль `CLIENT_OWNER`.

Пока компания не подтверждена, её представители не могут подавать заявки и добавлять сотрудников.

**Статусы компании:** На подтверждении → Активна / Отклонена.

### 4.3. Добавление сотрудников компании

1. Сотрудник сам регистрируется на платформе и сообщает свой логин.
2. Владелец или администратор компании добавляет его в компанию по логину и отмечает роли галочками.
3. Сотрудник видит компанию и действует в рамках назначенных ролей.

**Правила:**
- добавлять сотрудников и менять роли могут только `CLIENT_OWNER` и `CLIENT_ADMIN`;
- назначать можно только роли не выше своей: администратор не может назначить владельца;
- сотрудник, удалённый из компании, теряет доступ к её данным; его действия остаются в истории.

### 4.4. Сотрудники оператора

- В MVP создаются через сид с ролями процесса.
- У одного сотрудника может быть несколько ролей (например, технический специалист и инженер).

### 4.5. Переключатель ролей

Если у пользователя несколько ролей, в интерфейсе есть переключатель. От выбранной роли зависят меню, главный экран, очередь задач и доступные действия.

## 5. Описание ролей

### 5.1. Представители компании-клиента

**Владелец компании — `CLIENT_OWNER`**
- регистрирует компанию и проходит подтверждение;
- добавляет сотрудников, назначает и меняет роли, удаляет сотрудников;
- имеет все права инициатора заявок;
- видит всех участников и все заявки компании.

**Администратор компании — `CLIENT_ADMIN`**
- добавляет сотрудников, назначает роли (кроме владельца), удаляет сотрудников;
- видит участников компании;
- заявки подаёт, только если у него есть ещё и роль `CLIENT_REQUESTER`.

**Инициатор заявок — `CLIENT_REQUESTER`**
- создаёт заявку: адрес, скорость, желаемая дата, контактное лицо, пожелания по договору и цене;
- отправляет заявку оператору;
- видит ход заявки: статус, текущий этап, комментарии для клиента;
- отменяет заявку до активации услуги;
- создаёт новую заявку на основе отклонённой;
- видит все заявки своей компании.

**Чего не видят представители клиента:** исполнителей этапов, внутренние комментарии оператора, SLA этапов, заявки других компаний.

### 5.2. Менеджер по продажам — `SALES_MANAGER`

**Цель:** провести заявку клиента через оператора; быть единственной точкой контакта клиента с оператором.

**Зона ответственности:**
- получает заявку: если за клиентом в CRM закреплён менеджер — ему, иначе — из очереди менеджеров;
- проверяет заявку и фиксирует коммерческие условия: тариф (типовой / индивидуальный), скидка, тип договора;
- отправляет заявку в работу — система строит маршрут;
- дорабатывает заявку после возврата: уточняет у клиента, исправляет данные;
- подтверждает сдачу услуги клиенту (подписан акт) и закрывает заявку;
- отменяет заявку по просьбе клиента.

**Видит:** заявки, где он менеджер.

**Не может:** согласовывать заявки, где он менеджер; вносить результат ТВ; отмечать монтаж.

### 5.3. Технический специалист — `TECH_SPECIALIST`

**Цель:** определить, можно ли подключить клиента по адресу и какой ценой.

**Зона ответственности:**
- проверка технической возможности по адресу и скорости;
- результат ТВ: **есть** / **есть со стройкой** / **нет** (с причиной);
- при стройке — оценка затрат (CAPEX) и срока;
- запрос обследования объекта, если ТВ неочевидна.

**Видит:** очередь этапов «Проверка ТВ» и заявки, по которым вносил результат.

Результат ТВ — главный параметр маршрута (см. [research-b2b.md](research-b2b.md), п. 2.3).

### 5.4. Юрист — `LAWYER`

**Цель:** защитить оператора от юридических рисков нетипового договора.

**Зона ответственности:** нетиповой договор (форма клиента, протокол разногласий, особые условия SLA и штрафов), требования для госзаказчиков (44-ФЗ / 223-ФЗ). Решение: согласовано / возвращено на доработку / отклонено.

**Видит:** очередь юридических согласований и заявки, по которым принимал решение.

### 5.5. Финансовый контролёр — `FINANCE_CONTROLLER`

**Цель:** не допустить убыточной или рискованной сделки.

**Зона ответственности:** индивидуальная цена и скидки, окупаемость стройки (CAPEX против дохода), задолженность клиента. Решение: согласовано / возвращено на доработку / отклонено.

**Видит:** очередь финансовых согласований и заявки, по которым принимал решение.

### 5.6. Специалист по закупкам — `PROCUREMENT_SPECIALIST`

**Цель:** обеспечить стройку и подключение оборудованием и подрядчиком.

**Зона ответственности:** наличие или закупка оборудования, выбор подрядчика, сроки поставки и работ. Решение: согласовано / возвращено на доработку / отклонено.

**Видит:** очередь закупочных согласований и заявки, по которым принимал решение.

### 5.7. Руководитель B2B-направления — `B2B_HEAD`

**Цель:** итоговое решение по крупным и стратегическим сделкам; разбор сорванных сроков.

**Зона ответственности:** управленческое согласование (после профильных), эскалации по SLA.

**Видит:** все заявки (просмотр), свои этапы — с правом решения.

### 5.8. Инженер-монтажник — `ENGINEER`

**Цель:** подключить и запустить услугу.

**Зона ответственности:** фиксация стройки (силами подрядчика), монтаж и настройка, тест канала и отметка «услуга активирована», сообщение о проблеме исполнения (например, нет доступа на объект).

**Видит:** очередь этапов исполнения и заявки, по которым выполнял работы.

### 5.9. Координатор заявок — `COORDINATOR`

**Цель:** чтобы ни одна заявка не застряла и не нарушила SLA. Основной пользователь **панели оператора**.

**Зона ответственности:** мониторинг заявок, очередей и SLA; назначение и переназначение исполнителей; первый уровень эскалации; пауза и возобновление SLA при ожидании клиента; отмена заявки по служебной причине (дубль, ошибка).

**Видит:** все заявки, очереди и SLA.

**Не может:** принимать решения по этапам за исполнителей — только переназначить.

### 5.10. Системный администратор — `ADMIN`

**Цель:** техническое сопровождение платформы.

**Зона ответственности:**
- подтверждение и отклонение регистрации компаний;
- справочники (услуги, нормативы SLA) и пороги маршрутизации.

**Видит:** справочники, пороги, заявки на регистрацию компаний (реквизиты).

**Не видит:** заявки на подключение и их содержимое.

## 8. Правила взаимодействия

### 8.1. Назначение менеджера
1. После проверки данных система запрашивает в CRM закреплённого за клиентом менеджера.
2. Если менеджер найден — заявка назначается ему; если нет — попадает в очередь менеджеров.
3. Координатор может переназначить менеджера.

### 8.2. Назначение этапа
1. Система создаёт этап и помещает его в очередь роли.
2. Пользователь роли берёт этап в работу и становится исполнителем.
3. Координатор может назначить исполнителя сразу или переназначить этап в любой момент до решения.

### 8.3. Возврат на доработку
1. Исполнитель этапа возвращает заявку с обязательным комментарием: что исправить.
2. Заявка уходит менеджеру, SLA этапа приостанавливается. Клиент видит статус «На доработке».
3. Если нужны данные клиента — менеджер запрашивает их комментарием для клиента.
4. Менеджер исправляет данные и отправляет заявку повторно.
5. Заявка возвращается на тот же этап. Если изменились параметры, влияющие на маршрут, система пересобирает маршрут. Решения других согласующих сохраняются, если не изменились параметры, на которые они влияют.

### 8.4. Отклонение и отказ по ТВ
1. Согласующий отклоняет заявку с обязательной причиной **или** технический специалист вносит результат ТВ «нет» — заявка автоматически переходит в «Отклонена».
2. Причина отказа сохраняется в истории; менеджер и клиент получают уведомление.
3. Клиент может создать **новую заявку на основе отклонённой** (например, с другой технологией подключения). Новая заявка ссылается на исходную (`parentRequestId`).

### 8.5. Эскалация по SLA
1. Приближение срока → уведомление исполнителю этапа (или очереди роли, если исполнителя нет).
2. Нарушение срока → уведомление исполнителю и координатору.
3. Координатор переназначает этап или выясняет причину; при повторном нарушении — уведомление руководителю B2B.

## 10. MVP и развитие продукта

| Тема | MVP (прототип) | Развитие продукта |
|---|---|---|
| Вход | JWT, логин и пароль | — |
| Регистрация компании | Публичная регистрация, подтверждение системным администратором | Подтверждение полномочий представителя документами |
| Добавление сотрудников | По логину, роли — галочками | По ссылке-приглашению с регистрацией |
| Роли | Несколько ролей у пользователя, переключатель ролей | Объединение прав при совпадении ролей, история смены ролей |
| Компании пользователя | Одна компания | Несколько компаний (например, внешний финансовый консультант) и переключатель компаний |
| Типы представителей | Сотрудник | Сотрудник, внешний, наблюдатель |
| Доступ к заявке | По компании и роли | Участник конкретной заявки (`RequestMember`), в том числе внешний |
| Интерфейс компании | Список участников | История, участники, заявки компании |
| Администрирование | Системный администратор: справочники, пороги, подтверждение компаний | + администратор компании для своих справочников; изоляция данных; аудит действий администратора |
| Отказ по ТВ | Автоматический отказ, новая заявка со ссылкой на исходную | Автоматический отказ с предложением альтернативы, цепочка заявок, статистика отказов |

## 11. Принятые решения

Ответы тимлида на открытые вопросы, 2026-10-13.

| № | Вопрос | Решение (MVP) |
|---|---|---|
| 1 | Как пользователи попадают в систему | JWT; публичная регистрация; компания-клиент регистрируется представителем и подтверждается системным администратором; сотрудники добавляются в компанию по логину с ролями; роли в компании ≠ роли в процессе; демо-пользователи — сидом |
| 2 | Согласования параллельно или последовательно | Профильные — параллельно, управленческое — после них |
| 3 | ТВ «нет» | Автоматический отказ; новая заявка ссылается на исходную (`parentRequestId`); причина отказа — в истории |
| 4 | Несколько ролей у пользователя | Да, ManyToMany; роли назначаются галочками; переключатель ролей; свой интерфейс для каждой роли |
| 5 | Роль администратора | Есть; видит только справочники и пороги, не видит заявки и клиентов; пользователи оператора — через сид |
| 6 | Подрядчик | Внешний участник; его работу фиксирует инженер |
