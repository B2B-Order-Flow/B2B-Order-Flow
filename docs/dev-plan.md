# План разработки MVP

## 1. Назначение

Общий план итерации разработки MVP: что команда делает по неделям и к чему приходит к концу итерации. Документ для общего понимания; задачи, файлы и крайние даты по исполнителям — в планах недель ([plan-week1.md](plan-week1.md), [plan-week2.md](plan-week2.md)).

Итерация: **9 ноября — 4 декабря 2026**. Даты предварительные: при отставании переносятся задачи с приоритетом П2, а не конец итерации.

## 4. Ключевые зависимости

- **Каждую неделю первым делом (до вторника):** контракт ядра на эндпоинты недели (Кирилл) и миграции таблиц недели (Денис). Без них не начинаются ни шлюз, ни интерфейс, ни сущности. Порядок согласования и ревью — [plan-week1.md](plan-week1.md), раздел 8.
- **До 15 ноября:** `notifications.md` и таблица правил формата полей (Дима) — без них нет уведомлений и валидации на неделе 2.
- **До 22 ноября:** описание процесса нескольких вариантов услуги (Егор) — иначе функцию не успеть к 4 декабря.
- **Через всю итерацию:** сквозные тесты включаются по мере готовности ядра, а не в конце.

## 5. Что вне итерации

| Что | Статус |
|---|---|
| Архив и экспорт | П2 недели 3; если не успеваем — неделя 4 или после MVP |
| Несколько вариантов услуги | В модели заложено; реализация на неделе 4, если описан процесс и есть время |
| Брокер сообщений (RabbitMQ) | Путь развития, в MVP не входит |
| Генерация печатных форм договоров и актов | Вне объёма ([scope.md](scope.md)) |

## 6. Готовность к защите (к 4 декабря)

- SC-01, SC-02 и SC-03 проходят в интерфейсе всеми ролями; автотесты по ним зелёные в CI.
- Ключевые крайние случаи (сбой интеграции, нарушение SLA, отмена, доступ к чужим данным) покрыты тестами.
- Демонстрация на чистом стенде: `docker compose up`, сид, сквозной сценарий — два прогона подряд без правок кода.
- README с инструкцией запуска; [tz-coverage.md](tz-coverage.md) отражает итоговое состояние по задачам и критериям ТЗ.
