# Интеграции с внешними системами

## 1. Назначение

Документ задаёт контракты трёх mock-сервисов, синтетические данные, политику таймаутов и повторов, а также поведение системы при сбое интеграции (EC-10). Реальные системы МТС не используются и не требуются (ТЗ, раздел «Результат»).

Документ — вход для:
- Салавата — конфигурация WireMock и наборы данных;
- Кирилла — модуль Integration Gateway в ядре;
- Дениса — отображение ошибок интеграции в интерфейсе;
- QA — EC-03, EC-10, EC-15, SC-00.

Основа: [architecture.md](../architecture/architecture.md), [api-contract.md](api-contract.md), [status-model.md](status-model.md) (T01–T03), [domain-model.md](domain-model.md) (`external_check`).

## 2. Состав и назначение

| Система | Контейнер | Что даёт | Когда вызывается |
|---|---|---|---|
| **Mock CRM** | `mock-crm` | Сегмент клиента, закреплённый менеджер | Отправка заявки (T01) |
| **Mock Биллинг** | `mock-billing` | Задолженность клиента | Отправка заявки (T01) |
| **Mock Справочник клиентов** | `mock-registry` | Существование организации по ИНН, реквизиты, признак госзаказчика | Регистрация компании (SC-00), отправка заявки (T01) |

Все три поднимаются одним образом WireMock с разными наборами заглушек либо одним контейнером с разными путями — решение за Салаватом; контракт от этого не зависит.

```text
[ Core Service ]
   │ REST + Spring Retry, вне транзакций, таймаут 2 с на попытку
   ├──► GET http://mock-crm:8080/crm/v1/customers?inn=...
   ├──► GET http://mock-billing:8080/billing/v1/accounts/{inn}/balance
   └──► GET http://mock-registry:8080/registry/v1/organizations?inn=...
```

Базовые URL задаются переменными окружения (`MOCK_CRM_URL`, `MOCK_BILLING_URL`, `MOCK_REGISTRY_URL`), чтобы в тестах их можно было подменить на WireMock из Testcontainers.

## 3. Общие соглашения

| Тема | Решение |
|---|---|
| Протокол | REST, `application/json; charset=utf-8` |
| Версия | В пути (`/v1`) |
| Идентификатор клиента | ИНН (строка: 10 цифр для организации, 12 для ИП) |
| Трассировка | Ядро передаёт `X-Correlation-Id`; mock возвращает его же |
| Ошибки | `application/problem+json` с полем `code` — тот же формат, что в [api-contract.md](api-contract.md), раздел 3 |
| «Не найдено» | `404` с `code: NOT_FOUND` — это **нормальный бизнес-ответ**, а не сбой |
| Сбой | `5xx`, таймаут или недоступность хоста — технический сбой, обрабатывается по разделу 6 |
| Транзакции | Вызовы выполняются **до открытия транзакции** ядра и не держат соединение Hikari |

Важное различие: `404` от справочника при регистрации компании означает «ИНН не найден» и ведёт к бизнес-решению (отклонить регистрацию, SC-00 A1). `503` означает «справочник не ответил» и ведёт к EC-10. Смешивать их нельзя.

## 4. Контракты

### 4.1. Mock CRM

```
GET /crm/v1/customers?inn=7725012341
```

**200 OK**

```json
{
  "inn": "7725012341",
  "name": "ООО «Логистик Плюс»",
  "segment": "LARGE",
  "assignedManagerLogin": "a.smirnova",
  "updatedAt": "2026-10-01T09:00:00Z"
}
```

| Поле | Тип | Куда попадает | Примечание |
|---|---|---|---|
| `segment` | `SMB` / `LARGE` / `STRATEGIC` | `request.segment` | Влияет на R-08 |
| `assignedManagerLogin` | строка или `null` | `request.crm_manager_id` | `null` — заявка идёт в очередь менеджеров (EC-19) |
| `name` | строка | Не перезаписывает название компании | Только для сверки |

**404 Not Found** — клиента нет в CRM. Это не ошибка: заявка продолжает обработку, `segment` остаётся пустым, заявка идёт в очередь менеджеров. Пустой сегмент не включает R-08 (управленческое согласование по стратегическому клиенту).

Если `assignedManagerLogin` указывает на несуществующего или неактивного пользователя либо на пользователя без роли `SALES_MANAGER`, ядро считает, что менеджер не закреплён, и ставит заявку в очередь. Это пишется в `external_check` и в аудит.

### 4.2. Mock Биллинг

```
GET /billing/v1/accounts/7844002230/balance
```

**200 OK**

```json
{
  "inn": "7844002230",
  "debtAmount": "45000.00",
  "currency": "RUB",
  "checkedAt": "2026-10-26T14:00:00Z"
}
```

| Поле | Тип | Куда попадает | Примечание |
|---|---|---|---|
| `debtAmount` | строка, два знака | `request.debt_amount` | `> debt_threshold_rub` включает R-04 (EC-03) |

**404 Not Found** — лицевого счёта нет (новый клиент). Трактуется как `debtAmount = 0`.

### 4.3. Mock Справочник клиентов

```
GET /registry/v1/organizations?inn=5050123455
```

**200 OK**

```json
{
  "inn": "5050123455",
  "kpp": "505001001",
  "ogrn": "1025050123450",
  "name": "АО «Агрохолдинг Заря»",
  "legalAddress": "143000, Московская обл., г. Одинцово, ул. Южная, д. 4",
  "status": "ACTIVE",
  "isGovCustomer": false
}
```

| Поле | Тип | Куда попадает | Примечание |
|---|---|---|---|
| `status` | `ACTIVE` / `LIQUIDATED` | — | `LIQUIDATED` — основание отклонить регистрацию |
| `isGovCustomer` | boolean | `request.is_gov_customer` | Включает R-02 (юридическое согласование) |
| `kpp`, `ogrn`, `name`, `legalAddress` | строки | Сверка с введёнными реквизитами | Расхождение показывается администратору при подтверждении |

**404 Not Found** — организации нет в справочнике. При регистрации компании это основание для отклонения с причиной «ИНН не найден в справочнике клиентов» (SC-00 A1, код `COMPANY_INN_NOT_FOUND`). При отправке заявки (компания уже подтверждена) — `is_gov_customer = false`, процесс продолжается.

Проверка ИНН идёт в два шага: сначала **локально** контрольная сумма и длина (10 или 12 цифр), и только при успехе — запрос в справочник. Неверная контрольная сумма — `422` без обращения к моку.

## 6. Политика сбоев

### 6.1. Повторы и таймауты

| Параметр | Значение |
|---|---|
| Таймаут соединения | 1 с |
| Таймаут ответа | 2 с |
| Попыток всего | 3 (первая + 2 повтора) |
| Задержка между попытками | 200 мс, затем 600 мс (экспоненциально, множитель 3) |
| Худший случай на одну систему | ~7 с |
| Повторять на | `5xx`, таймаут, недоступность хоста |
| **Не** повторять на | `4xx`, включая `404` — это бизнес-ответ |

Реализация: `Spring RestClient` + `Spring Retry` (`@Retryable` с `maxAttempts = 3`), **вне** `@Transactional`.

### 6.2. Параллельность и общий бюджет

Три системы опрашиваются **параллельно** (общий бюджет ~7 с, а не 21 с), результат собирается по всем трём. Это умещается в бюджет обработчика ядра 10 с из [api-contract.md](api-contract.md), раздел 8.

### 6.3. Частичный успех

Системы независимы: отказ одной не отменяет данные остальных.

| CRM | Биллинг | Справочник | Результат |
|---|---|---|---|
| ОК | ОК | ОК | Переход T03, этап `MANAGER_REVIEW` |
| сбой | ОК | ОК | `integration_error = true`, заявка остаётся в `DATA_CHECK` (EC-10) |
| ОК | сбой | ОК | То же |
| ОК | ОК | сбой | То же |

Полученные данные сохраняются сразу, повторная проверка запрашивает **только недостающие** системы. Так повторный запуск не перезатирает уже полученный сегмент.

Отсутствие данных не трактуется как «долга нет» или «не госзаказчик»: заявка не идёт дальше, пока все три системы не ответили. Это прямое следствие решения «ждать с повторной проверкой, не пропускать и не отклонять» ([scenarios.md](../business/scenarios.md), принятое решение № 4).

### 6.4. Поведение при сбое (EC-10)

1. Ядро исчерпало попытки по одной или нескольким системам.
2. Заявка остаётся в статусе `DATA_CHECK`, выставляется `integration_error = true`.
3. В `external_check` пишется запись: система, `status = ERROR`, число попыток, сырой ответ или текст ошибки, время.
4. Координатор получает уведомление `INTEGRATION_ERROR`.
5. HTTP-ответ на `POST /requests/{id}/submit` — **успешный** (`200`): заявка принята, проверка не завершена. Интерфейс показывает, что данные уточняются.
6. Повторная проверка выполняется автоматически фоновой задачей и вручную координатором (`POST /requests/{id}/recheck-data`).
7. Заявка **не отклоняется** из-за технического сбоя никогда.

### 6.5. Фоновая повторная проверка

| Параметр | Значение |
|---|---|
| Периодичность | Каждые 5 минут (`PROD`), каждые 30 секунд (`DEMO`) |
| Что выбирает | Заявки в `DATA_CHECK` с `integration_error = true`, у которых есть незавершённые проверки |
| Интервалы попыток | Нарастающие: 5, 10, 20, 40 минут, далее каждый час |
| Предел | 24 часа; затем уведомление координатору и руководителю, автоматические попытки прекращаются, остаётся ручная |
| Контрольный срок | Заявка в `DATA_CHECK` контролируется отдельным сроком ([sla.md](sla.md), раздел 8) |

## 7. Что именно читает ядро

| Параметр заявки | Источник | Поле ответа | Если системы нет |
|---|---|---|---|
| `segment` | CRM | `segment` | Пусто, R-08 не срабатывает |
| `crm_manager_id` | CRM | `assignedManagerLogin` | Очередь менеджеров (EC-19) |
| `debt_amount` | Биллинг | `debtAmount` | `0.00` при `404`; при сбое — ждём |
| `is_gov_customer` | Справочник | `isGovCustomer` | `false` при `404`; при сбое — ждём |
| Реквизиты для сверки | Справочник | `kpp`, `ogrn`, `name`, `legalAddress` | Администратор решает вручную |

Сырой ответ каждой системы целиком сохраняется в `external_check.raw_payload` (JSONB) — читается целиком при разборе инцидентов, по нему не ищем.

## 8. Логирование и безопасность

- В лог пишутся: система, URL без параметров, код ответа, длительность, номер попытки, `correlationId`. Тело ответа в лог **не** пишется (там реквизиты и суммы) — оно хранится в `external_check`.
- Моки доступны только из приватной сети Docker, наружу их порты не публикуются.
- У моков нет аутентификации, потому что и данные синтетические, и сеть закрытая. В продуктовом варианте тут был бы mTLS или сервисный токен — это зафиксировано как осознанное упрощение.

## 9. Тесты

| Тест | Что проверяет | Сценарий |
|---|---|---|
| Успешная проверка трёх систем | Параметры записаны, переход T03 | SC-01 |
| `assignedManagerLogin = null` | Заявка в очереди менеджеров | EC-19, SC-03 |
| Долг выше порога | В маршрут добавлено финансовое согласование | EC-03 |
| `isGovCustomer = true` | В маршрут добавлено юридическое согласование | R-02 |
| `404` от CRM | Процесс продолжается, сегмент пуст | — |
| `404` от справочника при регистрации | Регистрация отклонена с причиной | SC-00 A1 |
| `503` на две попытки, затем `200` | Повторы доводят до успеха, заявка идёт дальше | — |
| Постоянный `503` | `integration_error`, заявка в `DATA_CHECK`, уведомление координатору, не отклонена | EC-10 |
| Задержка 30 с | Таймаут срабатывает, HTTP-ответ не висит | EC-10 |
| Частичный сбой | Полученные данные сохранены, повтор запрашивает только недостающее | EC-10 |
| Повторная проверка координатором | Заявка уходит дальше без повторной отправки клиентом | EC-10 |
| Неверная контрольная сумма ИНН | `422` без обращения к моку | EC-02 |
| Вызовы вне транзакции | При сбое не растёт число занятых соединений Hikari | — |

Инструменты: WireMock (в Testcontainers для интеграционных тестов ядра), отдельные контейнеры моков для E2E и демо.

## 10. Открытые вопросы

| № | Вопрос | Предложение | С кем решить |
|---|---|---|---|
| 1 | Один контейнер WireMock на все три системы или три отдельных | Три: ближе к реальности и позволяет гасить по одной в тестах | Салават, Кирилл |
| 2 | Нужен ли отдельный эндпоинт справочника для адресов подключения | Нет: адрес вводит клиент текстом, проверка ТВ — ручная (`TECH_CHECK`) | Дима |
| 3 | Предел автоматических повторов 24 часа | Да; дальше только вручную | Дима, Кирилл |
| 4 | Хранить ли историю всех вызовов или только последний по каждой системе | Все: `external_check` только добавляется, это материал для разбора | Кирилл |
| 5 | Нужен ли мок, возвращающий расхождение реквизитов с введёнными | Полезен для демонстрации работы администратора; добавить при наличии времени | Салават |
