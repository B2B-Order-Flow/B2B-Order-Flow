# Нефункциональные требования

## 1. Назначение

Документ фиксирует требования, которые не описываются сценариями: объёмы данных, время отклика, доступность, хранение и удаление данных, бэкап, лимиты и режимы деградации. Он нужен, чтобы при реализации и на защите можно было сказать не «система работает», а «система работает в таких границах».

Это **учебный прототип**, поэтому требования заданы на уровне, который можно проверить на одной машине. Там, где продуктовое решение отличалось бы, это указано отдельной строкой — такие места и есть материал для вопросов на защите.

Основа: [architecture.md](../architecture/architecture.md), [api-contract.md](api-contract.md), [domain-model.md](domain-model.md), [archive-export.md](archive-export.md).

## 2. Объёмы данных

Расчётный горизонт — демонстрация и защита, с запасом на сид и нагрузочную проверку.

| Сущность | Рабочий объём | Объём для нагрузочной проверки |
|---|---|---|
| Компании-клиенты | 7 в базовом сиде, +3 в тестовом профиле ([integrations.md](integrations.md), 5.1) | 1 000 |
| Пользователи | 20 в базовом сиде, 23 в тестовом ([integrations.md](integrations.md), 5.1) | 2 000 |
| Заявки | 50 | 20 000 |
| Этапы | ~400 | 160 000 |
| Записи аудита | ~2 000 | 500 000 |
| Уведомления | ~1 000 | 200 000 |
| Вложения | ~50 файлов, до 100 МБ | 2 000 файлов, до 5 ГБ |

Проверка: генератор синтетических заявок (`infra/seed/load-gen`) заполняет БД до объёма второй колонки, после чего замеряются показатели раздела 3. Это разовая проверка перед защитой, а не постоянный тест в CI.

## 3. Время отклика

Измеряется на объёме второй колонки раздела 2, на одной машине, 95-й процентиль, без учёта сети браузера.

| Операция | Цель (p95) | Предел |
|---|---|---|
| Вход, выдача токена | 300 мс | 1 с |
| Список заявок (страница 20) | 400 мс | 1 с |
| Карточка заявки с маршрутом и SLA | 600 мс | 1,5 с |
| Очередь роли, «мои задачи» | 400 мс | 1 с |
| Действие по этапу (решение, взятие) | 500 мс | 1,5 с |
| Отправка заявки (с тремя внешними вызовами) | 2 с | 10 с (бюджет обработчика) |
| Поиск по архиву | 1 с | 3 с |
| История заявки | 500 мс | 1,5 с |
| Экспорт 10 000 строк в CSV | 15 с | 60 с (асинхронно) |
| Доставка события по WebSocket после коммита | 1 с | 5 с |
| Срабатывание события SLA после наступления срока | 1 мин (`PROD`), 10 с (`DEMO`) | 2 интервала планировщика |

Требования к запросам: ни один экран не делает запрос без `LIMIT`, выборки по заявкам всегда идут с условием по `company_id` или `assignee_id`, выгрузка в CSV читается курсором, а не целиком в память.

## 4. Доступность и режимы деградации

Прототип работает в одном экземпляре каждого сервиса, без кластера и без автоматического переключения при отказе. Упавший контейнер при этом перезапускается политикой `unless-stopped` — это восстановление сервиса, но не резервирование.

| Компонент | Отказ | Что происходит | Что видит пользователь |
|---|---|---|---|
| Mock-сервис | Недоступен | Заявка остаётся в `DATA_CHECK`, `integration_error`, фоновые повторы | «Данные уточняются», заявка не потеряна (EC-10) |
| Ядро | Недоступно | BFF отдаёт `503`/`504` с `retryable: true` | Сообщение и кнопка «Обновить»; данные не теряются |
| БД | Недоступна | Ядро не обслуживает запросы, `/actuator/health` красный | То же, что при отказе ядра |
| BFF | Недоступен | Nginx отдаёт `502` | Статическая страница с сообщением |
| WebSocket | Разрыв | Переподключение с задержкой 1–30 с, затем чтение непрочитанных по REST | Уведомления доезжают с задержкой, не теряются |
| Планировщик SLA | Простой ядра | После старта обрабатываются все просроченные `next_event_at` по порядку | События SLA приходят с задержкой |

`healthcheck` задан у **всех** контейнеров: БД (`pg_isready`), ядро (`/actuator/health`), BFF (`/health`), Nginx (запрос статики), WireMock (`/__admin/health`). Порядок запуска выстроен цепочкой `depends_on: condition: service_healthy`: БД и моки → ядро → BFF → Nginx. Без healthcheck у BFF Nginx поднимается раньше него, и первые запросы получают `502`.

Чего в прототипе **нет** и что в продукте делалось бы иначе: кластер БД и репликация, несколько экземпляров ядра, общий pub/sub для WebSocket, внешний брокер, автоматическое переключение при отказе.

## 5. Хранение и удаление данных

Главная продуктовая ценность — что заявка с документами и историей доступна в любое время, в том числе после закрытия ([archive-export.md](archive-export.md)). Поэтому сроки хранения заданы явно.

| Данные | Срок хранения | Удаление |
|---|---|---|
| Заявки, этапы, решения, вложения | Бессрочно | Не удаляются никогда, в том числе после закрытия и отмены |
| `audit_log` | Бессрочно | Не удаляется и не правится: пользователю приложения выданы только `INSERT` и `SELECT`. Демо-заявки сид создаёт через API, поэтому аудит по ним пишет само приложение; миграции Flyway идут под ролью-владельцем и напрямую в журнал не пишут |
| `request_revision` | Бессрочно | Не удаляются |
| Уведомления | 90 дней после прочтения | Фоновая задача |
| `external_check` | 180 дней | Фоновая задача; агрегаты для разбора инцидентов не нужны |
| Журнал пауз SLA | Вместе с заявкой, бессрочно | Не удаляется |
| Ключи идемпотентности | 24 часа | Фоновая задача |
| Билеты WebSocket | 30 секунд | По истечении срока |
| Файлы экспорта | 24 часа | Фоновая задача |
| Неотправленный черновик заявки | До удаления клиентом | Мягкое удаление (`deleted_at`), данные остаются в БД |

Персональных данных в системе немного (ФИО, email, телефон контактного лица) и все они синтетические. Требования 152-ФЗ как к продуктовой системе не выполняются и не заявляются; задача прототипа — показать продуманную модель доступа и аудит. Это формулировка для защиты, а не отговорка: ограничение осознанное и записано здесь.

## 6. Бэкап и восстановление

| Параметр | Решение |
|---|---|
| Что бэкапим | `core_db` целиком и том с вложениями |
| Как | `pg_dump` по расписанию в именованный том `core-backups` из отдельного контейнера с cron; вложения — `tar` тома `core-files`. Дампы не кладутся в рабочее дерево репозитория, каталог выгрузок в `.gitignore` |
| Частота | Раз в сутки; перед защитой — вручную до и после сида |
| Хранение | 7 последних копий |
| Допустимая потеря данных (RPO) | До 24 часов: копия делается раз в сутки, между копиями возможна потеря изменений за этот период |
| Цель восстановления (RTO) | Прототип поднимается из последней копии не дольше 30 минут |
| Доступ контейнера бэкапа | К БД через отдельную роль `backup_ro` (только чтение, права для `pg_dump`); к тому `core-files` — только чтение; в сеть остальных сервисов не входит |
| Проверка | Восстановление проверяется минимум один раз до защиты, результат фиксируется в `infra/backup/README.md` |

Миграции Flyway выполняются отдельным пользователем БД; откат делается новой миграцией, а не правкой применённой.

## 7. Лимиты

| Что | Лимит | Поведение при превышении |
|---|---|---|
| Размер одного файла | 10 МБ | `422`, код `FILE_TOO_LARGE` |
| Вложений на заявку | 20 | `422`, код `TOO_MANY_ATTACHMENTS` |
| Типы файлов | `pdf`, `docx`, `xlsx`, `jpg`, `png` | `422`, код `FILE_TYPE_NOT_ALLOWED`; тип проверяется по содержимому, не по расширению |
| Размер тела JSON-запроса | 1 МБ (`client_max_body_size` на `/api`) | `413` на Nginx |
| Размер запроса на загрузку файла | 11 МБ — отдельный `location` для `/api/v1/requests/*/attachments` | `413` на Nginx. Лимит выше файлового (10 МБ), чтобы запас на служебные поля multipart не срабатывал раньше проверки в ядре и пользователь получал `FILE_TOO_LARGE`, а не `413` |
| `size` в пагинации | 100 | `422` |
| Строк в экспорте | 50 000 | `422`, код `EXPORT_TOO_LARGE`: слишком широкие фильтры — это ошибка самого запроса, а не частоты |
| Одновременных экспортов на пользователя | 1 | `429`, код `EXPORT_IN_PROGRESS` |
| Запросов с одного адреса | 100/мин на `/api`, 10/мин на `/auth/login` | `429` на Nginx. Значения конфигурируемые: в профилях `demo`, `e2e` и нагрузочном поднимаются, иначе Playwright и сид упираются в лимит с одного адреса |
| Длина комментария | 4 000 символов | `422` |
| Активных WebSocket-соединений на пользователя | 5, в профилях `demo` и `e2e` больше | Самое старое закрывается |

## 8. Безопасность

Подробно — [system-design.md](../architecture/system-design.md), раздел 5. Здесь только проверяемые требования.

| Требование | Как проверяется |
|---|---|
| Пароли хранятся хешем с солью (Argon2 или bcrypt) | Ревью, тест на отсутствие пароля в ответах API |
| Наружу открыт только Nginx | `docker compose ps`: у БД, ядра и моков нет публикуемых портов. Admin API WireMock открывается только compose-override профиля `e2e` |
| Actuator и Swagger ядра недоступны извне | Тест: запрос снаружи получает `404`/`502` |
| В логах нет паролей, токенов, тел ответов внешних систем | Grep по логам в CI-проверке |
| Данные одной компании недоступны другой | Негативный тест на каждый эндпоинт (EC-16) |
| Удалённый сотрудник теряет доступ | Негативный тест (EC-17) |
| Менеджер не согласует свою заявку | Негативный тест (EC-18) |
| Скачивание документа и экспорт пишутся в аудит | Тест на появление записи |
| Секреты не в репозитории | `gitleaks` в CI |
| Зависимости без известных критических уязвимостей | Проверка зависимостей в CI |

## 9. Наблюдаемость

| Что | Решение |
|---|---|
| Логи | SLF4J + Logback (ядро), `structlog` или стандартный logging (BFF); единый формат с `correlationId` |
| Сквозная трассировка | `X-Correlation-Id` проходит Nginx → BFF → ядро → `audit_log` |
| Здоровье | `/actuator/health` (ядро, внутри сети), `/health` (BFF) |
| Метрики | Прометеевский эндпоинт не поднимаем; достаточно логов и БД |
| Что считаем по БД | Число заявок по статусам, нарушения SLA, суммарные паузы, число возвратов |

Детали формата и уровней — `architecture/logging.md`.

## 10. Совместимость и локализация

| Тема | Решение |
|---|---|
| Браузеры | Последние версии Chrome, Firefox, Edge; мобильная вёрстка не требуется |
| Разрешение | От 1366×768 |
| Язык интерфейса | Русский, один; тексты в коде не хардкодятся вразнобой, а лежат в одном месте |
| Время | В БД UTC, в интерфейсе локальное время пользователя; рабочий календарь SLA — `Europe/Moscow` |
| Деньги | Рубли, строка с двумя знаками |
| Кодировка | UTF-8 везде, включая CSV (с BOM, чтобы Excel открывал корректно) |

Генератор синтетических заявок для проверки объёмов обращается к ядру напрямую, минуя Nginx: иначе он упрётся в лимит запросов с одного адреса независимо от профиля.
