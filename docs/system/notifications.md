# Уведомления

## 1. Назначение

Документ определяет, какие события создают уведомления, кто их получает, с каким текстом, и как уведомление доходит до пользователя.

Кому он нужен:
- ядро (Кирилл) — кому создаются записи `notification` по каждому событию (разделы 3, 4, 6);
- шлюз (Денис) — состав сигнала WebSocket (раздел 5);
- интерфейс (Егор) — тексты и показ уведомлений (разделы 4, 7; экран UI-14 — [ui-requirements.md](../business/ui-requirements.md), 7.4).

Связанные документы:
- коды событий — [api-contract.md](api-contract.md), раздел 7; WebSocket и канал «ядро → шлюз» — разделы 4.4 и 4.5;
- переходы — [status-model.md](status-model.md), раздел 6;
- события SLA и контрольных сроков — [sla.md](sla.md), разделы 7 и 8;
- кто что видит — [roles.md](../business/roles.md), разделы 5 и 8;
- хранение — [nfr.md](nfr.md); таблица `notification` — [domain-model.md](domain-model.md).

## 2. Каналы

| Канал | Что это | Когда |
|---|---|---|
| Уведомление в системе | Запись в `notification`: колокольчик со счётчиком и список UI-14. Источник истины | MVP |
| Сигнал WebSocket | Только «есть новое уведомление»; данные интерфейс забирает по REST | MVP, П2 недели 2. До подключения — запрос непрочитанных раз в 30 секунд и после каждого действия ([ui-requirements.md](../business/ui-requirements.md), 7.4) |
| Push в мобильном приложении | Те же записи `notification`, доставка на телефон | Итерация 3, состав — в аналитике приложения |
| Email, SMS | — | Не делаем |

Каждое событие матрицы (раздел 4) идёт во все каналы MVP: запись в системе и сигнал WebSocket.

В MVP пользователь уведомления не настраивает: какие события и кому приходят, определяет этот документ.

## 3. Кто получает

### 3.1. Получатели

| Получатель | Кто это |
|---|---|
| Автор заявки | Представитель клиента, который создал заявку. Он отвечает за заявку со стороны клиента. Владелец компании не получает уведомлений по чужим заявкам: он видит их в списке UI-05 |
| Менеджер заявки | Менеджер, назначенный на заявку (T03b) |
| Исполнитель этапа | Пользователь, взявший этап или назначенный на него |
| Очередь роли | Все пользователи с ролью, в очередь которой попал этап, пока у этапа нет исполнителя |
| Координатор | Все пользователи с ролью `COORDINATOR` |
| Руководитель B2B | Все пользователи с ролью `B2B_HEAD` |
| Представитель компании | Пользователь, зарегистрировавший компанию (события подтверждения) |
| Автор экспорта | Пользователь, запустивший экспорт |

Участники заявки (`request_member`) — крючок, в MVP не реализуется ([domain-model.md](domain-model.md)).

### 3.2. Правила

1. **Сотрудники оператора получают события своей роли по заявке:** менеджер — по своей заявке, исполнитель — по своему этапу, очередь — о новом этапе.
2. **Уведомление получают все адресаты события, в том числе тот, кто совершил действие.**
3. **Один получатель — одно уведомление на переход.** Если у перехода есть своё событие для этого получателя, создаётся оно; общее `STATUS_CHANGED` создаётся только тем получателям, для которых своего события нет. Если пользователь попадает в адресаты дважды (например, у него две роли), запись одна.
4. **Клиенту не уходят внутренние данные:** события SLA и контрольных сроков (кроме срока ответа на запрос об отмене, 4.5), внутренние комментарии, имена исполнителей ([roles.md](../business/roles.md), 5.1). При возврате на доработку клиент получает `STATUS_CHANGED`, а не событие с комментарием согласующего.

## 4. Матрица событий

Обозначения получателей — раздел 3.1. В текстах `{номер}` — `request.number`, `{этап}` — название типа этапа, `{причина}` — причина из события. Клик по уведомлению открывает карточку заявки (UI-08), кроме событий компании и экспорта.

Текст говорит, что произошло; если событие требует действия от получателя, текст заканчивается этим действием.

### 4.2. Этапы

| Код | Когда | Получатели | Текст |
|---|---|---|---|
| `STAGE_QUEUED` | Этап создан и попал в очередь роли | Очередь роли | «Новый этап «{этап}» по заявке {номер}» |
| `STAGE_ASSIGNED` | Этап взят или назначен (в том числе T14) | Исполнитель этапа | «Вам назначен этап «{этап}» по заявке {номер}» |
| `STAGE_REASSIGN_REQUIRED` | Исполнитель деактивирован ([status-model.md](status-model.md), 6.5) | Координатор | «Этап «{этап}» по заявке {номер}: исполнитель недоступен. Назначьте другого исполнителя» |

Этап `CLOSING` создаётся сразу на менеджера заявки без очереди ([status-model.md](status-model.md), 6.1.2), поэтому по нему создаётся `STAGE_ASSIGNED`, а не `STAGE_QUEUED`.

### 4.5. Контрольные сроки заявки

По [sla.md](sla.md), 8. Два кода на все контрольные сроки, вид срока — в `payload.deadlineKind`. Коды добавляются в каталог [api-contract.md](api-contract.md), раздел 7. Клиенту отправляется только предупреждение о сроке ответа на запрос оператора об отмене.

| Вид срока (`deadlineKind`) | `CONTROL_DEADLINE_WARNING` | `CONTROL_DEADLINE_BREACH` | Текст |
|---|---|---|---|
| `DATA_CHECK` — проверка данных | Координатор | Координатор | «Заявка {номер}: проверка данных не завершена (срок {скоро истекает / истёк}). Проверьте ошибку интеграции и запустите повторную проверку» |
| `MANAGER_ASSIGNMENT` — назначение менеджера | Координатор | Координатор | «Заявка {номер}: менеджер не назначен (срок {скоро истекает / истёк}). Назначьте менеджера» |
| `TECH_RESULT` — результат ТВ | Координатор | Координатор | «Заявка {номер}: нет результата ТВ (срок {скоро истекает / истёк}). Выясните причину задержки» |
| `ACCEPTANCE` — приёмка | — (клиенту уходит `ACCEPTANCE_REMINDER`) | Менеджер заявки | «Заявка {номер}: срок приёмки истёк, можно закрыть «Принято по умолчанию»» |
| `CANCEL_RESPONSE` — ответ на запрос об отмене | Сторона, которая должна ответить: при запросе клиента — менеджер заявки, при запросе оператора — автор заявки | При запросе клиента — переход T22 и `CANCEL_RESOLVED` (4.3); при запросе оператора — руководитель B2B ([status-model.md](status-model.md), 6.2) | «Заявка {номер}: срок ответа на запрос об отмене скоро истекает» |

`INTEGRATION_ERROR` и `CONTROL_DEADLINE_*` с видом `DATA_CHECK` не дублируют друг друга: первое приходит сразу, когда исчерпаны повторы, второе — когда заявка всё ещё стоит в проверке к контрольному сроку.

## 5. Сигнал WebSocket

Конверт — [api-contract.md](api-contract.md), 4.4: `id` (это `notification.id`), `type` (код события), `requestId`, `createdAt`, `payload`.

В `payload` — только то, что нужно для подписи без запроса к серверу. Персональных данных и комментариев в сигнале нет: текст уведомления интерфейс показывает по данным из REST.

| События | `payload` |
|---|---|
| Этапы, SLA, паузы | `stageId`, `stageType`; для `SLA_WARNING` — `minutesLeft` |
| Контрольные сроки | `deadlineKind` |
| Компания | `companyId` |
| Экспорт | `exportId` |
| Остальные | пусто |

Это отличается от событий TM Forum (например, TMF622), где в событие кладётся весь заказ: там события передаются между системами. У нас уведомления для людей, поэтому сигнал короткий, а данные интерфейс забирает по REST с проверкой прав.

Путь сигнала: ядро записывает `notification` в транзакции перехода → после коммита отправляет сигнал в канал `GET /internal/v1/events/stream` ([api-contract.md](api-contract.md), 4.5) → шлюз рассылает его по WebSocket-соединениям получателя → интерфейс читает непрочитанные по REST.

## 6. Правила создания

1. **Запись `notification` создаётся в той же транзакции, что и переход.** Нет перехода — нет уведомления; откат перехода откатывает уведомление.
2. **Сигнал отправляется после коммита** (`AFTER_COMMIT`), поэтому получатель не увидит уведомление о том, чего не произошло.
3. **Повтор команды не создаёт второго уведомления:** с тем же `Idempotency-Key` ядро возвращает сохранённый результат и перехода не выполняет ([api-contract.md](api-contract.md), 5.1).
4. **События планировщика создаются один раз.** SLA отмечает момент в таймере (`warned_at`, `breached_at`, [sla.md](sla.md), 7.1); контрольные сроки отмечаются так же, поэтому повторный проход планировщика уведомление не дублирует.
5. **Получатели вычисляются в момент события.** Если пользователь потом потерял роль, уже созданное уведомление остаётся у него.

## 7. Прочтение и хранение

| Операция | Эндпоинт | Правило |
|---|---|---|
| Список | `GET /notifications?unread=true` | Только свои уведомления, новые сверху |
| Прочитать одно | `POST /notifications/{id}/read` | Без тела; клик по уведомлению открывает карточку и отмечает прочитанным |
| Прочитать все | `POST /notifications/read-all` | Без тела |

- Повторное прочтение не ошибка: `read_at` не меняется.
- Хранение — 90 дней после прочтения, затем удаление фоновой задачей ([nfr.md](nfr.md)). Непрочитанные не удаляются.

## 8. Принятые решения

| № | Вопрос | Решение |
|---|---|---|
| 1 | Кто получает уведомления со стороны клиента | Автор заявки. Владелец компании по чужим заявкам уведомлений не получает |
| 2 | Уведомлять ли того, кто совершил действие | Да, уведомление получают все адресаты |
| 3 | Когда создаётся `STATUS_CHANGED` | Только тем получателям, для которых у перехода нет своего события |
| 4 | Коды для контрольных сроков | Два общих кода `CONTROL_DEADLINE_WARNING` и `CONTROL_DEADLINE_BREACH` с `deadlineKind`; `ACCEPTANCE_REMINDER` остаётся для клиента |
| 5 | Кто получает предупреждение о сроке ответа на отмену | Сторона, которая должна ответить |
| 6 | Настройки уведомлений у пользователя | В MVP нет |

## 9. Открытые вопросы

| № | Вопрос | Предложение | С кем решить |
|---|---|---|---|
| 1 | В SC-00 при регистрации компании «администратор уведомлён», но кода события для этого нет | Добавить код (например, `COMPANY_SUBMITTED`) с получателем «все администраторы» | Кирилл, Егор |
| 2 | Уведомлять ли менеджеров, когда заявка попала в очередь менеджеров (EC-19, нет закреплённого менеджера) | В MVP не уведомлять: очередь видна в UI-09, при задержке срабатывает контрольный срок `MANAGER_ASSIGNMENT` | Егор |
| 3 | Кто получает уведомления, если автор заявки больше не состоит в компании | Владелец компании | Егор |
| 4 | При отмене по соглашению сумму затрат подтверждает финансовый контролёр (T21), но события для него нет | Добавить ФК в получатели `CANCEL_REQUESTED`, когда нужна оценка затрат (неделя 3) | Егор, Кирилл |
