# Контракт API

## 1. Назначение

Документ задаёт контракт взаимодействия между компонентами: **внешний API** (React ↔ FastAPI BFF) и **внутренний API** (BFF ↔ Java-ядро), а также протокол WebSocket. Он определяет соглашения, единый формат ошибок, идемпотентность, оптимистичную блокировку и перечень операций.

Документ — вход для:
- Дениса — реализация BFF, DTO и валидация (Pydantic v2);
- Кирилла — контроллеры ядра и Bean Validation;
- Егора — вызовы из интерфейса и форматы ответов;
- Салавата — контрактные и E2E-тесты.

Основа: [architecture.md](../architecture/architecture.md) (разделы 2, 5, 6), [status-model.md](status-model.md), [domain-model.md](domain-model.md), [routing-rules.md](routing-rules.md), [sla.md](sla.md).

**Подход contract-first.** Единственный источник истины — файл `core-service/src/main/resources/openapi/core-api.yaml` (внутренний контракт) и `bff-gateway/openapi/external-api.yaml` (внешний). Модели для BFF генерируются из внутреннего контракта, а не пишутся заново. Контракт меняется только через pull request с аппрувом Дениса и Кирилла (CODEOWNERS).

## 2. Соглашения

| Тема | Решение |
|---|---|
| Базовый путь (внешний) | `https://<host>/api/v1/...` — через Nginx на BFF |
| Базовый путь (внутренний) | `http://core-service:8080/internal/v1/...` — только в приватной сети Docker |
| Версионирование | Версия в пути (`/v1`). Несовместимые изменения — новый префикс |
| Формат | `application/json; charset=utf-8`; загрузка файлов — `multipart/form-data` |
| Кодировка дат | ISO 8601 с таймзоной (`2026-10-26T14:05:00Z`). В БД — UTC, в интерфейсе — локальное время пользователя |
| Деньги | Целое число копеек либо строка с десятичной точкой; выбрано: **строка** (`"1200000.00"`), чтобы не терять точность |
| Имена полей | `camelCase` в JSON, `snake_case` в БД. Имена сущностей и статусов — близко к TM Forum |
| Идентификаторы | UUID v4 в пути; человекочитаемый `number` заявки — только для показа |
| Коды статусов и этапов | Строго как в [status-model.md](status-model.md), разделы 3 и 4 |
| Трассировка | Клиент может передать `X-Correlation-Id`; если не передан — BFF генерирует. Значение возвращается в ответе и пишется в `audit_log.correlation_id` |

### 2.1. Пагинация, сортировка, фильтры

Списки всегда страничные:

```
GET /api/v1/requests?page=0&size=20&sort=createdAt,desc&status=IN_APPROVAL&companyId=...
```

```json
{
  "content": [ { "id": "...", "number": "REQ-2026-000123" } ],
  "page": { "number": 0, "size": 20, "totalElements": 137, "totalPages": 7 }
}
```

- `size` по умолчанию 20, максимум 100.
- `sort` — поле и направление; допустимы только поля-колонки (см. [domain-model.md](domain-model.md), раздел 5). Сортировка по полю из JSONB запрещена и возвращает `422`.
- Фильтры — только по колонкам. Полный набор для архива — в [archive-export.md](archive-export.md).

### 2.2. Коды ответов

| Код | Когда |
|---|---|
| `200` | Успешное чтение или действие |
| `201` | Создан ресурс (заявка, вложение, комментарий); в `Location` — ссылка |
| `204` | Удаление черновика, отметка уведомления прочитанным |
| `400` | Некорректный синтаксис запроса |
| `401` | Токен отсутствует, истёк или не прошёл проверку |
| `403` | Роль или принадлежность компании не позволяют действие (EC-16, EC-18) |
| `404` | Объекта нет **или** он есть, но недоступен этому пользователю (не раскрываем существование чужих данных) |
| `409` | Конфликт: версия устарела, переход недопустим из текущего статуса, повторный запрос на отмену |
| `422` | Ошибка валидации бизнес-правил (EC-02), недопустимое поле сортировки или фильтра |
| `429` | Превышен лимит запросов (Nginx или лимит экспорта) |
| `502` / `503` / `504` | Ядро недоступно, не готово или не ответило в срок |

Отдельно: **`403` против `404`.** При попытке открыть заявку чужой компании возвращается `404`, а не `403`, чтобы по коду ответа нельзя было перебором узнать существующие идентификаторы. Сама попытка пишется в аудит (EC-16). `403` используется, когда объект пользователю доступен, но действие ему не разрешено (например, менеджер пытается согласовать свою заявку, EC-18).

## 3. Единый формат ошибок

`application/problem+json` по RFC 9457.

```json
{
  "type": "https://b2b-order-flow/errors/stage-already-decided",
  "title": "Этап уже закрыт",
  "status": 409,
  "detail": "Этап LEGAL_APPROVAL уже имеет решение APPROVE от 2026-10-26T12:00:00Z",
  "instance": "/api/v1/stages/1f2e.../decision",
  "code": "STAGE_ALREADY_DECIDED",
  "correlationId": "01JD2X8K...",
  "retryable": false
}
```

| Поле | Смысл |
|---|---|
| `code` | Машинный код из каталога ниже. Интерфейс ветвится по нему, а не по тексту |
| `retryable` | `true` — имеет смысл повторить (сетевой сбой, ядро недоступно). `false` — повтор не поможет |
| `violations` | Только для `422`: массив `{ "field": "speedMbps", "code": "MUST_BE_POSITIVE", "message": "..." }` |

### 3.1. Каталог кодов

| `code` | HTTP | Когда | Сценарий |
|---|---|---|---|
| `VALIDATION_FAILED` | 422 | Обязательные поля, формат, скорость ≤ 0 | EC-02 |
| `ACTIVE_ROLE_REQUIRED` | 422 | У пользователя несколько ролей, `X-Active-Role` не передан | — |
| `FILE_TOO_LARGE` | 422 | Файл больше 10 МБ | [nfr.md](nfr.md) §7 |
| `FILE_TYPE_NOT_ALLOWED` | 422 | Тип файла не из разрешённого списка (проверка по содержимому) | [nfr.md](nfr.md) §7 |
| `TOO_MANY_ATTACHMENTS` | 422 | Больше 20 вложений на заявку | [nfr.md](nfr.md) §7 |
| `COMPANY_NOT_CONFIRMED` | 422 | Компания не в статусе `ACTIVE` | EC-14 |
| `COMPANY_INN_EXISTS` | 409 | Активная компания с таким ИНН уже есть | EC-15 |
| `COMPANY_INN_NOT_FOUND` | 422 | ИНН не найден в справочнике (при подтверждении) | SC-00 A1 |
| `DUPLICATE_REQUEST_WARNING` | 200 | Не ошибка: предупреждение в теле ответа на создание | EC-12 |
| `ILLEGAL_TRANSITION` | 409 | Переход недопустим из текущего статуса | 6.4 статусной модели |
| `VERSION_CONFLICT` | 409 | `version` в запросе устарел | Конкурентные правки |
| `STAGE_ALREADY_DECIDED` | 409 | Этап закрыт или решение уже принято | EC-13 |
| `STAGE_NOT_IN_YOUR_QUEUE` | 403 | Этап не в очереди активной роли | — |
| `SELF_APPROVAL_FORBIDDEN` | 403 | Менеджер заявки согласует свою заявку | EC-18 |
| `CROSS_COMPANY_ACCESS` | 404 | Заявка другой компании | EC-16 |
| `MEMBERSHIP_REVOKED` | 403 | Сотрудник удалён из компании | EC-17 |
| `CANCEL_AFTER_ACTIVATION` | 409 | Отмена после активации | EC-09 |
| `CANCEL_REQUEST_EXISTS` | 409 | Уже есть открытый запрос на отмену | 11.3 процесса |
| `CANCEL_METHOD_NOT_ALLOWED` | 409 | Способ отмены не соответствует уровню обязательств | 11.3 процесса |
| `PAUSE_REASON_INVALID` | 422 | Причина паузы вне справочника | 10.1 процесса |
| `EXTERNAL_SYSTEM_UNAVAILABLE` | 200 | Не ошибка запроса: заявка остаётся в `DATA_CHECK` с флагом | EC-10 |
| `IDEMPOTENCY_KEY_REUSED` | 409 | Тот же ключ с другим телом запроса | — |
| `EXPORT_LIMIT_EXCEEDED` | 429 | Превышен лимит экспорта | [archive-export.md](archive-export.md) |
| `CORE_UNAVAILABLE` | 503 | BFF не получил ответ от ядра | `retryable: true` |
| `CORE_TIMEOUT` | 504 | Истёк таймаут ожидания ядра | `retryable: true` |

## 4. Аутентификация и доступ

### 4.1. Вход

```
POST /api/v1/auth/register    { "login", "password", "fullName", "email" }      → 201
POST /api/v1/auth/login       { "login", "password" }                           → 200
GET  /api/v1/me                                                                 → 200
```

Ответ на вход:

```json
{
  "accessToken": "eyJ...",
  "expiresIn": 28800,
  "user": {
    "id": "...", "login": "a.smirnova", "fullName": "Анна Смирнова",
    "companyRoles": [],
    "operatorRoles": ["SALES_MANAGER"],
    "companies": [ { "id": "...", "name": "...", "status": "ACTIVE" } ]
  }
}
```

- JWT выдаёт и проверяет **только ядро**. BFF пробрасывает `Authorization: Bearer ...` и не интерпретирует токен.
- Срок жизни токена — 8 часов, refresh-токена в MVP нет (повторный вход). Это осознанное упрощение.
- В теле токена: `sub` (id пользователя), `login`, `roles` (все роли), `companyId` (если есть), `exp`. Решение о доступе принимается по актуальным данным БД, а не только по токену: роль могли отозвать (EC-17).

### 4.2. Активная роль

У пользователя может быть несколько ролей, поэтому каждый запрос к защищённым операциям несёт заголовок:

```
X-Active-Role: TECH_SPECIALIST
```

- BFF пробрасывает заголовок без изменений, ядро проверяет, что роль есть у пользователя, и применяет права **именно этой роли**.
- Если заголовок не передан, а роль у пользователя одна — используется она. Если роль не передана, а их несколько — `422` с кодом `ACTIVE_ROLE_REQUIRED`.
- Если переданной роли у пользователя нет — `403`.

### 4.3. Межсервисная аутентификация

Внутренний API не доверяет сетевой изоляции:

```
X-Internal-Token: <общий секрет из переменной окружения>
Authorization: Bearer <токен пользователя, проброшенный без изменений>
X-Active-Role: <активная роль>
X-Correlation-Id: <идентификатор запроса>
```

Запрос без `X-Internal-Token` ядро отклоняет с `401`, даже из приватной сети. Секрет задаётся переменной окружения и не попадает в репозиторий.

### 4.4. WebSocket

Браузер не передаёт заголовки при установке WS-соединения, поэтому используется одноразовый билет:

```
GET /api/v1/ws/ticket        → { "ticket": "wst_...", "expiresIn": 30 }
WS  wss://<host>/ws?ticket=wst_...
```

- Билет одноразовый, живёт 30 секунд, привязан к пользователю и активной роли, выдаётся ядром, проверяется ядром при установке соединения через BFF.
- Конверт сообщения:

```json
{
  "id": "0f3c...",
  "type": "SLA_WARNING",
  "requestId": "...",
  "createdAt": "2026-10-26T14:05:00Z",
  "payload": { "stageType": "LEGAL_APPROVAL", "minutesLeft": 45 }
}
```

- **WebSocket — только сигнал.** Источник данных — REST: после реконнекта или пропущенного сообщения интерфейс вызывает `GET /api/v1/notifications?unread=true`. Поэтому потеря сообщения не теряет уведомление.
- Коды типов событий перечислены в разделе 7. Кто какое событие получает — в `notifications.md`.
- `ping` от сервера раз в 30 секунд; клиент переподключается с экспоненциальной задержкой (1, 2, 4, 8, максимум 30 секунд).

## 5. Идемпотентность и конкурентность

### 5.1. Идемпотентность создания

Запросы, создающие сущность, принимают заголовок:

```
Idempotency-Key: <UUID, генерирует интерфейс>
```

- Применяется к `POST /requests`, `POST /companies`, `POST /requests/{id}/attachments`, `POST /requests/{id}/cancellation-requests`.
- Ключ, пользователь и результат хранятся в таблице `idempotency_key` 24 часа. Повтор с тем же ключом и тем же телом возвращает **тот же** результат и исходный код ответа. Повтор с тем же ключом и другим телом — `409` (`IDEMPOTENCY_KEY_REUSED`).
- BFF **не повторяет** запись автоматически. Повторяются только `GET`.

### 5.2. Оптимистичная блокировка

Все действия, меняющие состояние заявки, этапа или запроса на отмену, передают версию объекта, которую видел пользователь:

```json
POST /api/v1/stages/{id}/decision
{ "decision": "RETURN", "comment": "Нужен протокол разногласий по п. 5.2", "version": 7 }
```

- Несовпадение версии — `409` (`VERSION_CONFLICT`) с актуальным состоянием объекта в `detail`. Интерфейс перезапрашивает заявку и показывает, что изменилось.
- `version` возвращается в каждом представлении заявки и этапа.
- Выбран `version` в теле, а не `If-Match`/`ETag`: проще отлаживать и генерировать модели, одинаково работает в обоих слоях.

### 5.3. Повторные действия из изменившегося статуса

Переходы идемпотентны по результату: повторный вызов `POST /requests/{id}/submit`, когда заявка уже в `DATA_CHECK`, возвращает `409` (`ILLEGAL_TRANSITION`), а не создаёт второй переход. Это закрывает случай «ядро выполнило действие, ответ потерялся»: интерфейс перезапрашивает состояние и видит, что действие прошло.

## 6. Перечень операций

Все пути приведены для внешнего API (`/api/v1`). Внутренний повторяет их один к одному с префиксом `/internal/v1` — BFF не переименовывает ресурсы, только адаптирует представление под интерфейс. Столбец «Роль» указывает, кому операция доступна (сокращения — по [roles.md](../business/roles.md), раздел 6); столбец «Переход» — идентификатор из [status-model.md](status-model.md).

### 6.1. Компании и пользователи

| Метод и путь | Роль | Что делает |
|---|---|---|
| `POST /companies` | Гость | Регистрация компании, статус `PENDING` |
| `GET /companies/{id}` | ВЛ, АК, ИН | Карточка своей компании |
| `GET /companies/{id}/members` | ВЛ, АК | Участники компании |
| `POST /companies/{id}/members` | ВЛ, АК | Добавить сотрудника по логину |
| `PUT /companies/{id}/members/{userId}/roles` | ВЛ, АК | Изменить роли (не выше своей) |
| `DELETE /companies/{id}/members/{userId}` | ВЛ, АК | Удалить сотрудника (EC-17) |
| `GET /admin/companies?status=PENDING` | АДМ | Очередь подтверждения |
| `POST /admin/companies/{id}/confirm` | АДМ | Подтвердить (сверка ИНН) |
| `POST /admin/companies/{id}/reject` | АДМ | Отклонить с причиной |

### 6.2. Заявка

| Метод и путь | Роль | Переход | Что делает |
|---|---|---|---|

| `PATCH /requests/{id}` | КЛ | — | Правка черновика |
| `DELETE /requests/{id}` | КЛ | — | Удалить неотправленный черновик |
| `POST /requests/{id}/submit` | КЛ | T01 | Отправить оператору |

| `POST /requests/{id}/commercial-terms` | МП | T04 | Зафиксировать тариф, скидку, тип договора и отправить в работу |
| `POST /requests/{id}/resubmit` | МП | T10 | Отправить повторно после доработки |
| `POST /requests/{id}/from-rejected` | КЛ | — | Новая заявка на основе отклонённой (`parentRequestId`) |

## 8. Таймауты и сбои

Правило: **внутренний таймаут всегда меньше внешнего**, иначе внешний уровень обрывает запрос, пока внутренний ещё работает, и исход записи становится неизвестным.

| Уровень | Таймаут | Повторы |
|---|---|---|
| Вызов mock-сервиса из ядра | 2 с на попытку | До 3 попыток с задержкой 200 мс и 600 мс ([integrations.md](integrations.md)) |
| Обработчик ядра | 10 с | — |
| `httpx` в BFF | 15 с (`connect` 2 с) | Только для `GET` |
| Nginx `proxy_read_timeout` | 30 с | — |

- Внешние вызовы выполняются **до открытия транзакции** и не держат соединение Hikari.
- Если внешняя система не ответила, заявка остаётся в `DATA_CHECK` с `integrationError: true`, HTTP-ответ при этом успешный (`200`), а повторную проверку выполняет фоновая задача или координатор через `POST /requests/{id}/recheck-data` (EC-10).
- При недоступности ядра BFF отдаёт `503` или `504` с `retryable: true`; интерфейс показывает сообщение и перезапрашивает состояние.

## 9. Разделение ответственности между слоями

| Задача | BFF | Ядро |
|---|---|---|
| Проверка синтаксиса и типов | Да (Pydantic) | Да (Bean Validation) |
| Бизнес-валидация, права, статусы | Нет | Да |
| Фильтрация полей по роли | Нет | Да |
| Агрегация нескольких вызовов под один экран | Да | Нет |
| Хранение состояния | Нет | Да |
| WebSocket-соединения | Да | Нет (отдаёт события) |
| Выдача и проверка JWT | Нет | Да |

Правило для ревью: если в BFF появляется `if role == ...`, это ошибка — решение должно принимать ядро.
