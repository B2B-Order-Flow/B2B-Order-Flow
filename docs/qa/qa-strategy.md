# Стратегия тестирования

Документ описывает, что, чем и когда мы проверяем. Он закрывает критерий ТЗ «предусмотрены автотесты для ключевых сценариев» (задача 17). Владелец: DevOps и QA. Сопоставление сценариев тестам согласует руководитель проекта.

## 1. Что проверяем и что нет

Проверяем сценарии SC-00…SC-03 и крайние случаи EC из [scenarios.md](../business/scenarios.md), переходы статусов и права по [status-model.md](../system/status-model.md), интеграции с моками ([integrations.md](../system/integrations.md)), проверяемые требования безопасности и целевые p95 из [nfr.md](../system/nfr.md) (разделы 3 и 8).

Не делаем: постоянные нагрузочные тесты в CI (нагрузку на 20 000 заявок проверяем один раз перед защитой), покрытие кода как цель (отчёт JaCoCo без порога), проверки безопасности сверх `nfr.md`.

## 2. Уровни тестов

| Уровень | Что проверяет | Чем | Кто пишет |
|---|---|---|---|
| Unit | Домен, автомат статусов (по тесту на переход), расчёт SLA на фиксированном `Clock` | JUnit 5 (ядро), pytest (BFF), React Testing Library (UI) | Владельцы модулей: ядро, BFF (разработчик API) и интерфейс пишут тесты к своему коду |
| Интеграционные | Ядро, PostgreSQL и моки вместе: маршруты, ошибки интеграций, повторы | JUnit 5, Testcontainers 2.x (PostgreSQL, WireMock) | Разработчик ядра и QA |
| Сквозные API-тесты | Сценарии SC и EC через API поднятого стенда | Playwright (режим API) | QA |
| UI-тесты | Демо-путь в интерфейсе, 2-3 сценария | Playwright | QA (локаторы и тестовые id согласует с фронтендом) |

Testcontainers берём версии 2.x: версия 1.x не работает с Docker Engine 29 ([spring-boot#48104](https://github.com/spring-projects/spring-boot/issues/48104)). Playwright для API и UI один, чтобы не держать два инструмента.

## 3. Какие сценарии автоматизируем

Обязательный минимум: демо-программа из [scenarios.md](../business/scenarios.md), раздел 10, плюс негативные проверки доступа и сбой интеграции.

| Сценарий | Уровень | Тестовые данные |
|---|---|---|
| SC-00 регистрация компании, A1 отказ | API | «Вектор» подтверждается, «Фантом» не найден в справочнике |
| SC-01 стандартная заявка | API, UI | ИП Соколов |
| SC-02 дополнительные согласования, A1 возврат юристом | API | «Логистик Плюс» |
| SC-03 крупная заявка: дополнение маршрута закупочным согласованием после ТВ, параллельные согласования, решение руководителя | API, UI | «Агрохолдинг Заря» |
| SC-03 A1 отклонение руководителем | API | «Агрохолдинг Заря» |
| EC-01 нет технической возможности | API | сид |
| EC-03 у клиента долг | API | «Северторг» |
| EC-04 стройка у стандартной заявки: добавляются финансовое и закупочное, при крупном CAPEX ещё управленческое | API | заявка уровня SC-01 (ИП Соколов), CAPEX 300 000 и 800 000 ([routing-rules.md](../system/routing-rules.md)) |
| EC-05 отклонено одно из параллельных согласований | API | «Логистик Плюс», отклоняет юрист |
| EC-07 нарушение SLA этапа | API, UI | сид с таймером, который скоро сработает |
| EC-10 внешняя система недоступна | Интеграционный, API | «Таймаут», «Медленный», «Шаткий», «Глухой» ([integrations.md](../system/integrations.md), раздел 5) |
| EC-16, EC-17, EC-18 доступ чужой компании, удалённый сотрудник, согласование своей заявки | API, негативные | сид |
| EC-20 отказ клиента после начала работ | API, UI | сид, заявка со стройкой |

Заявки в сиде в профиле DEMO даём отдельными записями под каждый сценарий, чтобы тесты не зависели друг от друга.

Отдельно проверяем логи, ошибки и безопасность из `nfr.md`, раздел 8:

| Проверка | Уровень |
|---|---|
| Ответ с ошибкой содержит `correlationId`, стека в нём нет | API |
| `correlationId` из запроса попадает в `audit_log` и доходит до мока (мок возвращает его же) | Интеграционный |
| При ответе 5xx в логе ядра одна строка `ERROR` | Интеграционный |
| В ответах API нет пароля, Actuator и Swagger снаружи недоступны | API |
| Скачивание документа и экспорт пишутся в `audit_log` | API |
| У БД, ядра и моков нет публикуемых портов (`docker compose ps` по базовому compose) | Скрипт в CI |
| В логах нет паролей, токенов и тел ответов внешних систем (поиск по логам прогона) | Скрипт в CI |

Остальные EC проверяют владельцы модулей на unit-уровне или в интеграционных тестах. Тесты SLA уже перечислены в [sla.md](../system/sla.md), раздел 11, тесты интеграций в [integrations.md](../system/integrations.md), раздел 9: мы не дублируем их, а берём как основу. Для EC-08, EC-09, EC-12, EC-14, EC-15, EC-21 и EC-22 уровень и исполнителя назначаем при планировании итерации 3; что останется без автоматизации, отмечаем в этом файле.

## 4. Время и SLA в тестах

Время считает только ядро, источник времени подменяемый `Clock` ([sla.md](../system/sla.md), раздел 9). В unit и интеграционных тестах `Clock` фиксированный.

На стенде включаем профиль `sla.profile=DEMO`: нормативы в минутах, планировщик запускается раз в 5-10 секунд. Заявки, которым нужно нарушение срока (EC-07, EC-20), загружаем сидом с таймерами, которые скоро сработают. Результат ждём опросом с таймаутом (Awaitility, `expect.poll` в Playwright), без `sleep`. Отдельный эндпоинт сдвига времени пока не нужен, в документах его нет.

## 5. Моки и данные

Ядро берёт адреса моков из `MOCK_CRM_URL`, `MOCK_BILLING_URL` и `MOCK_REGISTRY_URL`. В интеграционных тестах они указывают на WireMock из Testcontainers, в сквозных тестах и на демо на отдельные контейнеры из compose. Организации и ИНН берём из [integrations.md](../system/integrations.md), раздел 5. Состояние сценариев WireMock сбрасываем через Admin API перед каждым тестом, который их использует. В базовом compose порты моков закрыты, для сквозных тестов Admin API открываем в отдельном override-файле, который в проверке портов не участвует.

Данные стенда делим на три слоя. Справочники и настройки, в том числе `routing_config` для `PROD` и `DEMO`, идут миграциями ядра (`db/migration`). Демо-пользователи, их роли и компании идут отдельными миграциями `db/demo`, которые подключаются только в профилях `DEMO` и тестовом ([integrations.md](../system/integrations.md), 5.1); список и соответствие ИНН с моками в [infra/seed/README.md](../../infra/seed/README.md). Демо-заявки создаёт скрипт из `infra/seed/demo-requests/` через API шлюза, а не вставкой в таблицы, иначе у них не будет истории.

## 6. Когда что запускается

| Событие | Что запускается |
|---|---|
| PR в `dev` | Unit-тесты изменённой папки, линтеры, `gitleaks`, проверка зависимостей, проверка портов, поиск секретов в логах unit- и интеграционных тестов |
| PR в `dev` и слияние | Интеграционные тесты |
| Слияние в `dev`, по метке, ночью | Сквозные тесты на compose в профиле DEMO и поиск секретов в логах сервисов за прогон |
| Один раз перед защитой | Нагрузка `infra/seed/load-gen` на 20 000 заявок, восстановление из бэкапа, прогон «чистая машина, `compose up`, сквозной сценарий» |

Сквозные тесты не гоняем на каждый push: они самые долгие, поэтому идут при слиянии в `dev`, по метке и ночью. Репозиторий публичный, лимита минут GitHub Actions нет.

## 7. Когда считаем достаточным

Числовых порогов в ТЗ нет. Предлагаю такой критерий (согласовать с руководителем проекта): все сценарии из раздела 3 зелёные в CI, демо-путь проходит на чистом стенде, негативные проверки доступа и проверка секретов проходят, целевые p95 из `nfr.md` выдерживаются в разовом нагрузочном прогоне на объёме 20 000 заявок.

## 8. Открытые вопросы

Открытых вопросов нет. Тест эскалации EC-07 (+50% норматива после нарушения) привязан к значению из конфигурации ([sla.md](../system/sla.md), раздел 7) и меняется вместе с ним.
