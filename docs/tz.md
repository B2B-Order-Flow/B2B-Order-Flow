# Техническое задание

## Описание проекта

Студенты проектируют и реализуют систему обработки заявок на подключение телеком-услуг для корпоративных клиентов.

В качестве базового сценария рассматривается подключение услуги широкополосного доступа в интернет (ШПД) для корпоративного клиента.

Клиент инициирует заявку на подключение услуги. В зависимости от параметров заявки система должна определить необходимые этапы её обработки и участников процесса.

Для стандартной заявки маршрут может включать проверку технической возможности и последующее исполнение. Для нестандартной заявки могут дополнительно потребоваться согласования юридического, финансового или закупочного блока. Для крупных или нестандартных проектов может предусматриваться дополнительное управленческое согласование.

Таким образом, студенты должны не только реализовать техническую систему, но и самостоятельно определить:

- какие роли участвуют в процессе;
- какие этапы проходит заявка;
- какие условия влияют на маршрут;
- какие действия доступны каждой роли;
- в каких случаях требуется дополнительное согласование;
- какие сроки устанавливаются для отдельных этапов;
- какие события должны приводить к уведомлениям.

Внешние системы — например, CRM, биллинг, справочник клиентов — эмулируются самостоятельно в виде mock-сервисов с синтетическими данными и документированными контрактами API.

Взаимодействие компонентов системы может быть реализовано через REST API, брокер сообщений или другие выбранные студентами механизмы. Архитектурный подход (например, модульный монолит или микросервисная архитектура) выбирается студентами исходя из требований проекта и должен быть обоснован.

## Задачи

1. Изучить бизнес-сценарий обработки заявки на подключение B2B-услуги и описать процесс от создания до исполнения.
2. Определить роли участников процесса и зоны ответственности каждой роли.
3. Спроектировать доменную модель заявки и статусную модель.
4. Определить правила формирования маршрута заявки в зависимости от её параметров.
5. Предусмотреть несколько сценариев обработки: стандартная заявка, заявка с дополнительными согласованиями, крупная/нестандартная заявка.
6. Спроектировать механизм согласования между несколькими подразделениями.
7. Выбрать архитектурный подход и обосновать выделение компонентов системы.
8. Реализовать основные компоненты системы обработки заявок.
9. Реализовать API Gateway или другой механизм единой точки взаимодействия с системой, если это требуется выбранной архитектурой.
10. Реализовать взаимодействие с mock-сервисами внешних систем (например, CRM, биллинг, справочник клиентов).
11. Реализовать контроль SLA для отдельных этапов обработки заявки.
12. Реализовать уведомления участников процесса о назначении, изменении статуса, приближении или нарушении SLA.
13. Реализовать историю изменений заявки и действий пользователей.
14. Разработать веб-панель оператора или другой пользовательский интерфейс для работы с заявками.
15. Описать API и контракты взаимодействия между компонентами системы.
16. Настроить логирование и базовую обработку ошибок.
17. Покрыть ключевые бизнес-сценарии автотестами.
18. Подготовить README и инструкцию по запуску проекта.
19. Подготовить и провести демонстрацию сквозного сценария обработки заявки.

## Технологии

Язык программирования и конкретный технологический стек выбираются студентами исходя из требований проекта и обосновываются в рамках архитектурного решения.

В качестве рекомендуемых технологий могут использоваться:

- Go / C++ / Java (Spring Boot) / Node.js;
- PostgreSQL;
- RabbitMQ / Kafka;
- REST API;
- API Gateway (например, Kong / Spring Cloud Gateway);
- Docker / Docker Compose;
- OpenAPI / Swagger;
- JUnit / pytest и другие инструменты автоматизированного тестирования;
- WireMock / MockServer для эмуляции внешних систем.

Использование микросервисной архитектуры не является обязательным требованием. При её выборе студенты должны обосновать выделение сервисов, их ответственность и способ взаимодействия.

## Цель

Разработать учебный прототип системы, которая автоматизирует обработку заявок на подключение телеком-услуг для корпоративных клиентов: от создания заявки и проверки исходных данных до согласования, исполнения и закрытия заявки с контролем SLA и прозрачной историей статусов.

В рамках проекта студенты должны самостоятельно спроектировать бизнес-процесс обработки заявки, определить необходимые роли, этапы и маршруты согласования, а также выбрать и обосновать архитектурный подход и технологический стек.

## Результат (продукт)

Работающий учебный прототип системы обработки B2B-заявок, включающий пользовательский интерфейс или API для создания и обработки заявок, механизм маршрутизации и согласования, контроль SLA, уведомления и историю изменений.

Архитектура системы, в том числе использование микросервисного подхода, выбирается студентами самостоятельно и должна быть обоснована исходя из требований к системе.

Внешние системы (CRM, биллинг, справочники клиентов и другие) эмулируются студентами самостоятельно с использованием синтетических данных и документированных API-контрактов. Доступ к реальным системам МТС не требуется и не предоставляется.

## Критерий оценки

Критерии приёмки результата / продукта:

- Описан конкретный бизнес-сценарий обработки заявки на подключение B2B-услуги.
- Определены роли участников процесса и зоны их ответственности.
- Разработана статусная модель заявки и логика переходов между статусами.
- Реализован механизм маршрутизации и согласования заявки в зависимости от её параметров.
- Предусмотрены различные варианты маршрута для стандартных и нестандартных заявок.
- Реализован контроль SLA и уведомления о приближении или нарушении сроков.
- Сохраняется история изменений и прохождения заявки по этапам.
- Реализовано взаимодействие с одним или несколькими mock-сервисами внешних систем.
- Выбранный архитектурный подход и ключевые технические решения обоснованы студентами.
- Реализована базовая обработка ошибок и логирование.
- Предусмотрены автотесты для ключевых сценариев.
- Подготовлены README и инструкция по запуску проекта.
- Система запускается на собственной инфраструктуре студентов.
- Проведена публичная защита с демонстрацией сквозного сценария обработки заявки.
