# План итерации MVP: задачи недели 1 и график документов

## 1. Назначение

Документ фиксирует задачи первой недели разработки по исполнителям и график появления и доработки файлов документации. Компоненты названы так же, как в [tz-coverage.md](tz-coverage.md): `core-service`, `bff-gateway`, `ui`, `mocks`, `infra`. Задачи DevOps и QA (репозитории, Compose, CI, мониторинг качества) в документ не входят.

Цель недели 1: каркас всех компонентов и вертикальный срез от создания заявки клиентом до взятия её менеджером (переходы T01–T03b).

Правило недели: файлы системной аналитики не правятся. Расхождения «код против документов» накапливаются списком и закрываются пакетом (раздел 7).

## 2. Ядро (`core-service`) — Кирилл

**Задачи**
1. Скелет ядра: Java 21, Spring Boot, JPA, Security/JWT, Flyway. Первым шагом проверить сборкой, что выбранные версии Spring Boot и библиотек совместимы; при несовместимости взять ближайшую рабочую версию и зафиксировать её.
2. Миграции для компаний, пользователей и ролей. Вход, выдача токена, подтверждение компании администратором.
3. Миграции для заявки, `service_offer` (минимум одно предложение на заявку), этапов, `audit_log`, `request_revision`.
4. Создание черновика и отправка заявки. Переходы T01–T03b: проверка данных, назначение менеджера, взятие заявки менеджером (`claim`).
5. Вызов трёх моков при отправке (CRM, биллинг, справочник ИНН) вне транзакции. Таймаут и повторы по `integrations.md`; сбой не теряет заявку.
6. Запись в `audit_log` при каждом переходе.

**Файлы и на что обратить внимание**
- [domain-model.md](system/domain-model.md):
  - JSONB только для данных, читаемых целиком; всё для фильтров, логики и SLA — колонки.
  - Поле `version` для оптимистичной блокировки.
  - Таблицы `idempotency_key` и `work_calendar`, колонка `search_vector`.
- [status-model.md](system/status-model.md):
  - T03 запускает контрольный срок «Назначение менеджера», T03b его останавливает.
  - Все переходы идут через один сервис, прямых `UPDATE status` нет.
  - Этапы `CONTRACT_SIGNING` и `CLOSING` (на следующих неделях) создаются сразу на владельца заявки, без очереди.
- [integrations.md](system/integrations.md):
  - Состав сида (§5.1) и ИНН-заглушки сбоев: Таймаут, Медленный, Шаткий, Глухой.
  - Сбой моков не откатывает заявку: она остаётся в `DATA_CHECK` с `integration_error` (EC-10).
- [nfr.md](system/nfr.md):
  - Пароли хранятся хешем с солью.
  - Пользователю приложения выданы только `INSERT` и `SELECT` на `audit_log`.
  - Ни одного запроса без `LIMIT`; выборки по заявкам всегда с условием по `company_id` или `assignee_id`.
- [system-design.md](architecture/system-design.md), разделы про безопасность и сбои связи: проверка принадлежности данных компании на каждом эндпоинте (EC-16).

**Результат недели**: заявка проходит путь от создания клиентом до взятия менеджером; есть интеграционный тест на Testcontainers и негативный тест на доступ к данным чужой компании.

## 3. Шлюз (`bff-gateway`) — Денис

**Задачи**
1. Скелет BFF на FastAPI (Pydantic v2, httpx). БД и состояния нет, экземпляр один.
2. Общий клиент к ядру с таймаутами; сбои (недоступно, таймаут) преобразуются в единый формат ошибки с `retryable: true`.
3. Сквозные заголовки: `X-Correlation-Id` (генерируется, если нет), `X-Internal-Token` к ядру, `X-Active-Role` от интерфейса.
4. Эндпоинты недели: вход, регистрация компании, создание, отправка, получение и список заявок, `claim`.
5. Первая версия OpenAPI-контракта для этих эндпоинтов, согласованная с ядром до начала кодирования.
6. Заготовка проверки расхождения OpenAPI ядра и BFF для CI.

**Файлы и на что обратить внимание**
- [api-contract.md](system/api-contract.md):
  - Формат ошибок RFC 9457 (`application/problem+json`, поля `code`, `retryable`, `correlationId`) и каталог кодов.
  - `Idempotency-Key` для создания, `version` в теле при изменении.
- [architecture.md](architecture/architecture.md), раздел про шлюз: бизнес-логики в BFF нет.
- [system-design.md](architecture/system-design.md):
  - Раздел 6: при сбое связи — ошибка в общем формате и обновление страницы запросом к ядру.
  - EC-10: ожидание не дольше бюджета повторов, около 7 с.
- [nfr.md](system/nfr.md): §7 — лимиты (в том числе тело JSON 1 МБ); §3 — целевое время отклика.
- WebSocket на этой неделе не делается. Достаточно зафиксировать, что событие является сигналом, а данные берутся по REST.

**Результат недели**: через BFF проходит вся цепочка из задач ядра; при недоступном ядре пользователь получает корректную ошибку, а не `500`.

## 4. Интерфейс (`ui`) — Егор

**Задачи**
1. Первым шагом написать [ui-requirements.md](business/ui-requirements.md): экраны, поля, состояния, тексты ошибок.
2. Каркас: React, Vite, TanStack Query, маршрутизация, единый слой запросов с обработкой ошибок и кнопкой «Обновить».
3. Переключатель активной роли, значение уходит в `X-Active-Role`.
4. Экраны недели: вход, регистрация компании, список заявок, форма заявки (с учётом нескольких вариантов услуги в модели), карточка с историей, очередь менеджера с кнопкой «Взять».
5. Все тексты интерфейса хранятся в одном месте.

**Файлы и на что обратить внимание**
- [roles.md](business/roles.md): матрица прав — видимость кнопок определяется ей.
- [scenarios.md](business/scenarios.md): SC-00 (регистрация компании) и SC-01 задают порядок экранов.
- [business-process.md](business/business-process.md): названия статусов для пользователя.
- [status-model.md](system/status-model.md): набор статусов и переходов.
- [api-contract.md](system/api-contract.md): формат ошибок и пагинация, которые интерфейс обязан показывать.
- [nfr.md](system/nfr.md), §10: Chrome, Firefox, Edge; от 1366×768; русский язык; локальное время пользователя.

**Результат недели**: `ui-requirements.md` в репозитории; клиент и менеджер проходят свою часть SC-01 в браузере.
