# План итерации MVP: задачи недели 1 и график документов

## 1. Назначение

Документ фиксирует задачи первой недели разработки по исполнителям и график появления и доработки файлов документации. Компоненты названы так же, как в [tz-coverage.md](tz-coverage.md): `core-service`, `bff-gateway`, `ui`, `mocks`, `infra`. Задачи DevOps и QA (репозитории, Compose, CI, мониторинг качества) в документ не входят.

Срок недели 1: **9–15 ноября 2026** (предварительно; календарь итерации — [dev-plan.md](dev-plan.md)).

Цель недели 1: каркас всех компонентов и вертикальный срез от создания заявки клиентом до взятия её менеджером (переходы T01–T03b).

Кто какие тесты пишет: unit — владельцы модулей, интеграционные и сквозные — по [qa-strategy.md](qa/qa-strategy.md), раздел 2.

Контракт ядра пишет Кирилл, контракт шлюза — Денис. Схему БД (миграции Flyway на SQL) пишет Денис, сущности JPA по ней — Кирилл. Порядок согласования, ревью и правила работы без конфликтов — раздел 8.

Правило недели: файлы системной аналитики не правятся. Расхождения «код против документов» накапливаются списком и закрываются пакетом (раздел 7).

Общий план итерации до 4 декабря 2026 по неделям — [dev-plan.md](dev-plan.md). Как читать сроки внутри недели: «первым делом» — до вторника включительно, «середина недели» — среда, «конец недели» — воскресенье.

## 2. Ядро (`core-service`) — Кирилл

**Задачи**
1. Скелет ядра: Java 21, Spring Boot, JPA, Security/JWT, Flyway. Первым шагом проверить сборкой, что выбранные версии Spring Boot и библиотек совместимы; при несовместимости взять ближайшую рабочую версию и зафиксировать её.
2. **До 10.11.** Первым делом — внутренний OpenAPI-контракт (`core-api.yaml`) на эндпоинты недели и генерация серверных интерфейсов из него (раздел 8).
3. Сущности JPA для компаний, пользователей и ролей — по миграциям Дениса. Вход, выдача токена, подтверждение компании администратором.
4. Сущности JPA для заявки, `service_offer` (минимум одно предложение на заявку), этапов, `audit_log`, `request_revision`; `ddl-auto=validate`. Ревью миграций Дениса.
5. Создание черновика и отправка заявки. Переходы T01–T03b: проверка данных, назначение менеджера — взятие из очереди (`claim`) и назначение координатором (`assign-manager`, EC-19). На этой неделе переходы пишут статус и аудит; контрольные сроки и уведомления, которые они запускают по [status-model.md](system/status-model.md), раздел 8, подключаются на неделе 2, когда появятся таблицы SLA и `notification`.
6. Вызов трёх моков при отправке (CRM, биллинг, справочник ИНН) вне транзакции. Таймаут и повторы по `integrations.md`; сбой не теряет заявку.
7. Запись в `audit_log` при каждом переходе.

**Файлы и на что обратить внимание**
- [domain-model.md](system/domain-model.md):
  - JSONB только для данных, читаемых целиком; всё для фильтров, логики и SLA — колонки.
  - Поле `version` для оптимистичной блокировки.
  - Таблицы `idempotency_key` и `work_calendar`, колонка `search_vector`.
  - Раздел 8: соглашения по схеме — сущности должны им соответствовать.
- [status-model.md](system/status-model.md):
  - T03 запускает контрольный срок «Назначение менеджера», T03b его останавливает.
  - Все переходы идут через один сервис, прямых `UPDATE status` нет.
  - Этапы `CONTRACT_SIGNING` и `CLOSING` (на следующих неделях) создаются сразу на владельца заявки, без очереди.
- [integrations.md](system/integrations.md):
  - Состав сида (§5.1) и ИНН-заглушки сбоев: Таймаут, Медленный, Шаткий, Глухой.
  - Сбой моков не откатывает заявку: она остаётся в `DATA_CHECK` с `integration_error` (EC-10).
- [nfr.md](system/nfr.md):
  - Пароли хранятся хешем с солью.
  - Пользователю приложения выданы только `INSERT` и `SELECT` на `audit_log`.
  - Ни одного запроса без `LIMIT`; выборки по заявкам всегда с условием по `company_id` или `assignee_id`.
- [system-design.md](architecture/system-design.md), разделы про безопасность и сбои связи: проверка принадлежности данных компании на каждом эндпоинте (EC-16).
- [api-contract.md](system/api-contract.md):
  - раздел 3: формат ошибок RFC 9457, каталог кодов, `INTERNAL_ERROR` (3.2) — ответы формирует ядро;
  - раздел 4.1–4.3: вход, JWT (выдаёт и проверяет только ядро), `X-Active-Role`, `X-Internal-Token`;
  - раздел 5: `Idempotency-Key`, `version`, повторные действия.
- [roles.md](business/roles.md): права ролей — все проверки доступа в ядре.
- [logging.md](architecture/logging.md): поля лога, `correlationId` через MDC, ошибка логируется один раз на границе сервиса.

**Результат недели (до 15.11)**: заявка проходит путь от создания клиентом до взятия менеджером; есть интеграционный тест на Testcontainers и негативный тест на доступ к данным чужой компании.

## 3. Шлюз (`bff-gateway`) — Денис

**Задачи**
1. **Схема БД ядра — первым делом недели, до 10.11.** Миграции Flyway (SQL) в `core-service/src/main/resources/db/migration/`:
   - компании, пользователи, роли, членство;
   - заявка, `service_offer`, `request_stage`, `audit_log`, `request_revision`, `external_check`, `idempotency_key`;
   - права на таблицы: в миграции `audit_log` отозвать у пользователя приложения `UPDATE` и `DELETE` (скрипт ролей выдаёт их по умолчанию); чтение для `backup_ro`. Сами роли создаёт скрипт `infra/postgres/init` (DevOps), миграции роли не создают ([domain-model.md](system/domain-model.md), раздел 8);
   - демо-пользователи, роли и компании сида — отдельными миграциями в `db/demo/` только для профилей `DEMO` и тестового ([integrations.md](system/integrations.md), 5.1).
   Ревью — Кирилл; после слияния он пишет сущности. Миграции, которые Кирилл уже успел написать на этой неделе, остаются за ним; Денис продолжает со следующих таблиц, чтобы не переписывать готовое.
2. Скелет BFF на FastAPI (Pydantic v2, httpx). БД и состояния нет, экземпляр один.
3. Общий клиент к ядру с таймаутами; сбои (недоступно, таймаут) преобразуются в единый формат ошибки с `retryable: true`.
4. Сквозные заголовки: `X-Correlation-Id` (генерируется, если нет), `X-Internal-Token` к ядру, `X-Active-Role` от интерфейса.
5. Эндпоинты недели: вход, регистрация компании, создание, отправка, получение и список заявок, `claim`, `assign-manager`.
6. Внешний OpenAPI-контракт (`external-api.yaml`) для этих эндпоинтов — по слитому контракту ядра (раздел 8); ревью контракта ядра со стороны шлюза.
7. Заготовка проверки расхождения OpenAPI ядра и BFF для CI.

**Файлы и на что обратить внимание**

  - `Idempotency-Key` для создания, `version` в теле при изменении.
- [architecture.md](architecture/architecture.md), раздел про шлюз: бизнес-логики в BFF нет.
- [system-design.md](architecture/system-design.md):
  - Раздел 6: при сбое связи — ошибка в общем формате и обновление страницы запросом к ядру.
  - EC-10: ожидание не дольше бюджета повторов, около 7 с.
- [nfr.md](system/nfr.md): §7 — лимиты (в том числе тело JSON 1 МБ); §3 — целевое время отклика.
- [logging.md](architecture/logging.md): поля лога, `correlationId` через `contextvars`, преобразование недоступности ядра в `CORE_UNAVAILABLE` и `CORE_TIMEOUT`.

**Бизнес-правила и BFF (отдельный пункт)**

Бизнес-правил для BFF отдельно не готовится: шлюз их не реализует. Маршрутизация, статусы и переходы, SLA, права и бизнес-валидация выполняются только в ядре ([api-contract.md](system/api-contract.md), раздел 9; [architecture.md](architecture/architecture.md)). Источники правил: [routing-rules.md](system/routing-rules.md), [status-model.md](system/status-model.md), [sla.md](system/sla.md), [roles.md](business/roles.md). Шлюзу нужно другое:
- **Схемы эндпоинтов (OpenAPI)** — до кода: внутренний контракт `core-service/src/main/resources/openapi/core-api.yaml` пишет Кирилл, внешний `bff-gateway/openapi/external-api.yaml` — Денис по слитому внутреннему (раздел 8); пути, роли и переходы уже заданы в [api-contract.md](system/api-contract.md), раздел 6.
- **Правила формата полей** для Pydantic (длины, обязательность, форматы ИНН, телефона, email, лимиты): базовые значения в [nfr.md](system/nfr.md), раздел 7, и [domain-model.md](system/domain-model.md); полную таблицу по эндпоинтам готовит Дима к началу недели 2 ([plan-week2.md](plan-week2.md), раздел 6); для эндпоинтов недели 1 достаточно этих двух документов.
- **Матрица уведомлений** («событие → получатель → канал», состав сигнала WebSocket) — [notifications.md](system/notifications.md), готовит Дима к началу недели 2; до этого канал событий описан в [api-contract.md](system/api-contract.md), раздел 4.5.
- **Что отдавать роли в ответе** — решает ядро, BFF проксирует без фильтрации ([api-contract.md](system/api-contract.md), раздел 6.2).
- Если для шлюза нужно решение, которого нет в документах, вопрос идёт Диме до реализации, а не решается в коде шлюза.

**Результат недели (до 15.11)**: миграции недели слиты, и ядро стартует на них с `ddl-auto=validate`; через BFF проходит вся цепочка из задач ядра; при недоступном ядре пользователь получает корректную ошибку, а не `500`.

## 8. Согласование контрактов и правила работы без конфликтов

**Владельцы контрактов и схемы**
- Схема БД (`core-service/src/main/resources/db/migration/`) — Денис: SQL-миграции по [domain-model.md](system/domain-model.md), раздел 8. Ревью — Кирилл. Номера версий Flyway выдаёт только владелец папки, поэтому гонки за номера нет.
- Внутренний контракт ядра (`core-service/src/main/resources/openapi/core-api.yaml`) — Кирилл, полностью. Ядро генерирует серверные интерфейсы из этого файла, а не описывает API только аннотациями в коде: так код и контракт не расходятся.
- Внешний контракт шлюза (`bff-gateway/openapi/external-api.yaml`) — Денис. Пути и модели повторяют внутренний контракт ([api-contract.md](system/api-contract.md), раздел 6); отличаться может только представление под интерфейс (агрегация, WebSocket).

**Порядок на каждую неделю**
1. В начале недели Кирилл открывает PR с изменениями `core-api.yaml` на эндпоинты недели, а Денис — PR с миграциями таблиц недели; оба — первым делом, до реализации. Ревью контракта — Денис, ревью миграций — Кирилл.
2. После слияния Денис генерирует модели и открывает PR с `external-api.yaml`. Ревью: Егор (как потребитель).
3. Реализация в ядре, шлюзе и интерфейсе идёт параллельно по слитым контрактам.
4. Любое изменение `core-api.yaml` после слияния — отдельный PR с ревью Дениса; проверка расхождения в CI ловит пропуски.

**Чтобы задержка контракта ядра не блокировала остальных**
- Пока контракт недели не слит, Денис делает задачи, не зависящие от него: сид-скрипт, контрактные тесты, каркас WebSocket.
- После слияния контракта шлюз и интерфейс могут работать против заглушки ядра, поднятой из `core-api.yaml` (например, Prism или WireMock), не дожидаясь реализации.
- Если контракт недели не готов к середине недели (к среде), это сигнал руководителю: перенос эндпоинтов, а не работа «без контракта».

**Ревью**

| PR | Ревьюеры |
|---|---|
| Ядро (`core-service/`, кроме миграций) | Денис — контракт и поведение API; Дима или Салават — код на Java |
| Миграции БД | Кирилл |
| Шлюз (`bff-gateway/`) | Дима или Салават |
| Интерфейс (`ui/`) | По [team.md](team.md), правила работы |

Владельцы папок фиксируются в `CODEOWNERS`.

**Общие правила**

2. Контракт раньше кода; изменения контракта — только через PR.
