# Логирование

Документ закрывает часть задачи 16 ТЗ про логи. Формат ошибок API описан в [api-contract.md](../system/api-contract.md), раздел 3. Владелец: Салават, участвуют Кирилл и Денис.

## 1. Принципы

Логи нужны разработчику и тому, кто поддерживает стенд. История заявки живёт отдельно в `audit_log` в базе, пишется в той же транзакции, что и изменение заявки, и из логов её не восстанавливаем.

Каждый сервис пишет в stdout контейнера, по одной строке JSON на событие. Логи собирает Docker, отдельных систем сбора (Loki, ELK) нет. Prometheus-эндпоинт не поднимаем ([nfr.md](../system/nfr.md), раздел 9), Grafana в состав не входит.

Ядро пишет через SLF4J и Logback, BFF через `structlog` или стандартный `logging`. Формат и имена полей одинаковые.

## 2. Поля

| Поле | Что внутри |
|---|---|
| `timestamp` | Время события, UTC |
| `level` | `ERROR`, `WARN`, `INFO`, `DEBUG` |
| `service` | `core-service` или `bff-gateway` |
| `correlationId` | Сквозной идентификатор запроса |
| `message` | Короткое описание события |
| `userId`, `role` | Идентификатор пользователя и активная роль, если запрос авторизован |
| `requestId`, `stageId` | Идентификаторы заявки и этапа, если событие относится к ним |

Для вызовов внешних систем добавляем `system`, шаблон пути без значений (например `/billing/v1/accounts/{inn}/balance`, ИНН в логе не нужен), `status`, `durationMs`, `attempt` ([integrations.md](../system/integrations.md), раздел 8).

## 3. correlationId

Клиент может передать заголовок `X-Correlation-Id`, если его нет, BFF создаёт значение сам ([api-contract.md](../system/api-contract.md), раздел 2). Nginx заголовок не меняет и пишет его в свой access log. Идентификатор возвращается в ответе, уходит в ядро, ядро передаёт его в моки ([integrations.md](../system/integrations.md), раздел 3), записывается в `audit_log.correlation_id` и попадает в каждую строку лога. В ядре для этого используем MDC, в BFF переменную контекста (`contextvars`).

## 4. Уровни

- `ERROR`: ответы 5xx, необработанные исключения, исчерпанные повторы вызова внешней системы.
- `WARN`: повторная попытка вызова мока, запрос отклонён по правам.
- `INFO`: ключевые события: создание заявки, смена статуса, срабатывание таймера SLA, вход пользователя.
- `DEBUG`: только при отладке, на стенде и демо выключен.

Ошибку логируем один раз, в общем обработчике на границе сервиса, вместе со стеком. Клиенту стек не отдаём, ему достаточно `correlationId` из тела ответа. Ядро превращает необработанное исключение в ответ `application/problem+json`, BFF так же превращает недоступность ядра в `CORE_UNAVAILABLE` или `CORE_TIMEOUT`. Кода для ответа 500 в каталоге пока нет (см. вопросы ниже).

## 5. Чего в логах не должно быть

Пароли, токены (JWT, `X-Internal-Token`), тела ответов внешних систем (они хранятся в `external_check`), реквизиты и суммы. Вместо значений пишем идентификаторы. CI ищет в логах прогона пароли, токены и тела ответов внешних систем, а `gitleaks` проверяет репозиторий ([nfr.md](../system/nfr.md), раздел 8). Реквизиты и суммы поиском не поймать, их контролирует ревью кода.

## 6. Ротация и поиск

Ротацию делает Docker: драйвер `json-file` с ограничением размера и числа файлов. Значения (предлагаю 10 МБ и 3 файла) уточним при сборке compose.

Искать по запросу так: `docker compose logs nginx bff-gateway core-service | grep <correlationId>`. Историю изменений заявки смотрим в `audit_log` по тому же `correlation_id`.
