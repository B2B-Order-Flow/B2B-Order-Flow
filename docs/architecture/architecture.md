# Архитектура B2B-Order-Flow

## 1. Архитектурный подход

В системе применяется **гибридная микросервисная архитектура (BFF + Транзакционное ядро)**.

**Обоснование:** Команда состоит из 5 человек с четким распределением компетенций между Python и Java. Выделение FastAPI в качестве API Gateway / BFF (Backend-for-Frontend) позволяет гибко и итеративно управлять контрактами интерфейса, валидацией DTO и поддержкой WebSockets. В то же время Spring Boot (Java 21) обеспечивает надежное, высоконагруженное транзакционное ядро для сложной доменной логики, статусного автомата, маршрутизации и контроля SLA.

---

## 2. Транспортный слой и двухслойный REST API

Взаимодействие компонентов системы построено на основе **двухслойного REST API (HTTP/JSON)** и протокола **WebSockets**:


```

[ Frontend (React / UI) ]
│
│ 1. Внешний REST API (HTTP/JSON)
│    + WebSockets (Real-time notifications)
▼
[ API Gateway / BFF (Python / FastAPI) ]
│
│ 2. Внутренний REST API (HTTP/JSON)
│    (Защищенная приватная сеть Docker / DMZ)
▼
[ Core Service (Java 21 / Spring Boot) ]

```

### 2.1. Внешний REST API (Frontend ↔ FastAPI BFF)
- **Организация:** Фронтенд (React) отправляет REST-запросы исключительно на единую точку входа — FastAPI BFF.
- **Обработка:** FastAPI выполняет первичную асинхронную валидацию входящих JSON-пейлоадов через **Pydantic v2**, проверяет JWT-токены, форматирует DTO под потребности UI и генерирует внешнюю документацию OpenAPI (Swagger UI).

### 2.2. Внутренний REST API (FastAPI BFF ↔ Java Core)
- **Организация:** FastAPI преобразует запросы пользователей и вызывает микросервис транзакционного ядра по внутреннему REST API (используя асинхронный HTTP-клиент `httpx`).
- **Безопасность и изоляция:** Внутренний REST API развернут во внутренней изолированной Docker-сети и недоступен для внешнего интернета.
- **Обработка:** Spring Boot принимает HTTP-запросы, выполняет бизнес-логику в рамках ACID-транзакции со своей БД (`core_db`), пишет аудиторский лог и возвращает строго валидированный JSON-ответ.

---

## 3. Стратегия работы с Базами Данных (Паттерн Database-per-Service)

В системе реализован классический микросервисный паттерн **Database-per-Service**. Каждый микросервис владеет своей собственной изолированной базой данных PostgreSQL 16. Прямой доступ к базам друг друга сервисам запрещен.

1. **БД Сервиса BFF / API Gateway (`fastapi_db`):**
   - Принадлежит исключительно FastAPI-приложению.
   - Оптимизирована под быстрые операции чтения/записи шлюза, кэширование, хранение пользовательских сессий, контекстов запросов и маппинг активных WebSocket-подключений.
2. **БД Транзакционного ядра (`core_db`):**
   - Принадлежит исключительно Spring Boot (Java) ядру.
   - Управляется через миграции Flyway.
   - Закрытая, высоконагруженная реляционная БД, хранящая всю критическую доменную модель: заявки (`requests`), этапы (`request_stages`), задачи согласований (`approval_tasks`), аудиторские логи (`audit_logs`) и метаданные документов.

**Преимущество:** Полная изоляция бизнес-ядра от операционного веб-шума (устранение I/O Bottleneck и исключение исчерпания пула соединений БД), независимость разработки для Дениса и Кирилла.

## 4. Система реалтайм-уведомлений (WebSockets & Events)

Для мгновенного информирования пользователей без постоянного опроса сервера (polling) реализована асинхронная шина событий:

1. **Генерация события в ядре (Java):** При смене статуса заявки, возврате на доработку, появлении новой задачи в очереди или срабатывании SLA-таймера Spring Boot генерирует событие через `Spring Events`.
2. **Передача на шлюз:** Ядро отправляет внутренний защищенный REST-вызов/вебхук на FastAPI-шлюз.
3. **Доставка до клиента (WebSockets):** FastAPI через пул активных WebSocket-соединений пушит уведомление в браузер конкретному пользователю или на всю очередь соответствующей роли.

## 5. Работа с документами, вложениями и экспортом

### 5.1. Управление вложениями
- **Загрузка:** Прикрепление файлов (сканы договоров, протоколы разногласий) к заявке или этапу.
- **Хранение:** Физические файлы сохраняются в защищенном хранилище (локальная файловая система контейнера / S3-мок), а их метаданные (имя, размер, тип, ID заявки, автор) фиксируются в реляционной БД ядра. Доступ строго разграничен через Spring Security.

### 5.2. Генерация документов и экспорт
- **Генерация:** Автоматическое формирование печатных форм (договоры, оферты, акты сдачи-приемки) на основе шаблонов и актуальных данных конкретной заявки на этапах подписания и закрытия.
- **Экспорт отчетов:** Выгрузка реестров заявок, историй изменений и аналитики по соблюдению SLA в форматы CSV/PDF для координаторов и руководства.

## 6. Безопасность, надежность и инфраструктурные ответы

### 6.1. Конфиденциальность и хранение данных
- **Конфиденциальные данные:** Персональные данные пользователей, ИНН/ОГРН компаний, индивидуальные цены, коммерческие скидки, объемы CAPEX, финансовые параметры отмены и неизменяемый журнал аудита (`AuditLog`).
- **Локализация хранения:** Вся конфиденциальная бизнес-информация хранится исключительно в **БД-2 (`core_db`)**. База находится в изолированном приватном контуре Docker-сети, закрыта от прямого доступа из внешнего интернета и защищена авторизацией на уровне Spring Security (JWT + BCrypt).

### 6.2. Локализация компонентов SLA, истории и уведомлений
- **Контроль SLA:** Инкапсулирован в Java-ядре. Фоновый сервис (`@Scheduled` + `Clock`) циклически проверяет активные этапы (`RequestStage`), рассчитывает пороги предупреждений (осталось 25% времени) и генерирует события эскалации.
- **История изменений:** Фиксируется в таблице `audit_logs` внутри `core_db`. Каждая смена статуса, решение согласующего или возврат на доработку записываются атомарно.
- **Уведомления:** Генерируются Java-ядром (`Spring Events`) и передаются на FastAPI BFF, который удерживает WebSocket-соединения с UI.

### 6.3. Обеспечение согласованности данных при сбоях
- **Транзакционность (ACID):** Все доменные операции в Java-ядре выполняются под управлением `@Transactional`. При сбое на любом шаге происходит полный откат транзакции в PostgreSQL.
- **Устойчивость к сбоям внешних моков:** При недоступности Mock-сервисов (CRM, биллинг) интеграционный слой использует паттерн **Spring Retry** (повторные попытки с экспоненциальной задержкой).

## 7. Структура проекта

```text
B2B-Order-Flow/
├── api-gateway/       — FastAPI BFF (двухслойный REST API, валидация DTO, WebSockets, fastapi_db)
├── core-service/      — Java Spring Boot ядро (домен, FSM, маршруты, SLA, документы, core_db)
├── ui/                — React панель оператора и клиентский контур
├── mocks/             — WireMock / мок-сервисы внешних систем (CRM, биллинг)
├── infra/             — Docker Compose, конфигурации баз данных
├── tests/             — Интеграционные и E2E тесты (Testcontainers, Playwright)
└── docs/              — Документация (Markdown, Mermaid)

```

## 8. Итоговый технологический стек

| Слой / Компонент | Технология |
| --- | --- |
| **API Gateway / BFF** | Python 3.11+, FastAPI, Pydantic v2, Uvicorn, WebSockets, httpx |
| **Транзакционное ядро** | Java 21, Spring Boot 3.x, Spring Data JPA, Spring Events |
| **Межсервисный транспорт** | Двухслойный REST API (HTTP/JSON) + WebSockets |
| **Базы данных** | PostgreSQL 16 (2 изолированные БД: `fastapi_db` и `core_db`) |
| **Миграции БД** | Flyway (для `core_db`) |
| **Безопасность** | Spring Security + JWT (jjwt) + BCrypt |
| **Документация API** | OpenAPI (Swagger UI) / FastAPI docs |
| **Интеграции** | RestTemplate / WebClient, Spring Retry |
| **SLA-контроль** | Spring `@Scheduled` + `Clock` |
| **Фронтенд** | React, Vite, Axios, React Router |
| **Тестирование** | JUnit 5, Testcontainers, Playwright, WireMock |
| **Контейнеризация** | Docker, Docker Compose |
| **CI/CD** | GitHub Actions |
