# Архитектура B2B-Order-Flow

## 1. Архитектурный подход

В системе применяется **гибридная микросервисная архитектура (BFF + Транзакционное ядро)**.

**Обоснование:** 
1. Выделение FastAPI в качестве BFF (Backend-for-Frontend) позволяет гибко управлять контрактами интерфейса, валидацией DTO и поддержкой WebSockets, не нагружая транзакционное ядро.
2. Spring Boot (Java 21) обеспечивает надежное транзакционное ядро для сложной доменной логики, статусного автомата, маршрутизации и контроля SLA.
3. BFF является stateless-сервисом (без собственной БД), что упрощает горизонтальное масштабирование и сохраняет единую точку правды для данных.

---

## 2. Транспортный слой и двухслойный REST API

Взаимодействие компонентов системы построено на основе **двухслойного REST API (HTTP/JSON)** и протокола **WebSockets**:

```text
[ Frontend (React / UI) ]
│
│ 1. Внешний REST API (HTTP/JSON)
│    + WebSockets (Real-time notifications)
▼
[ Nginx (Reverse Proxy / TLS) ]
│
│ 2. HTTP/WS
▼
[ BFF (Python / FastAPI) - Stateless ]
│
│ 3. Внутренний REST API (HTTP/JSON)
│    (Защищенная приватная сеть Docker)
▼
[ Core Service (Java 21 / Spring Boot 4.1.x) ]
```

- **Внешний REST API (Frontend ↔ FastAPI BFF):** Фронтенд (React) отправляет REST-запросы исключительно на BFF. FastAPI выполняет первичную валидацию входящих JSON-пейлоадов через **Pydantic v2**, проверяет JWT-токены, форматирует DTO под потребности UI и генерирует внешнюю документацию OpenAPI.
- **Внутренний REST API (FastAPI BFF ↔ Java Core):** FastAPI вызывает ядро по внутреннему REST API (используя `httpx` с явными таймаутами). Spring Boot принимает запросы, выполняет бизнес-логику в рамках ACID-транзакции со своей БД (`core_db`), пишет аудиторский лог и возвращает строго валидированный ответ.

---

## 3. Стратегия работы с Базами Данных и JSONB

В системе используется **единая реляционная база данных PostgreSQL 16 (`core_db`)**. Отказ от паттерна Database-per-Service в пользу одной БД обусловлен необходимостью сохранения строгих ACID-транзакций (изменение статуса, запись аудита и создание задач должны быть атомарными).

**Правило использования JSONB:**
*   **Обычные колонки:** Абсолютно все поля, которые участвуют в бизнес-логике (статусы, суммы, даты, связи). Любое поле, которое фильтруется, сортируется, JOIN-ится или влияет на логику SLA — строго колонка.
*   **JSONB (Postgres):** Используется исключительно для гибких полей, которые читаются целиком (например, «сырые» payload-ответы от Mock-сервисов для истории, либо произвольные атрибуты услуги, не требующие поиска). Класть в JSONB данные для фильтрации запрещено.

## 4. Асинхронная обработка и брокер сообщений

На этапе MVP для внутренних событий используется механизм `Spring Events` в связке с паттерном **Transactional Outbox** (сначала пишем уведомление в БД в одной транзакции с бизнес-изменением, затем после коммита через `@TransactionalEventListener` отправляем сигнал на FastAPI).

**Путь к развитию (Брокер):**
Архитектура спроектирована с учетом внедрения **RabbitMQ** при росте нагрузки. В будущем брокер возьмет на себя:
*   Асинхронную доставку уведомлений (разгрузка основного потока).
*   Выполнение тяжелых ресурсоемких задач (генерация PDF-документов, экспорт отчетов).
*   Интеграции с внешними системами по паттерну Saga.

---

## 5. Безопасность и Аутентификация

- **JWT:** Выдает и валидирует исключительно Java-ядро. BFF только проксирует запрос логина и отбрасывает невалидные токены.
- **Права доступа (RBAC):** Все решения о правах (кто может согласовать, менять статус) принимаются в Java-ядре на основе JWT и ролей.
- **Reverse Proxy (Nginx):** Единственная точка входа из внешнего мира. Терминирует TLS, раздает статику React и проксирует запросы на BFF.
- **WebSocket Auth:** Браузер не передает заголовки в WS, поэтому используется механизм одноразовых билетов (Ticket), получаемых по REST.

## 6. Структура проекта

```text
B2B-Order-Flow/
├── bff-gateway/       — FastAPI BFF (Stateless: REST прокси, валидация, WebSockets)
├── core-service/      — Java 21 Spring Boot (домен, FSM, маршруты, SLA, core_db)
├── ui/                — React панель оператора и клиентский контур
├── mocks/             — WireMock моки внешних систем (CRM, биллинг)
├── infra/             — Docker Compose, Nginx, GitHub Actions
└── docs/              — Документация (Markdown, Mermaid)
```

## 7. Итоговый технологический стек

| Слой / Компонент | Технология |
| --- | --- |
| **Reverse Proxy** | Nginx (TLS, статика, rate limit) |
| **BFF** | Python 3.12+, FastAPI, Pydantic v2, WebSockets, httpx |
| **Транзакционное ядро** | **Java 21**, Spring Boot 4.1.x, Spring Data JPA, Spring Security |
| **База данных** | PostgreSQL 16 (единая `core_db`) |
| **Миграции БД** | Flyway |
| **Аутентификация** | OAuth2 Resource Server (JWT) |
| **Интеграции** | Spring RestClient, Spring Retry (вне `@Transactional`) |
| **SLA-контроль** | Spring `@Scheduled` + `Clock` |
| **Брокер (Будущее)** | RabbitMQ (для Outbox и тяжелых задач) |
| **Фронтенд** | React, Vite, TanStack Query, React Router |
| **Тестирование** | JUnit 5, Testcontainers, Playwright, WireMock, pytest |
| **Контейнеризация** | Docker, Docker Compose |
| **CI/CD** | GitHub Actions |
