# Архитектура

## Подход

Модульный монолит.

Обоснование: команда 5 человек, срок 3 месяца. Микросервисы дают изоляцию, но требуют больше ресурсов на инфраструктуру, CI/CD и координацию. Микросервисная архитектура не выбрана.

## Компоненты системы

### Core — ядро
Назначение: доменная логика.

Содержит:
- Доменные сущности (заявка, этап, согласование, клиент)
- Статусная модель
- Движок маршрутизации
- Контроль SLA
- История изменений

### API — REST-интерфейс
Назначение: единая точка взаимодействия с системой.

Содержит:
- Контроллеры
- DTO
- Мапперы
- OpenAPI-спецификация

### Integration — интеграции
Назначение: взаимодействие с внешними системами.

Содержит:
- Клиент к mock CRM
- Клиент к mock биллингу
- Клиент к mock справочнику клиентов
- Обработка ошибок и retry

### Notification — уведомления
Назначение: уведомление участников процесса.

Содержит:
- Отправка email (заглушка)
- Отправка in-app уведомлений
- Шаблоны уведомлений

### UI — панель оператора
Назначение: пользовательский интерфейс.

Содержит:
- Список заявок
- Карточка заявки
- Форма создания
- Действия по ролям

### Mocks — mock-сервисы
Назначение: эмуляция внешних систем.

Содержит:
- Mock CRM
- Mock биллинг
- Mock справочник клиентов

Реализация: WireMock с синтетическими данными и документированными контрактами.

## Структура проекта
```text
B2B-Order-Flow/
├── core/ — ядро (домен, маршрутизация, SLA, история)
├── api/ — REST API
├── integration/ — интеграции с mock-сервисами
├── notification/ — уведомления
├── ui/ — панель оператора
├── mocks/ — mock-сервисы
├── infra/ — Docker, CI/CD
├── db/ — миграции БД
├── tests/ — тесты
└── docs/ — документация
```

## Взаимодействие компонентов

|---|---|---|
| UI | API | REST |

| Core | Integration | Внутренние вызовы |

## API Gateway

Не требуется.

Обоснование: система реализована как модульный монолит с единой точкой входа (API). Gateway нужен при микросервисной архитектуре, когда есть несколько сервисов и требуется единая точка маршрутизации. В монолите эту роль выполняет сам API-слой.

## Взаимодействие с внешними системами

Внешние системы (CRM, биллинг, справочник клиентов) эмулируются через mock-сервисы (WireMock).

Контракты:
- REST API
- JSON
- Документированы в OpenAPI

Обработка ошибок:
- Таймаут
- Retry
- Fallback

## Ограничения

- Один деплой
- Одна БД
- Нет горизонтального масштабирования
- Модули связаны в одном процессе
