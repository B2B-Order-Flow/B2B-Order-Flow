# Архитектура B2B-Order-Flow

## 1. Архитектурный подход

В системе применяется **гибридная микросервисная архитектура (BFF + Транзакционное ядро)**.

**Обоснование:** 
1. Выделение FastAPI в качестве BFF (Backend-for-Frontend) позволяет гибко управлять контрактами интерфейса, валидацией DTO и поддержкой WebSockets, не нагружая транзакционное ядро.
2. Spring Boot (Java 21) обеспечивает надежное транзакционное ядро для сложной доменной логики, статусного автомата, маршрутизации и контроля SLA.
3. BFF не имеет собственной БД и не принимает решений о правах и статусах: единая точка правды — ядро (`core_db`). BFF хранит только живые WebSocket-соединения, поэтому в MVP работает одним экземпляром; при горизонтальном масштабировании понадобится общий pub/sub для рассылки событий.
4. Разделение зон ответственности: контур API и интерфейса отделён от доменного ядра, а OpenAPI-контракт BFF ↔ ядро (подход contract-first) служит единым источником DTO и правил валидации.

---

## 2. Транспортный слой и двухслойный REST API

Взаимодействие компонентов системы построено на основе **двухслойного REST API (HTTP/JSON)** и протокола **WebSockets**:

```text
[ Frontend (React / UI) ]
│
│ 1. Внешний REST API (HTTP/JSON)
│    + WebSockets (Real-time notifications)
▼
[ Nginx (Reverse Proxy / TLS) ]
│
│ 2. HTTP/WS
▼
[ BFF (Python / FastAPI) - Stateless ]
│
│ 3. Внутренний REST API (HTTP/JSON)
│    (Защищенная приватная сеть Docker)
▼
[ Core Service (Java 21 / Spring Boot 4.1.x) ]
```

- **Внешний REST API (Frontend ↔ FastAPI BFF):** Фронтенд (React) отправляет REST-запросы исключительно на BFF. FastAPI выполняет первичную валидацию входящих JSON-пейлоадов через **Pydantic v2**, пробрасывает JWT-токен ядру (решение о доступе принимает только ядро), форматирует DTO под потребности UI и генерирует внешнюю документацию OpenAPI.
- **Внутренний REST API (FastAPI BFF ↔ Java Core):** FastAPI вызывает ядро по внутреннему REST API (используя `httpx` с явными таймаутами). Spring Boot принимает запросы, выполняет бизнес-логику в рамках ACID-транзакции со своей БД (`core_db`), пишет аудиторский лог и возвращает строго валидированный ответ.

## 3. Стратегия работы с Базами Данных и JSONB

В системе используется **единая реляционная база данных PostgreSQL 16 (`core_db`)**. Отказ от паттерна Database-per-Service в пользу одной БД обусловлен необходимостью сохранения строгих ACID-транзакций (изменение статуса, запись аудита и создание задач должны быть атомарными).

**Правило использования JSONB:**
*   **Обычные колонки:** Абсолютно все поля, которые участвуют в бизнес-логике (статусы, суммы, даты, связи). Любое поле, которое фильтруется, сортируется, JOIN-ится или влияет на логику SLA — строго колонка.
*   **JSONB (Postgres):** Используется исключительно для гибких полей, которые читаются целиком (например, «сырые» payload-ответы от Mock-сервисов для истории, либо произвольные атрибуты услуги, не требующие поиска). Класть в JSONB данные для фильтрации запрещено. Полная схема сущностей — [domain-model.md](../system/domain-model.md).

## 4. Асинхронная обработка и брокер сообщений

На этапе MVP уведомления хранятся в таблице `notification` ядра: запись создаётся в одной транзакции с бизнес-изменением (статус, аудит, этап). После коммита ядро отправляет сигнал на BFF (`@TransactionalEventListener(AFTER_COMMIT)`), а фоновая задача доотправляет записи с пустым `published_at`. WebSocket служит сигналом, а не источником данных: после реконнекта или ошибки интерфейс перечитывает непрочитанные уведомления по REST. Это упрощённый вариант Transactional Outbox; полноценный релей с брокером добавляется на этапе развития.

**Путь к развитию (Брокер):**
Архитектура спроектирована с учетом внедрения **RabbitMQ** при росте нагрузки. В будущем брокер возьмет на себя:
*   Асинхронную доставку уведомлений (разгрузка основного потока).
*   Выполнение тяжелых ресурсоемких задач (генерация PDF-документов, экспорт отчетов).
*   Интеграции с внешними системами по паттерну Saga.

## 5. Безопасность и Аутентификация

- **JWT:** Выдаёт и проверяет исключительно Java-ядро при каждом запросе. BFF пробрасывает запрос логина и заголовок `Authorization` без интерпретации; ядро не доверяет BFF и само принимает все решения о доступе. Вызовы BFF → ядро дополнительно аутентифицируются межсервисным секретом (подписанный заголовок), чтобы ядро нельзя было вызвать напрямую из соседних контейнеров.
- **Права доступа (RBAC):** Все решения о правах (кто может согласовать, менять статус) принимаются в Java-ядре на основе JWT и ролей.
- **Активная роль:** пользователь переключает роль в интерфейсе; BFF передаёт её заголовком `X-Active-Role`, ядро проверяет, что роль есть у пользователя, и применяет права именно этой роли. Доступ к данным компании и к заявке определяет единая политика доступа ядра ([system-design.md](system-design.md), раздел 5).
- **Reverse Proxy (Nginx):** Единственная точка входа из внешнего мира. Терминирует TLS, раздает статику React и проксирует запросы на BFF.
- **WebSocket Auth:** Браузер не передает заголовки в WS, поэтому используется механизм одноразовых билетов (Ticket), получаемых по REST.

## 6. Обработка сбоев связи и конкурентность

Принцип: **ядро — единственный источник истины; при сбоях система сообщает об ошибке и не пытается компенсировать их** (никаких саг и очередей повторов между BFF и ядром).

- **Единый формат ошибок:** `application/problem+json` (RFC 9457) с полями `type`/`code`, `title`, `status`, `detail`, `correlationId`, `retryable`. Недоступность ядра или таймаут — `502/503/504`, конфликт версий — `409`, ошибка валидации — `422`.
- **Поведение интерфейса:** при ошибке с `retryable = true` показывает сообщение и перезапрашивает актуальное состояние заявки у ядра.
- **Повторы:** BFF автоматически повторяет только чтения (GET). Записи (POST/PUT/PATCH) автоматически не повторяются.
- **Неопределённый исход записи** (ядро выполнило действие, ответ потерян): создание заявки защищено заголовком `Idempotency-Key`; переходы статусов идемпотентны — повторное действие из уже изменённого статуса получает `409`.
- **Конкурентные изменения:** оптимистичная блокировка (`version` в сущностях, `@Version` в JPA); конфликт — `409`.
- **Таймауты по уровням:** внутренний всегда меньше внешнего — вызов mock-сервиса с повторами < обработчик ядра < таймаут `httpx` в BFF < таймаут Nginx. Ожидание недоступной внешней системы (EC-10) не блокирует HTTP-запрос: заявка остаётся в статусе «Проверка данных», перепроверку выполняет фоновая задача.

## 7. Структура проекта

```text
B2B-Order-Flow/
├── bff-gateway/       — FastAPI BFF (Stateless: REST прокси, валидация, WebSockets)
├── core-service/      — Java 21 Spring Boot (домен, FSM, маршруты, SLA, core_db)
├── ui/                — React панель оператора и клиентский контур
├── mocks/             — WireMock моки внешних систем (CRM, биллинг)
├── infra/             — Docker Compose, Nginx, GitHub Actions
└── docs/              — Документация (Markdown, Mermaid)
```

## 8. Итоговый технологический стек

| Слой / Компонент | Технология |
| --- | --- |
| **Reverse Proxy** | Nginx (TLS, статика, rate limit) |
| **BFF** | Python 3.12+, FastAPI, Pydantic v2, WebSockets, httpx |
| **Транзакционное ядро** | **Java 21**, Spring Boot 4.1.x, Spring Data JPA, Spring Security |
| **База данных** | PostgreSQL 16 (единая `core_db`) |
| **Миграции БД** | Flyway |
| **Аутентификация** | OAuth2 Resource Server (JWT) |
| **Интеграции** | Spring RestClient, Spring Retry (вне `@Transactional`) |
| **SLA-контроль** | Spring `@Scheduled` + `Clock` |
| **Брокер (Будущее)** | RabbitMQ (для Outbox и тяжелых задач) |
| **Фронтенд** | React, Vite, TanStack Query, React Router |
| **Тестирование** | JUnit 5, Testcontainers, Playwright, WireMock, pytest |
| **Контейнеризация** | Docker, Docker Compose |
| **CI/CD** | GitHub Actions |
