# ADR 001. Выбор архитектуры и технологического стека

## Статус

Принято.

## Дата

2026-10-03

## Контекст

Разрабатывается учебный прототип системы обработки и согласования заявок на подключение B2B-услуг для заказчика ООО «МТС ДИДЖИТАЛ».

Условия:
- Команда: 5 человек
- Срок: 3 месяца
- Тип проекта: прикладной
- Сложность: А
- Внешние системы эмулируются (mock-сервисы)

По ТЗ требуется:
- Выбрать архитектурный подход (модульный монолит или микросервисы)
- Обосновать выделение компонентов системы
- Реализовать взаимодействие через REST API, брокер сообщений или другое
- Реализовать API Gateway, если требуется архитектурой

## Рассмотренные варианты

### Вариант 1. Микросервисная архитектура

Каждый модуль (Core, Integration, Notification) — отдельный сервис.

Плюсы:
- Независимые деплои
- Изоляция отказов
- Можно масштабировать отдельные сервисы

Минусы:
- Требует отдельных команд на сервис
- Требует инфраструктуры (orchestration, service mesh, gateway)
- Распределённые транзакции — сложно
- Распределённое логирование и трейсинг — сложно
- Время на инфраструктуру — 1–2 месяца из 3
- Сложнее тестировать и отлаживать

### Вариант 2. Модульный монолит

Одно приложение с чётким разделением на модули.

Плюсы:
- Один деплой
- Одна БД
- Один CI/CD
- Проще тестировать
- Проще отлаживать
- Быстрее старт
- Модули можно выделить в сервисы при необходимости

Минусы:
- Модули в одном процессе
- Нет горизонтального масштабирования
- Один деплой на всё

## Решение

Выбран вариант 2 — модульный монолит.

## Обоснование

- Команда 5 человек — нет ресурсов на отдельные команды на каждый сервис
- Срок 3 месяца — микросервисы требуют 1–2 месяца только на инфраструктуру
- Учебный прототип — не требует горизонтального масштабирования
- Модульная структура — чёткие границы, каждый модуль можно выделить в сервис при необходимости
- Микросервисы — организационная модель для больших команд, у нас маленькая команда

## Выделение компонентов

| Компонент | Назначение |
|---|---|
| Core | Домен, статусы, маршрутизация, SLA, история |
| API | REST-интерфейс |
| Integration | Взаимодействие с mock-сервисами |
| Notification | Уведомления |
| UI | Панель оператора |
| Mocks | Mock CRM, биллинг, справочник клиентов |

## Технологический стек

| Слой | Технология |
|---|---|
| Язык | Java 21 |
| Фреймворк | Spring Boot 3.x |
| БД | PostgreSQL 16 |
| ORM | Spring Data JPA |
| Миграции | Flyway |
| Брокер | RabbitMQ |
| API | REST + OpenAPI (SpringDoc) |
| UI | React / Vue |
| Mock | WireMock |
| Тесты | JUnit 5 + Testcontainers |
| Контейнеры | Docker + Docker Compose |
| CI/CD | GitHub Actions |

Обоснование стека:
- Java + Spring Boot — готовая экосистема: JPA, Security, Scheduling, Validation
- PostgreSQL — стандарт, надёжная, легко в Docker
- RabbitMQ — проще Kafka для учебного проекта
- WireMock — без кода, документированные контракты

## API Gateway

Не требуется.

Обоснование: система — модульный монолит с единой точкой входа (API). Gateway нужен при микросервисной архитектуре, когда несколько сервисов и требуется единая точка маршрутизации. В монолите эту роль выполняет сам API-слой.

## Последствия

- Один деплой
- Одна БД
- Один CI/CD
- Проще тестировать и отлаживать
- Нет горизонтального масштабирования
- Модули связаны в одном процессе
